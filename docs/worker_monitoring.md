# Мониторинг обработчиков

Дополнение 02.11.2026: пятый сервис **Telegram — сотрудники** (`telegram_staff`).
Необходим только при включённом боте, username и источнике токена; local_test —
disabled. Те же heartbeat, блокировки, адаптеры и оповещения.
[Конфигурация и техническая очередь](telegram_staff_bot.md).

Страница **Интеграции → Обработчики**, `/crm/integrations/workers/`, доступна каждому
активному авторизованному сотруднику. Управление — только `is_superuser`, POST и CSRF.
Права API-ключей, Avito, Яндекса и продаж не расширяются.

## Установка и запуск

Миграция `integrations.0009_worker_monitoring` добавляет технические таблицы
`WorkerController`, `WorkerService`, `WorkerProcess`, `WorkerCommand`, `WorkerEvent`.
Она не меняет прежние очереди, товары или финансы. **На рабочей БД при разработке
миграция не применяется.** Для внедрения нужны отдельное разрешение, проверенный
миграционный план и согласованный SQLite-снимок по `operations.md`. Защищённую
копию `backups/current_state_20261031.sqlite3` сохранять по правилам проекта.

После согласования: проверить отсутствие выполняемой физической печати, остановить
только проверенные процессы проекта, применить `.venv\Scripts\python.exe manage.py migrate`,
перезапустить сайт и worker для загрузки нового кода. При `--noreload` сам сайт код
не перечитает. Секреты и медиа резервируются отдельно. Затем открыть штатный ярлык
и проверить подтверждённые статусы. Не запускать синхронизации ради проверки UI.

Обычный `start_localhost.ps1` сохраняет исправный сайт, задаёт технический режим
`managed` и запускает скрытый `run_worker_supervisor`. Только контроллер запускает
необходимые worker. Повторный ярлык не сбрасывает счётчики и историю. Журналы
процессов в `outputs/localhost/` не перезаписываются.

`-SiteOnly` не запускает supervisor, интеграции или печать. При отсутствии действующего
supervisor устанавливается технический режим `site_only`: отсутствие worker не авария.
При уже работающем supervisor сохраняются его режим и процессы; `-SiteOnly` не является
их принудительной остановкой. Настройки бизнес-интеграций не меняются.

Отдельный запуск, способный возобновить реальные очереди:

```powershell
.venv\Scripts\python.exe manage.py configure_worker_monitoring
.venv\Scripts\python.exe manage.py run_worker_supervisor
```

`--once` у контроллера и worker означает настоящий цикл, не имитацию. Применять
к рабочей среде только намеренно. В тестах адаптер ОС, API и печать подменяются.

## Ожидаемая работа

| Сервис | Когда необходим |
| --- | --- |
| Avito | Оба зашифрованных реквизита и прежняя успешная проверка `last_success_at` |
| Яндекс | `Integration.enabled=True` и источник ключа в окружении либо файл ключа |
| Google Sheets | `enabled=True`, ID таблицы и существующий файл Service Account |
| Печать | Валидная локальная конфигурация принтера на Windows |

Ненастроенный сервис получает «Не настроен», явный `enabled=False` — «Отключён».
Ошибка API после успешной настройки не отключает наблюдение. Наличие источника ключа
не доказывает его пригодность: отказ API остаётся ошибкой задания. Мониторинг не
проверяет API. Печать остаётся необходимой для старых заданий отключённого Маркета.
Отключение не удаляет задания и не переводит их в успешные.

## Подтверждение и восстановление

Интервалы именованы в `worker_runtime.py`: контроль и браузер — 15 секунд, heartbeat
worker — 20 секунд, допустимая давность — 90 секунд. Heartbeat использует отдельный
поток и отдельное Django-соединение: длительная задача не выглядит остановкой.
Единичная блокировка SQLite пропускает запись; следующая попытка её повторяет.
Свежесть heartbeat оценивается после чтения CIM и подтверждений из БД: запись,
поступившая во время инвентаризации, не считается ошибочной будущей датой.

Windows-проверка учитывает проектный интерпретатор, путь `manage.py`, команду,
очереди, UUID экземпляра, PID и время создания. Повторно использованный PID не
принимает старое подтверждение. Живой процесс без heartbeat не дублируется и не
завершается автоматически: статус неизвестен. Недоступность CIM или таймаут также
запрещают запуск. Старые worker принимаются под наблюдение, но без нового heartbeat
остаются неизвестными до согласованного обновления процесса.

Контроллер удерживает файловую блокировку весь срок жизни, worker — блокировки
обслуживаемых очередей. `--service all` и отсутствие `--service` покрывают все три.
ОС освобождает блокировки при завершении. Файлы в `outputs/localhost/workers/`
не удалять во время работы. При запуске сохраняется намерение с UUID **до** создания
процесса; новый контроллер сперва сверяет процессы, не повторяя неоднозначный запуск.

На появление heartbeat отводится 45 секунд, затем нужна минута стабильного
подтверждения. До этого — «Восстанавливается». После неудач задержки 15/30/60 секунд;
максимум три последовательные неудачи инцидента. Кратковременное появление процесса
не обнуляет счётчик. После трёх неудач автовосстановление приостанавливается,
остальные сервисы продолжают работу. Перезагрузка страницы, ярлыка или контроллера
не снимает блокировку. Ошибки задач/API/бумаги не увеличивают счётчик запуска.

## Ручные команды и интерфейс

HTTP только ставит команду с UUID в очередь. Уникальные ограничения, транзакции
SQLite IMMEDIATE и существующий повтор блокировки БД объединяют одновременные
запросы. Исполняет supervisor, команды ОС фиксированы, `shell=True` не используется.
«Запустить» восстанавливает необходимый остановленный сервис; «Восстановить все»
не перезапускает исправные и не включает отключённые. Результат отдельный по сервису:
принято, выполняется, подтверждено либо ошибка. Ручная попытка после лимита разрешена;
её неудача не открывает бесконечную серию. Блокировку снимает стабильный успех.

Четыре сервиса показаны в постоянном порядке. Следующие действия читаются из
настоящих очередей: при готовых задачах Avito предпочитает ручные/статусные, Яндекс —
события/заказы. Среди будущих задач берётся ближайший фактический срок. Выполняемая
задача, безопасная фаза Avito и просрочка показаны отдельно. Пустая печать:
«Ожидание задания на печать / По поступлению». GET ничего не планирует и не меняет.
Успешные задачи выводятся только по достоверным отметкам; нет отметки — «Нет данных».
Журнал ограничен последними 40 событиями, без загрузки всей истории и сырых ошибок.

Красный `!` виден всем сотрудникам, включая мобильную шапку, и ведёт на мониторинг.
Потеря сети делает состояние неизвестным и приостанавливает звук. Возвращение во
вкладку актуализирует данные; запросы и таймеры не накапливаются.
Новый канал `workers` использует прежнюю общую кнопку звука. Отдельное пространство
IndexedDB `gamebat-worker-alerts-<user>` и атомарная аренда согласуют вкладки: один
сигнал за десятиминутный цикл инцидента. Перезагрузка не озвучивает цикл повторно;
новая авария получает новый ID. Пространства Avito/Яндекса и их permissions сохранены.
Блокировку autoplay видно по общей кнопке; она позволяет повторно включить звук.
При закрытом браузере звук невозможен, но контроллер продолжает работу.

## Диагностика и границы

Полностью завершившийся supervisor **не может восстановить себя сам** без внешнего
диспетчера. Устаревший heartbeat даёт «Контроллер недоступен», а не общий зелёный
статус. Повторно открыть штатный ярлык CRM. Сайт и worker — разные процессы.

При сбое печати проверить ярлык, бумагу, очередь Windows и состояние заказа.
Мониторинг не меняет `MarketPrintJob`, не повторяет `uncertain`, сохраняет защиту
`printing/spooled` и не отправляет готовность по факту перезапуска. Физический
результат подтверждает прежний механизм.

`worker_models`, `worker_monitoring`, `worker_policy`, `worker_heartbeat`,
`worker_schedule`, `worker_views` разделяют данные, контроль, политику, активность,
очереди и HTTP. Windows изолирован в `worker_processes` и общем PowerShell-модуле.
Будущий хостинг потребует другого адаптера и агента магазина; сейчас они не создаются.
Журналы и техническая история автоматически не очищаются.
