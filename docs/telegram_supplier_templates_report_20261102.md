## Пользовательский сценарий

В прежнюю постоянную клавиатуру добавлена «Скачать шаблоны поставщиков с ценами».
Оптовый прайс наличия остаётся первой независимой функцией. Кнопки показываются
по правам; при отсутствии доступных функций пустая клавиатура не отправляется,
выводится сообщение с просьбой обратиться к администратору.

После новой кнопки отображается список `Supplier`, отсортированный по `letter`
и ID, с кнопкой «Назад». Полное название разрешено только при
`partners.view_supplier_details`; иначе используется `safe_label`. Никаких
жёстко заданных A/F/M или отдельных Telegram-справочников нет. Удалённый поставщик
не может быть использован по старой кнопке.

При выборе поставщика создаётся долговечное задание `supplier_price_templates`
без склада и две записи документов. После подготовки обоих XLSX они отправляются
по очереди — диски, техника. Имена совпадают с веб-экспортом:
`resource-supplier-A-cd-template.xlsx`, `resource-supplier-A-tech-template.xlsx`.
Новая команда сотрудника позже формирует свежий комплект.

## Права и границы данных

Общий допуск требует активного пользователя, включённого бота, явного разрешения,
действующей привязки и `telegram_bots.use_staff_bot`. Оптовое разрешение перенесено
из общего допуска на границу отдельной функции. Поэтому старые пользователи
сохраняют оптовый прайс, а сотруднику можно выдать только шаблоны.

Для новой функции одновременно нужны `price.download_supplier_template` и
`price.view_supplier_prices`. Права автоматически не выдаются. Они проверяются
перед списком поставщиков, после выбора, перед генерацией каждого файла и перед
каждой отправкой. Перед внешним вызовом также обновляются привязка, состояние
пользователя/бота, наличие поставщика и аренда исполнителя. Входящие данные
ограничены личным Telegram-чатом; callback ID валидируется до ORM-запроса.

Обе функции используют прежние квитанции update/offset, cooldown и единственный
активный слот сотрудника. Конкурентные разные функции не создают два задания.
Генерация остаётся в прежнем исполнителе документов, отдельно от polling.
Второй бот/worker не создавался; другие четыре сервиса не изменялись.

## Excel и совместимость

`telegram_bots.documents.supplier_documents` напрямую вызывает прежний
`price.excel.generate_supplier_template` с действительным actor, выбранным
supplier_id и product_kind `cd`/`tech`. HTTP-вызов веб-представления не используется.
Генератор и импорт `price/excel.py` не изменялись.

Используются актуальные сохранённые AED из SupplierCDPrice/SupplierTechPrice,
без валютного пересчёта, наценки или цены другого поставщика. Новые разрешённые
товары остаются с пустыми ценовыми ячейками; отсутствие цен не отменяет файл.
Группировка, оформление, скрытые идентификаторы/метаданные и импорт сохранены.
Файл не содержит добавленных Telegram-колонок или ID сотрудника. Каждый файл
проверяется по существующему лимиту 45 MiB; подготовка всего комплекта завершается
до первого sendDocument. Файлы находятся только в памяти.

## Подтверждения, сбои и перезапуск

StaffBotJob получает тип функции с совместимым default `wholesale_stock_price`,
необязательного поставщика и общий итог `partial`. Новая StaffBotJobDocument
хранит тип файла, состояние, отдельный подтверждённый message_id и времена.
Уникальность пары job/type и согласованность типа/назначения защищены БД.
Исторические оптовые задания не требуют новых записей документов.

Намерение каждого sendDocument сохраняется до HTTP. Сам HTTP не находится внутри
транзакции. Подтверждения БД используют существующий retry_database_lock; это
повторяет только сохранение, а не внешнюю отправку.

- Два подтверждения: общий итог `done`.
- Диски подтверждены, техника отклонена или не отправлена: `partial`.
- Таймаут или отказ записи подтверждения после HTTP: документ `uncertain` и
  общий итог `uncertain`; уже подтверждённый первый файл сохраняет свой ID.
- Отказ первого файла останавливает второй, общий итог `error`.
- Ошибка генерации/лимита до HTTP: документы не отправляются.

После аварии `sending` документа становится `uncertain`. Подтверждённые документы
не затираются; неподтверждённый остаток не отправляется автоматически. Если оба
подтверждения уже сохранились, общий успешный итог можно восстановить без сети.
Уведомление о восстановленном частичном/неизвестном результате выполняется только
после проверки личности бота и отсутствия webhook. При недоступной сети уведомление
тоже может не дойти; результаты видны в CRM.

Новый явный запрос после cooldown разрешён, включая после ошибки. Он формирует
оба файла заново и может намеренно повторить ранее полученный файл. Автоматического
повтора или продолжения комплекта нет. Начатый HTTP-запрос невозможно отозвать
задним числом при одновременном отзыве прав.

Административный журнал показывает сотрудника, тип операции, склад/поставщика,
время, два результата с message_id и общий итог. Частичная отправка учитывается
штатным мониторингом как требующая внимания. XLSX и секреты не журналируются.
