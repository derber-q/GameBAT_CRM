# Сборка заказов Яндекса сканером

## Требования

На странице незавершённых продаж сканер ищет товар по всему `BarcodeRegistry`, сохраняя ведущие нули. Выбирается самый старый заказ Маркета в `PROCESSING / STARTED`, которому ещё нужна эта позиция. Каждый скан учитывает одну штуку. Печать и готовность запускаются после сканирования всего состава заказа. Эти правила и создание одной коробки при отсутствии ранее заданных коробок подтверждены пользователем 20.10.2026.

Официальный PDF `A9_HORIZONTALLY` печатается на подключённом к компьютеру CRM Xprinter XP-365B, бумага 58×40 мм. Браузерное окно печати не используется. После отправки в очередь Windows обработчик ждёт `JOB_STATUS_PRINTED` либо подтверждение всех напечатанных страниц сохранённого задания (`RETAINED`, `PagesPrinted >= TotalPages > 0`). Один `JOB_STATUS_COMPLETE` не подходит: это только отправка устройству. Только после подтверждения сохраняется `printed_at` и запрашивается готовность. Ручная кнопка готовности в продаже также требует `printed_at`.

Источник подтверждения — драйвер Windows. У мониторов без TrueEndOfJob статус может отражать отправку устройству раньше фактического выхода бумаги; универсальный API Windows не гарантирует аппаратную обратную связь. При неизвестном результате, ошибке, исчезнувшем задании или таймауте три минуты готовность не отправляется и печать автоматически не дублируется. [Семантика состояний и счётчиков Windows](https://learn.microsoft.com/en-us/windows/win32/printdocs/job-info-2), [сохранение задания до проверки](https://learn.microsoft.com/en-us/windows/win32/printdocs/setjob).

## Модули и порядок

| Модуль | Ответственность | Зависимости |
| --- | --- | --- |
| `native-label-print` | Проверка PDF и размера, GDI-печать через Windows с размером бумаги на одно задание | PyMuPDF, Pillow, pywin32 |
| `market-picking` | Поиск старейшего подходящего заказа, счётчики состава, идемпотентность сканов | BarcodeRegistry, OrderLine, Sale |
| `market-print-workflow` | Обновление заказа, коробки, PDF, печать, готовность; состояния и аудит | Первые два модуля, существующая очередь Маркета |
| `market-scan-ui` | Глобальный обработчик сканера, последовательная отправка сканов и наблюдение за заданиями | Все предыдущие |

Порядок: native-label-print → market-picking → market-print-workflow → market-scan-ui. Существующая ручная кнопка стикера использует ту же тихую печать, без автоматической готовности.

## Данные и интерфейсы

`MarketPicking` хранит снимок состава и количества сканов. `MarketScanEvent` с уникальным UUID запроса сохраняет результат конкретного скана: повтор HTTP не увеличивает количество и не выбирает следующий заказ. `MarketPrintJob` хранит этап обработки, PDF, ссылки на задания Маркета, отдельно `spooled_at`/`printed_at`, номер задания Windows и признак отправки готовности. Для одного заказа допустим один автоматический сценарий сборки; ручная перепечатка создаётся отдельным явным запросом. Автоматический сценарий получает свежий PDF после обновления заказа и подготовки коробок.

POST сканирования требует `sales.view_sales`, `yandex_market.manage_orders`, `yandex_market.print_labels` и CSRF. Штрихкод и UUID проверяются сервером. Состав заказа должен совпадать с сохранённой продажей; изменение состава во время сборки останавливает процесс. Отменённые, завершённые, тестовые заказы, отключённые интеграции и недоступные статусы не обрабатываются.

Обработчик `run_label_print_worker` обслуживает только задания печати; операции API передаются существующей очереди Маркета. Настройки принтера читаются из игнорируемого локального файла `.label-printer.json`. Имя принтера, произвольные пути и команды не принимаются от браузера. Печать выполняется без shell и без удержания транзакции БД. При потере процесса на этапе печати состояние считается неопределённым и автоматически не повторяется.

Сканер подключается через `window.GameBAT.registerGlobalBarcodeHandler` только на странице незавершённых продаж, не мешает обычному вводу и не сканирует во время открытого диалога. Сканирование сериализуется в браузере; сервер дополнительно защищает счётчики и UUID. Ошибки и прогресс показываются на текущей странице без подтверждений и навигации.

## Проверки и запуск

- Тесты: `.venv\Scripts\python.exe manage.py test sales.test_market_scanning sales.test_label_printing sales.test_market_controls yandex_market.tests --noinput`.
- JavaScript: `outputs\node\node.exe sales/test_market_scan_js.cjs`, затем все `test_*.cjs`.
- Браузер: изолированная тестовая БД, настоящий обработчик сканера, подменённые API/Windows-печать; проверяются несколько товаров, количества, несколько заказов, отсутствие диалогов и навигации.
- Общие проверки: полный Django suite, `check`, проверка миграций, `verify_inventory` при изменении учётной логики.
- Worker: `.venv\Scripts\python.exe manage.py run_label_print_worker` (скрыто штатным стартовым скриптом).
- Рабочую БД и физическую печать проверять отдельно. Тесты не печатают реальные ярлыки и не меняют статусы в Маркете.

## Границы

Существующие складские остатки, деньги, снимки продаж и статусы оплаты не меняются новой логикой сканирования. Фактическое изменение статуса Маркета импортирует существующий сервис. Нельзя автоматически дублировать печать после неизвестного результата, печатать до завершения всего состава или отправлять готовность при ошибке печати.
