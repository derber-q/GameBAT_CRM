# ReSOURCE Local Agent: установка, резервирование и восстановление

Функция от 03.11.2026. [Контракт и решения](local_agent_design.md),
[проверки и фактическое состояние внедрения](local_agent_report_20261103.md),
[инструкция Windows-комплекта](../local_agent/README.md).

## Что входит

Local Agent — самостоятельное Tkinter/ttk-приложение Windows 10/11 x64 с четырьмя
вкладками, значком в области уведомлений и отдельными потоками печати и загрузки.
GUI не поднимает HTTP-сервер и не запускает Django-сайт. Библиотека Django нужна
только сохранённому PDF-драйверу Print Agent; ORM рабочей CRM клиент не открывает.
Tk входит в Python и не требует Chromium/Qt. Основной размер комплекта создают
прежний PDF-рендерер и Python; фактическая проверенная ZIP-сборка около 57 МиБ.
Это переносимая сборка с EXE и `_internal`, не подписанный установщик.

Серверное приложение `crm_backups` хранит конфигурацию, задания, одноразовые
подключения, единственное активное резервное устройство, аудит, явное назначение
принтера и реестр опубликованных программ. Продажи, склад и касса не переписаны.
Старые Print Agent, печать Яндекса и Avito остаются основой исполнения.

## Страницы и права

| Страница | URL | Доступ |
| --- | --- | --- |
| Резервное копирование | `/crm/backups/` | Только активный superuser |
| Локальные приложения | `/crm/backups/devices/` | Только активный superuser |
| Приложения и расширения | `/crm/backups/apps/` | `crm_backups.download_client_apps` |
| Скачать опубликованную программу | `/crm/backups/apps/download/<UUID>/` | То же право |

Пункты находятся в меню «Интеграции». Обычным сотрудникам не выдаются полные
архивы, коды регистрации и токены. Права каталога приложений автоматически не
раздаются. GET административных страниц не регистрирует устройство и не запускает
снимок. Все административные изменения требуют POST/CSRF. Коды подключения
показываются один раз в ответе без кэширования, живут 10 минут и не находятся в URL.

## Windows: первый запуск

1. Откройте каталог приложений в CRM, скачайте Windows ZIP, сверьте SHA-256.
2. Распакуйте весь ZIP в постоянную папку и откройте EXE. Python устанавливать не надо.
3. В настройках укажите origin CRM: `http://127.0.0.1:8000` для этого компьютера;
   удалённый адрес требует HTTPS с действующим сертификатом.
4. Вкладка «Печать»: выберите принтер Windows и проверьте подключение без печати.
5. Создайте публичный `registration.json`; администратор вставляет его в страницу
   локальных приложений. Серверу передаётся только хеш, а не секрет.
6. Включите обработчик. По умолчанию новый профиль и обе функции выключены.

Настройки и журналы находятся в `%LOCALAPPDATA%\ReSOURCE\LocalAgent\profiles\<профиль>`.
У каждого профиля свои UUID, токены, SQLite-журнал и блокировки. DPAPI CurrentUser
защищает токены; ACL каталога ограничивает доступ владельцем Windows и SYSTEM.
Никаких секретов в EXE/ZIP нет. Закрытие окна оставляет приложение в области
уведомлений. «Завершить» останавливает задачи после текущего безопасного шага;
прерванная загрузка остаётся `.partial`. Автозапуск HKCU устанавливается только
после отдельного подтверждения пользователя, без службы/повышения привилегий.

### Прежний агент и дополнительные принтеры

Действующий Xprinter не переключается при установке. Для явного перехода штатно
остановите старый агент, выберите его config.json в GUI и включите обработчик.
Используются прежние `agent.lock`/`journal.sqlite3`; файл не переносится и не
перезаписывается. Прежний журнал нельзя удалять — он защищает от повторного StartDoc.

Кнопка создания нового профиля открывает независимый экземпляр. Зарегистрируйте
его отдельно, выберите другой принтер. Общая блокировка принтера защищает от двух
одновременно обслуживающих его профилей. Учитывается и уже работающий старый
default Print Agent, ещё не использующий новую общую блокировку.
Неизвестные старые нестандартные конфигурации CLI сначала остановите штатно:
они не обнаруживаются сканированием произвольных каталогов компьютера.

Если включён ровно один агент, сохранён прежний автоматический выбор. Если их
несколько, администратор явно выбирает устройство для **новых** заданий.
Сохранённое назначение не меняется после ошибки или смены default. Отключённая
выбранная цель вызывает отказ, а не отправку на случайный доступный принтер.
`GAMEBAT_PRINT_AGENT_ID` остаётся прежним fallback; явная настройка страницы имеет
приоритет. Backend native/agent автоматически не переключается.

Порядок печати сохраняется: проверенный PDF → запись намерения → Windows →
подтверждение драйвера → готовность Яндекса. Spooler не равен физическому выходу
бумаги. `uncertain` не перепечатывается автоматически; результат проверяет сотрудник.
Чужой агент не получает ни задание, ни PDF. Печать не использует резервный токен.

## Ключ восстановления и подключение получателя

Во вкладке настроек владелец создаёт ключ восстановления X25519. Приватный PKCS8
зашифрован паролем (минимум 12 байт); сохраняется в выбранный новый `.recovery.pem`.
Публичный `.public.pem` передайте в форму резервирования CRM. Приватный файл и
пароль серверу не передаются. Сделайте отдельную копию ключа вне компьютера
магазина. Потеря единственного приватного ключа/пароля необратима. При ротации
сохраните прежние приватные ключи; старые архивы имеют прежний key_id.

После сохранения ключа и явного подтверждения его отдельного хранения настройте
расписание и включите резервирование. Время по умолчанию — 03:00 Europe/Moscow;
часовой пояс задаётся явно. Разрешено создавать серверный снимок без включённого
Windows-компьютера. Догоняющий снимок имеет реальное время, а пропущенные дни
не выдаются за успешные копии прошлого состояния.

На странице устройств создайте одноразовый код, введите его в GUI «Подключить
резервное устройство». Программа создаёт собственный случайный секрет и UUID;
сервер хранит SHA-256. Уникальный активный слот БД и сериализация операций не дают
зарегистрировать двух получателей даже при конкурентных запросах. Смена получателя
требует явного административного подтверждения; прежний ключ отзывается в той же
транзакции подключения нового. Код нельзя использовать повторно. Отзыв резервного
устройства не отключает печать. Два профиля с украденной копией одного credential
не допускаются одновременно через lease сессии; credential всё равно следует отозвать.

Токен печати, токен резервирования и приватный ключ восстановления — три разных
секрета. Последний нужен только владельцу для расшифровки. Авторизация не строится
по IP/MAC, имени компьютера или Windows-пользователя.

## Снимок, шифрование и передача

Рабочая SQLite копируется только через Online Backup API. На короткое окно
BEGIN IMMEDIATE блокирует запись всех SQLite-процессов; middleware просит
повторить обычное изменение через несколько секунд. Машинное API печати не
перенаправляется; при активной печати снимок отклоняется до копирования файлов.
Предел окна — 15 секунд; фактическая длительность записывается в manifest.
Тяжёлые файлы заранее копируются в приватный staging при доступной торговле,
проверяются SHA-256 и версии источника (device/inode, размер, mtime_ns/ctime_ns).
В окне сверяются состав и версии источников перед/после снимка БД и ключи;
любая смена прекращает копию. После освобождения БД проверяются все FileField-ссылки,
соответствие ключей зашифрованным полям, хеши опубликованных программ и integrity/FK.
Отсутствующий файл, меняющийся ключ или превышение окна дают ошибку,
а не «полную копию». Файлы не удаляются для исправления проверки.

Внутри зашифрованного контейнера:

- `database.sqlite3` — самостоятельный согласованный снимок;
- `protected_media/` — защищённые документы, фотографии и PDF;
- `client_applications/` — опубликованные установочные комплекты, включая старые версии;
- `recovery/secrets.json` — действующие ключи Django/интеграций/витрины и необходимые
  конфигурационные файлы Яндекса, Google, Telegram, принтера в base64;
- `manifest.json` — хеши/размеры, формат, момент снимка, миграции, engine,
  окружение, версия/HEAD и честный признак незакоммиченного кода.

Git, исходники целиком, venv, журналы и прежние backups не копируются рекурсивно.
Проверяется наличие и хеш каждого опубликованного файла каталога. Один HEAD не
восстанавливает незакоммиченный код: сохраните совместимую версию отдельно через
обычный управляемый Git-процесс. Функция сама не коммитит исходники.

Формат v1 использует стандартные X25519/HKDF-SHA256/AES-256-GCM из cryptography.
У каждого архива свежие ephemeral key и nonce, весь заголовок защищён AAD, тег 128 бит.
Расшифрованные байты не выдаются до проверки полного тега. Это собственный формат
контейнера над стандартными примитивами, не совместимый с ZIP-паролем/7z/age.
Перед расшифровкой проверяйте SHA-256 по доверенному журналу устройства/CRM;
публичный ключ сам по себе не является подписью происхождения архива.

Долгие упаковка/шифрование и скачивание происходят после снятия блокировки БД.
Чтение/запись ограничены блоками 1 MiB. Сервер ограничивает временное хранилище
20 ГиБ, одну тяжёлую операцию и число ожидающих архивов (по умолчанию два).
Доставленные копии удаляются с сервера только после срока хранения и проверки
принадлежности/хеша. Недоставленные не удаляются автоматически ради освобождения
места; при заполнении показывается отказ. Неизвестные файлы не очищаются.

Клиент продолжает ровно тот же UUID через Range + If-Match/ETag. При изменении
размера/хеша продолжение запрещено. Сначала `.partial`, затем SHA-256/размер,
атомарное переименование, запись в журнал и подтверждение CRM. Отзыв проверяется
на каждом блоке длинной передачи. «Сохранено» на сервере означает подтверждение
устройства, а не только готовность архива. SHA-256 не заменяет тест восстановления.

## Локальная история и очистка

По умолчанию `%USERPROFILE%\ReSOURCE\Backups`, очистка выключена. После включения
сохраняются семь последних ежедневных копий; срок и дополнительные недели
настраиваются. Закрепление хранится в SQLite. Последний исправный архив,
закреплённые, чужие файлы, ссылки, активные и чужие partial не удаляются.
Ошибка новой загрузки запрещает автоматическое сокращение исправной истории.
Ручное удаление требует подтверждения и тоже не удаляет последний исправный.

При обрыве просто восстановите связь/запустите приложение. Если отозван токен,
нужен новый одноразовый код администратора. При нехватке места смените каталог
или вручную перенесите подтверждённые копии, не трогая незнакомые файлы.
Папка Git/установки/ссылки не подходит. Копия на том же физическом диске
**не защищает от полного отказа этого диска**. Выключенный компьютер ничего не скачивает.

## Проверка восстановления владельцем

Не восстанавливайте поверх рабочей БД и не запускайте вторую рабочую CRM.
В новом отдельном каталоге выполните:

```powershell
.venv\Scripts\python.exe manage.py restore_crm_backup C:\SAFE\copy.backup C:\SAFE\restore-new --private-key C:\OFFLINE\owner.recovery.pem
.venv\Scripts\python.exe scripts/verify_restored_backup.py C:\SAFE\restore-new
```

Пароль запрашивается скрыто; не передавайте его аргументом командной строки.
Распаковка отказывается перезаписывать любой существующий каталог, проверяет GCM,
пути, manifest, хеши, размеры, ключи и SQLite. Вторая команда использует искусственные
настройки запуска, восстановленную БД в read-only/immutable и отключённую сеть.
Проверяет `verify_inventory`, `verify_cash` и совместимость миграций; сайт/worker
не стартуют. Это offline-проверка, а не подмена строгого окружения `local_test`.
Каталог с распакованными секретами приватный; храните его под правами владельца.

Для реального восстановления разверните совместимую версию кода в отдельной
остановленной установке. После проверки перенесите database/protected_media и
client_applications в постоянные хранилища. Из `recovery/secrets.json` восстановите
эффективные `SECRET_KEY`, `INTEGRATION_ENCRYPTION_KEY`, `RESOURCE_TOKEN_ENCRYPTION_KEY`
как защищённые env/файлы. `files_base64` содержит зашифрованный yandex-market-key,
google-service-account.json, telegram-staff-bot-token и label-printer.json; декодируйте
их в отдельное защищённое хранилище и настройте пути. Не печатайте содержимое.
Сопоставление имён важно: сохранённый `SECRET_KEY` передаётся как
`DJANGO_SECRET_KEY`, `TELEGRAM_STAFF_BOT_TOKEN` — как
`GAMEBAT_TELEGRAM_STAFF_BOT_TOKEN`; для Google задаётся путь
`GOOGLE_SERVICE_ACCOUNT_FILE` к восстановленному JSON. Если Telegram-токен
восстановлен из `files_base64`, задайте `TELEGRAM_STAFF_TOKEN_FILE` в защищённой
конфигурации Django либо верните прежний `.telegram-staff-bot-token`.
Не меняйте ключ шифрования старых данных новым случайным. Внешний Avito/Маркет
и Windows-журнал печати не откатываются вместе с CRM — сначала сверка внешних состояний.

## Запуск сервера, сборка и публикация

Четыре миграции `crm_backups.0001`–`0004` добавляют только технические таблицы.
На рабочую SQLite их применяют по согласованному плану с новой проверенной копией,
сохраняя `backups/current_state_20261031.sqlite3`. Прежние бизнес-таблицы не меняются.
Резервирование выключено по умолчанию, права сотрудникам не выдаются.

В рабочем Docker существующий container_runtime запускает отдельный
`run_backup_worker` рядом с web и прежним supervisor. Второй supervisor не создаётся.
Блокировка исполнителя привязана к пути SQLite, а не папке архивов. В нативной
установке отдельно запускают `python manage.py run_backup_worker`; повторный
экземпляр не допускается. Контейнерный runtime управляет завершением всей своей
группы, старые пять сервисов продолжают использовать прежний мониторинг.

Постоянные серверные пути задаются `GAMEBAT_BACKUP_ROOT` и `GAMEBAT_APP_ARTIFACT_ROOT`.
Локальные defaults — `.local-backup-cache` и `.local-app-artifacts` в рабочем bind mount;
при будущем production они должны указывать на shared-хранилища вне release-каталога.
При local_live в Docker на Windows задайте приватные ACL папки серверных снимков
на хосте до первого включения: Linux chmod на bind mount не заменяет Windows ACL.
В текущем внедрении это делает `local_agent.configuration.private_folder` на хосте.
`local_test` имеет отдельные fixture-пути и не принимает рабочие устройства/API/ключи.
Production-gate проекта сохранён. PostgreSQL pg_dump-адаптер подготовлен, но полное
PostgreSQL-резервирование **не включено и не считается испытанным**.

Сборка Windows выполняется на Windows из allowlist без стандартного Django hook,
который способен подхватить db.* проекта. Зависимости GUI/сборки описаны в
`local_agent/requirements*.txt`. Команды:

```powershell
python scripts/build_local_agent.py outputs/НОВЫЙ_КАТАЛОГ
python scripts/package_avito_extension.py outputs/НОВЫЙ_ФАЙЛ.zip
python manage.py publish_client_app local_agent outputs/КОМПЛЕКТ.zip --actor-id ID_СУПЕРПОЛЬЗОВАТЕЛЯ
python manage.py publish_client_app opera outputs/РАСШИРЕНИЕ.zip --actor-id ID_СУПЕРПОЛЬЗОВАТЕЛЯ
```

Сборщик проверяет отдельную копию EXE вне репозитория с PATH без Python, DPAPI,
Tk и импортом PDF-драйвера, без печати/сети. В ZIP манифест состава и SHA-256.
Расширение берётся из актуального manifest; его ID, origin/permissions и функции
не изменяются. ZIP распаковывается и проверяется отдельно. Публикация — явное
действие администратора после проверки, а не сборка при открытии страницы.
Прежние опубликованные версии сохраняются. Если файла нет или хеш неверен,
скачивание отклоняется. Отсутствующая сборка показывается без активной кнопки.
