# Интеграции, запуск и эксплуатация

Актуализировано 31.10.2026 по текущим исходникам. Навигатор: [техническая документация](README.md).

## 1. ОБЩИЙ ПРИНЦИП
Сайт сохраняет локальные изменения, отдельные worker исполняют внешние задания. Очередь, журнал API, текущее состояние и фактическое удалённое состояние различаются. Отсутствие ошибки формы не означает, что объявление изменилось. Перед диагностикой выяснить: включён ли сервис в настройках, запущен ли нужный worker этого проекта, есть ли задание, когда run_after, какая фаза/ошибка, получено ли подтверждение внешнего значения.
Этот документ не подтверждает, что интеграции сейчас включены. Рабочие токены и процессы намеренно не опрашивались при подготовке источников.

## 2. AVITO
IntegrationCredential хранит реквизиты. AvitoProductProfile описывает локальный профиль товара, AvitoRemoteListing — полученное объявление, AvitoListingConnection — связь. Фотографии, синхронизационные задания и логи — отдельные модели. Перепривязка объявления и удаление товара — разные операции.
Изменение цены/физического остатка через штатные сервисы вызывает назначение сверки после commit. Очередь объединяет повторяющиеся изменения и выполняет повторные попытки с учётом фаз. Подтверждённое чтение после отправки важнее одного успешного HTTP-ответа записи. Ошибка отдельного объявления не должна выдаваться как успех всей партии.
Необходимые действия показывают, где по данным CRM/удалённого снимка нужно опубликовать или снять объявление. Основной рабочий список рассчитан на ручное действие пользователя в Avito и последующее обновление статусов. При этом другие настроенные механизмы синхронизации могут менять внешние цены/остатки: нельзя заявлять, что любые вызовы CRM к Avito всегда read-only.
Периодическая проверка необходимых действий выполняется примерно раз в 15 минут. Интерфейсный счётчик и уведомления используют локальный результат. Звук должен сигнализировать о новых действиях, а не о любом повторном ответе с count>0. Устаревший снимок не позволяет гарантировать текущую публикацию.

## 3. AVITO CHECK / REEFAPI
Ручной поиск открывает Avito с запросом товара; он не расходует кредиты ReefAPI. Основная таблица pricing/avito_check_catalog.py выбирает CD и Tech с реальной AvitoListingConnection и положительной суммой физических складских остатков. Две независимые AvitoManualPrice(scope=russia|rostov) хранят собственные сумму, дату и автора; уникальна пара (profile, scope). Миграция integrations.0011 сохраняет прежние строки как russia, Ростов не заполняет. Предупреждение РФ > Ростов не блокирует запись. Сортировка по дате использует РФ. Дополнительная справочная себестоимость — base_price_rub + delivery_rub последнего обычного ProcurementPriceList(is_trip_addition=False), без старых версий при отсутствии позиции. Текущий cost остаётся отдельно. Автоматический integrations/avito_check.py сохраняет собственную очередь/правила, включая исключение архивных товаров. Подробнее: [Avito Check](../avito_check.md).
Автоматическая проверка через ReefAPI использует ключ, бюджет, дневное кеширование и режимы проверки. Платный запрос — внешний эффект; тестировать только заглушками. Найденное предложение/рекомендация не должны сами менять цену продажи в обход подтверждённого сохранения.
При подтверждении цен прихода ручной поиск нужен и для непривязанного товара. Отсутствие в основной таблице Avito Check не должно блокировать эту локальную помощь.

## 4. РАСШИРЕНИЕ OPERA/CHROMIUM
browser_extensions/avito_check — Manifest V3, версия manifest 1.7.0. background.js координирует вкладки и сообщения, crm.js получает разрешённый CRM-контекст, protocol.js задаёт протокол, panel.js строит панель на Avito, cards.js/cards.css изменяют поведение цен/карточек. Это не серверная установка в Python. ZIP распространяется через «Интеграции → Приложения и расширения»; после скачивания нужны перезагрузка расширения и вкладок CRM.
Контекст и все команды содержат составной ключ kind/product_id/scope. Очередь: товар РФ → тот же Ростов → следующий РФ; начинается с нажатого этапа. Подстановка, expected_recorded_at и обновление DOM относятся строго к выбранному scope; конфликт HTTP 409 не продвигает очередь. Старое расширение без scope отклоняется явно. Поле предзаполняется собственным ручным минимумом; у непроверенного Ростова пусто. Клик по карточке выбирает цену до скидки и блокирует переход. Алгоритм cards.js не менялся при добавлении географий. География в URL: /all и /rostov-na-donu; строгость городского радиуса не подтверждена из-за HTTP 429 Avito, её нельзя выдавать за проверенную.
Исходная цена увеличена. Сравнение с полем панели использует яркий зелёный/красный/жёлтый фон для ниже/выше/равно. Скидочная цена подавляется; нельзя случайно скрыть исходную цену вместе с контейнером. DOM Avito сторонний и меняется, поэтому selectors/наблюдатели требуют регрессионных fixtures.
Кнопка сохранить и следующий сохраняет в CRM и открывает следующий поисковый контекст; пропуск не равен сохранению. Межсайтовые сообщения проверяют источник/разрешённые адреса; не расширять host_permissions до всех сайтов без необходимости. В manifest есть явный список CRM-хостов, новый LAN-адрес нужно согласованно добавить. Не помещать ключи внешних API в расширение.
После обновления распакованного расширения требуется его перезагрузка в браузере и обновление уже открытой страницы/новый ручной поиск из CRM. Работа на обычном Avito без CRM-контекста не обязана показывать панель задания.

## 5. GOOGLE SHEETS
GoogleSheetsIntegration и GoogleSheetsSyncJob — настройки и очередь. Синхронизация односторонняя: CRM публикует прайс/физическое наличие, Google-таблица не становится источником складских движений. Есть ручной запуск и периодический примерно раз в 10 минут. Повторные задания дедуплицируются, ошибки сохраняются для повтора.
Service account JSON — секрет. Права доступа к документу и рабочие диапазоны/настройки проверяются отдельно. Успешная проверка credentials не доказывает запись всех строк. Не импортировать отредактированные внешние остатки обратно в рабочую БД по собственной инициативе.

## 6. ЯНДЕКС МАРКЕТ FBS
Integration хранит настройки бизнес/кампания/склад и параметры работы. RemoteOffer и OfferConnection связывают offerId с реальным товаром CRM. Настройки FBS-цены, категории, медиа и content action имеют собственные проверки. Схему категории нельзя выдумывать из названия игры.
Импорт заказов ограничен заданным началом обработки и выполняется идемпотентно. Удалённый заказ сохраняется как OrderMetadata/OrderLine и связывается с внутренней продажей через доверенный путь. Обычная HTTP-форма не должна позволять подделывать yandex_market sale_type.
Если оффер неизвестен либо на нужном складе нет товара, требуется диагностируемая ошибка/исправление связи или перемещение. Нельзя создать выдуманное наличие, списать другой склад или объявить ошибку успешным импортом. Удалённые статусы хранятся отдельно от локального внимания сотрудника.
WebhookEvent, SyncJob, ApiLog, ApiBudget и AuditEvent позволяют отслеживать входящее событие, задания, лимиты и действия. Стабильный внешний webhook /integrations/yandex/notifications/ не менять без миграции настройки сервиса. Проверка подлинности и повторов должна сохраняться.
Возврат связан с ReturnMetadata и отдельным подтверждением приёма; отмена удалённого заказа, возврат товара и удаление локальной продажи не взаимозаменяемы.

## 7. УВЕДОМЛЕНИЯ ЯНДЕКСА
После реального импорта продажи создаётся MarketOrderAttention. Бейдж/всплывающее сообщение и звук берутся из локального состояния. Опрос примерно каждые 15 секунд, повтор звука по неподтверждённому заказу примерно через 10 минут. Браузер может блокировать звук до пользовательского действия. Ошибка сети не должна выдавать старое состояние как новое событие.
Подтверждение сотрудником означает «уведомление принято», а не «товар собран/напечатан/отгружен». Если worker не работает, открытая страница сама не гарантирует поступление удалённого заказа. Для искусственных проверок использовать тестовую БД и подменённый API, а не настоящую продажу.

## 8. ЯРЛЫКИ И ТИХАЯ ПЕЧАТЬ
LabelDocument хранит запись официального PDF. Кэширование назначается после импорта заказа; подпись кэша учитывает состав/коробки/доставку. Подходящий файл переиспользуется, устаревший нельзя считать актуальным только по order_id. Терминальное завершение/отмена очищает файл по правилам кэша; активная печать откладывает очистку. Исторические записи без подтверждённой подписи не удаляются произвольным массовым скриптом.
Формат принтера 58×40 мм, официальный тип A9_HORIZONTALLY. Браузерное window.print открывает диалог и не гарантирует фактическую печать. Для автоматического сценария используется отдельный Windows run_label_print_worker и настроенный локальный принтер. pywin32/PDF-обработка принадлежат машине печати.
Сканирование в незавершённых продажах: товар → самый старый подходящий заказ → учёт всех штук/строк → одна коробка по умолчанию → MarketPrintJob → worker → подтверждение печати → готовность к отгрузке. Неполный состав не должен ставить ready. Нажатие ручной кнопки ready также не отменяет требование печати.
MarketPicking/MarketScanEvent отслеживают сборку; MarketPrintJob — попытку печати и её состояние. Повтор HTTP/скана не должен печатать вторую копию без нового разрешённого действия. Неопределённый результат принтера нельзя автоматически повторять как точно не напечатанный: возможна уже вышедшая этикетка. Подтверждение ОС/очереди не является датчиком наклеивания ярлыка, окончания бумаги и физической передачи перевозчику; эту аппаратную границу нужно учитывать в интерфейсе.

## 9. ПРОЦЕССЫ И ЗАПУСК
Обычный start_localhost.ps1 проверяет сайт и запускает отдельные worker avito/yandex/google, а также печать согласно текущему скрипту. Фоновые окна скрыты, журналы идут в outputs/localhost. Параметр -SiteOnly специально запускает только сайт. Не путать его с полной интеграционной конфигурацией.
Management command run_integration_worker поддерживает --service all|avito|google|yandex, --once и период опроса --poll (по умолчанию 2 секунды). --once не делает вызов безопасным: он может реально изменить внешний сервис. run_label_print_worker — отдельная команда.
Перед остановкой проверить команду, cwd/путь и PID конкретного процесса. Нельзя завершать все python.exe. --noreload требует перезапуска после Python/кешированных шаблонов; worker тоже должен загрузить обновлённый код. Не плодить одинаковые worker без проверки механизма захвата задания.
Для телефона нужен адрес машины в LAN, DJANGO_ALLOWED_HOSTS с конкретным адресом и доступность порта. runserver — локальный сервер разработки, не готовый публичный HTTPS-деплой. Название хоста и порт не гарантируют безопасность публикации в интернет.

## 10. БЕЗОПАСНАЯ ДИАГНОСТИКА
.venv/Scripts/python.exe manage.py check — системные проверки.
.venv/Scripts/python.exe manage.py makemigrations --check --dry-run — соответствие схемы моделям без создания миграций.
.venv/Scripts/python.exe manage.py verify_inventory — проверка реализации/неотрицательности, без исправления.
.venv/Scripts/python.exe manage.py verify_cash — сверка касса/сейф с журналом, без исправления.
.venv/Scripts/python.exe manage.py test --noinput — suite на отдельной тестовой базе.
test_*.cjs запускаются Node и проверяют JS с моделируемым DOM. Browser checks используют отдельные settings/БД: сначала читать их конфигурацию. Перечень файлов команд и проверок в reference/ui_and_migrations.md.
verify_avito_sync обращается к настоящему API даже без --fix; с --fix может менять объявления. Не использовать как нейтральный линтер. Не запускать синхронизацию ради документации/UI. При тестах API/принтер подменяются, рабочие ключи не используются.
Финал OK/FAILED и код процесса важнее промежуточных ошибок негативных тестов. Отсутствие полного запуска нельзя описывать как «все тесты прошли». Снимки старых отчётов ограничены датой подготовки.

## 11. РЕЗЕРВИРОВАНИЕ И ВОССТАНОВЛЕНИЕ
Рабочая db.sqlite3, backups, секреты и медиа не включаются в новый Git-коммит. Активную SQLite копировать через Backup API либо после остановки всех пишущих процессов; одного копирования основного файла при WAL недостаточно. Проверять integrity_check и foreign_key_check копии.
Отдельно сохранять ключ Django, ключ шифрования интеграций, env-настройки и protected_media. БД не содержит сами фотографии/подтверждающие файлы. В отчёте фиксировать commit и согласованную копию БД без раскрытия секретов.
Восстановление: сохранить текущее состояние; остановить проверенные пишущие процессы; восстановить совместимую пару код+БД в отдельном месте; вернуть секреты/медиа; проверить целостность/миграции/остатки/кассы; запустить сайт; только после проверки целевых значений включать внешние worker. Откат CRM не откатывает уже изменённые объявления Avito.
Коммит/push выполняются лишь по прямой просьбе в текущей задаче, без force push и разрушительного reset. Старое разовое разрешение не распространяется на новые изменения.

С 02.11.2026 `telegram_bots` использует прежние генераторы безымянного оптового Excel
и шаблонов поставщика с ценами, одноразовую привязку к `accounts.User` и отдельные
права каждой функции. Два файла шаблонов отправляются последовательно с отдельными
подтверждениями; частичный/неизвестный результат не вызывает автоматический повтор.
`telegram_staff` —
пятый процесс существующего supervisor. Работа в local_test запрещена; production
остаётся закрыт. [Полный контракт](../telegram_staff_bot.md),
