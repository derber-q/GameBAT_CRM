# Исходники, рабочие данные и единственная резервная копия

## Что хранится в Git

Исходники Django/JS/CSS/шаблонов, миграции, тесты, зависимости, управляемые статические ресурсы, правила работы и техническая документация. Миграции являются исходниками: они нужны для создания новой базы и чтения существующей схемы. Их нельзя удалять как «старые» или заменять текущей рабочей SQLite.

Не включаются `.venv`, `node_modules`, временные файлы, `outputs`, `output`, `tmp`, `reports`, `backups`, `protected_media`, журналы, SQLite/sidecar/копии, `.env*` и локальные ключи. Графические исходники, которые используются `resource_storefront.asset_pipeline`, не являются мусором только потому, что страницы отдают WebP.

## Рабочая база и активные файлы

`db.sqlite3` — текущая рабочая БД. `db.sqlite3-wal` и `db.sqlite3-shm` принадлежат активной SQLite; не удалять их как кеш работающего сайта. Обычное копирование одного `db.sqlite3` при WAL не гарантирует полный актуальный снимок.

31.10.2026 по поручению владельца создана одна согласованная копия:

`backups/current_state_20261031.sqlite3`

Рядом `current_state_20261031.json`: время, SHA-256, размеры, результаты целостности/foreign keys и контрольные количества строк таблиц. Эти данные остаются локально; в Git не добавляются. Старые копии удаляются только после проверки новой, без использования маски, способной затронуть защищённую копию или рабочий файл.

SQLite может создать рядом служебные `-wal`/`-shm` даже при диагностическом открытии копии. Это не дополнительные резервные базы. Для окончательной проверки неизменяемого согласованного снимка используется read-only URI с `immutable=1`, без записи в файл; для живой рабочей БД этот режим не применять. Служебные файлы защищённого снимка не удаляются общей очисткой.

Копия не является точкой, к которой нужно откатывать работу после каждого изменения кода. Она фиксирует состояние на момент создания; работающий сайт/worker могут продолжать добавлять актуальные операции. При будущих опасных изменениях создать и проверить новый согласованный снимок, затем отдельно заменить устаревший защищённый экземпляр.

## Что не содержится в SQLite

Ключи шифрования/подписи и сами файлы медиа не восстанавливаются из БД. Сохранять локальные `.django-secret-key`, `.integration-encryption-key`, `.resource-token-encryption-key`, `.yandex-market-key`, настройки принтера и `protected_media`. Их наличие в старой резервной папке не разрешает удалить действующий оригинал.

Для полного переноса нужна согласованная пара код+БД, ключи, настройки среды и защищённые файлы. Данная очистка не меняет пользовательские ключи и не публикует их значения. Откат локальной БД не откатывает реальные объявления Avito.

## Автоматическая защита Git

```powershell
.venv\Scripts\python.exe scripts/check_repository.py
git config --local core.hooksPath .githooks
```

На данном рабочем месте локальная настройка включена. При новом клонировании её нужно включить отдельно: локальный Git config не переносится с репозиторием.

Hook проверяет индекс, включая принудительный `git add -f`, запрещённые пути и сигнатуру SQLite независимо от расширения. Он не выводит содержимое файлов/значения ключей. Рабочий файл можно убрать только из индекса с `git rm --cached -- <путь>`, сохранив на диске. Изменённые, но ещё не добавленные в индекс файлы этим hook не анализируются как будущий коммит; перед добавлением всё равно требуется просмотр diff.

Проверка не является полноценным сканером всех возможных секретов. Новый нестандартно названный credential JSON или строка токена в Python требует внимательного review. Нельзя считать успешный hook разрешением коммитить произвольный файл с рабочего компьютера.

## Текущее дерево и история Git

На начале проверки рабочая БД уже не отслеживалась. В старых коммитах обнаружены пять blob-снимков с путём `db.sqlite3`. `.gitignore`, hook и обычный новый коммит не удаляют эти объекты из истории.

Эта задача прекращает будущее попадание локальных данных и очищает рабочую папку. Опубликованная история не переписывается, ветки/теги не удаляются и force push не выполняется. Полное удаление старой БД из истории — отдельная операция с координацией всех клонов и опубликованных refs; резервную SQLite она не заменяет.

## Временные результаты и инструменты

Логи текущих `outputs/localhost`/`outputs/integration_workers` могут быть открыты работающими процессами. Не останавливать все Python-процессы ради их удаления. Node/Playwright нужны только проверкам, не серверу CRM; инструменты должны оставаться локальными и исключёнными из Git. Отчёты сравнения инвойсов и подтверждение адресной коррекции являются результатами работы пользователя, а не кэшем Python.
