# Ручные обновления CRM

Контракт 01.11.2026: «Интеграции → Обновления», доступ только superuser.
В local_live и local_test кнопки показывают сообщение о доступности только для
production. Не выполняются запросы GitHub, загрузка кода или административная операция.
Локальная рабочая копия считается экспериментальной; её базовый Git SHA не означает,
что все незакоммиченные файлы опубликованы на GitHub.

В production проверка и установка запускаются отдельными нажатиями. Открытие страницы,
запуск сайта, idle-цикл менеджера и появление нового коммита ничего не устанавливают
и не проверяют в GitHub. Автоматического обновления по расписанию или webhook нет.
После проверки кнопка установки относится к показанному неизменяемому SHA main;
изменение main не заменяет уже одобренный SHA незаметно для администратора.

Менеджер работает отдельно от Django на Linux с rootless Docker. Веб-контейнер
не получает Docker socket, GitHub-токен, конфигурацию менеджера или команды shell.
Личная административная SQLite менеджера хранит заявки, результаты и аудит,
отдельно от бизнес-БД. Web получает только read-only JSON состояния и Unix socket
с проверкой host UID для фиксированных команд. Журнал переживает смену образа CRM. Одновременные операции и
повторная отправка UUID не создают вторую установку.

Источник фиксирован: derber-q/GameBAT_CRM. Менеджер принимает только образ по digest,
подтверждённый успешным статусом CI для конкретного SHA. Кандидат проверяется без
рабочих данных, ключей и сети. После остановки пишущих процессов создаются копии
PostgreSQL и shared-файлов; затем переключаются только web и supervisor. Успех
фиксируется после проверки версии, БД и обработчиков. Предыдущий образ сохраняется.

На этом шаге поддерживаются обновления с неизменённым набором миграций. Изменение
схемы блокируется до отдельного проверенного процесса миграций этапа B. Откат кода
разрешён только при совпадающей схеме и не восстанавливает старую БД. После сбоя
менеджера начатая установка не повторяется автоматически: требуется проверка состояния.
Непроверенный CI, неизвестная версия, отсутствие менеджера или несовместимая схема
не превращаются в «успешно». Production по-прежнему заблокирован до этапа B.

Проверки: сначала интерфейс и запреты локальных режимов, затем журнал и очередь,
поддельные GitHub/Docker и сбои установки, изолированные проверки в Linux и браузер.
Текущие тестовые контейнеры не запускаются и не изменяются. Испытание на выбранном
VPS требуется перед включением установки; сам этот документ его не подтверждает.

## Использование

Страница: `/crm/integrations/updates/`, меню «Интеграции → Обновления».
Оба пункта проверки и установки в локальных режимах показывают сообщение без сетевых
запросов и без создания заявки. Production показывает сохранённые сведения менеджера;
GET страницы не запускает GitHub, команды сервера или установку. Проверка новой версии
тоже требует отдельного POST от superuser. Последние сведения при ошибке сети остаются
с датой их получения, без объявления их актуальными.

Настройка сервера, права, rootless Docker, Unix socket, резервирование и восстановление
после прерывания: [инструкция менеджера](../deploy/updater/README.manager.md).
Готовый отдельный пакет создаётся
`python scripts/package_update_manager.py outputs/НОВЫЙ_КАТАЛОГ`.
Пакет не включает рабочую БД, ключи, медиа или настройки конкретного сервера.

В GitHub подготовлен файл workflow «Подготовка ручного production-релиза».
Он запускается только workflow_dispatch и не подключается к VPS. Проверяет
Windows/SQLite, Linux/SQLite, PostgreSQL, браузер, миграции и зависимости, после чего
может опубликовать образ GHCR и привязать digest к SHA статусом resource/deployment.
CI пока не запускался; production_gate намеренно блокирует допуск до проверенного
production/PostgreSQL этапа B. Наличие workflow не означает успешную проверку версии.

SHA образа и отпечаток файлов миграций/зависимостей проверяются перед установкой;
образ кандидата запускается без сети и данных CRM. Сохранённая предыдущая версия
не удаляется. Возврат кода после неудачного запуска относится к той же ручной
операции и не восстанавливает БД. Отдельной автоматической установки новых версий нет.

История, инициатор, время, этапы, ошибка и проверка резервной копии хранятся в личном
журнале менеджера. Web читает только JSON состояния и отправляет ограниченную команду
через Unix socket. Даты исходной установки не выдумываются: при первой регистрации
неизвестная дата остаётся неизвестной; известная дата фиксируется после успешного
ручного обновления. Перезапуск web не стирает очередь и историю.
