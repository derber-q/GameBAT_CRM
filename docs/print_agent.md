# ReSOURCE Print Agent

Контракт: раздел 8 исходного задания и прямое поручение о печати из контейнера и
после переноса CRM на сервер. Сохраняются MarketPrintJob, PDF Яндекса 58×40 мм,
права сотрудников и порядок PDF → подтверждённая печать → READY_TO_SHIP.

Агент на Windows-компьютере принтера устанавливает только исходящие соединения.
Для удалённого сервера обязателен HTTPS с проверкой сертификата/имени, без
перенаправлений; HTTP допускается только для loopback текущей локальной CRM.
Открывать входящий порт магазина и передавать агенту SQLite, Django SECRET_KEY
или ключи маркетплейсов не требуется. Токен агента отдельный, заменяемый; в БД
хранится его SHA-256, полный токен — только в защищённом локальном конфиге агента.

Windows local_live по умолчанию сохраняет native-печать. Backend agent включается
явно для рабочего контейнера. local_test не принимает настоящие команды агента
и не разрешает физическую печать. Тестовые контейнеры в этой задаче не меняются.

## Протокол и гарантии

Агент аутентифицируется Bearer-токеном и передаёт случайный UUID экземпляра процесса.
Сервер не выдаёт его задания второму активному экземпляру. Назначение задания
атомарно, каждый захват имеет UUID. API не исполняет произвольные команды и
не выдаёт чужие документы. Поля API ограничены, PDF проверяется по SHA-256,
размеру и геометрии, адрес скачивания строится из UUID внутри закреплённого origin.

Последовательность: agent_waiting → agent_claimed → agent_printing → agent_spooled
→ printed → существующее завершение/готовность. До обращения к Windows клиент
сохраняет маркер в собственном SQLite-журнале, сервер также сохраняет начало
печати до внешнего эффекта. Повторный HTTP не создаёт новую печать.
Потеря результата после начала означает uncertain: ни автоматического повтора,
ни READY_TO_SHIP. Исчезнувшее задание Windows и COMPLETE сами по себе не являются
подтверждением; сохраняются действующие проверки PRINTED/счётчиков драйвера.
Это подтверждение драйвера, а не отдельный физический датчик выхода бумаги.

Прерванный захват до начала печати можно выдать заново с новым UUID. Захват после
начала не передаётся другому агенту. Неопределённый результат требует проверки
сотрудником и явного решения в интерфейсе с правами печати и аудитом.
Новый запрос печати не обходит незавершённое/неопределённое задание заказа.

## Порядок реализации и приёмка

1. Добавочная схема и API: отдельная аутентификация, heartbeat, назначения и результаты.
2. Локальный журнал, защищённый транспорт и существующий Windows-драйвер агента.
3. Подключение к очереди и мониторингу, ручная проверка uncertain.
4. Проверки на искусственных PDF/подменённом принтере, резервная копия и миграция.
5. Регистрация и подключение агента на текущем компьютере; проверка связи без
   тестовой физической печати и без создания тестовых заказов маркетплейса.

Обязательны проверки повторов, двух агентов, потери связи до/после отправки,
отсутствия бумаги, неправильных PDF, подмены задания, прав/CSRF, native-режима и
блокировки local_test. Реальные API/печать не используются ради испытаний.
Проверка выбранного VPS остаётся отдельной: его адрес и инфраструктура ещё не заданы.

## Эксплуатация

Пошаговая установка отдельного комплекта, запуск, остановка, перенос на HTTPS-сервер,
ротация и отзыв токена описаны в [инструкции агента](../print_agent/README.md).
Комплект создаётся командой `python scripts/package_print_agent.py outputs/НОВЫЙ_КАТАЛОГ`.
В архив входят только исходники агента, минимальные зависимости и инструкция;
рабочие настройки, токен, журнал, БД CRM и медиа не включаются.

На текущем компьютере агент настроен для `Xprinter XP-365B` и адреса
`http://127.0.0.1:8000`. В compose только рабочего контейнера задан
`GAMEBAT_PRINT_BACKEND=agent`. Агент запускается отдельно через
`start_print_agent.ps1`; контроллер внутри контейнера автоматически запускает
координатор `run_label_print_worker`. Последний можно восстановить на странице
«Обработчики». Удалённый сайт не может запустить выключенный Windows-компьютер:
на нём должен работать агент. Автозапуск агента при входе в Windows не устанавливался.

## Отображение готовности после печати

Ответ опроса печати содержит текущие `market_status`, `market_substatus`,
`market_status_label` и `market_actions`. Подпись статуса общая для HTML и JSON
(`sales.market_controls.market_status_label`). После подтверждения READY_TO_SHIP
браузер скрывает кнопку готовности и показывает текстовый статус в той же строке;
обновляет также снимок статуса формы отмены. Другие заказы не изменяются.
Это одинаково работает при печати кнопкой и при сборке сканером. Повторная загрузка
списка или карточки показывает тот же статус из OrderMetadata.

Регрессия 01.11.2026 была только в отображении: прежний JS блокировал кнопку, но
оставлял её видимой без подписи статуса. Исправление не меняет БД заказа и не
повторяет печать/команду готовности. Браузерная проверка
`sales.market_scan_browser_checks` воспроизводит полный переход и проверяет
соседний заказ; `sales.test_market_controls` проверяет JSON и первичную отрисовку.
