# Яндекс Маркет FBS — реализация и запуск

Дата проверки API: 24.09.2026. Код работает в существующей CRM; формулы статистики, приходов, реализации и кассы не заменены.

## Состояние подключения

При первоначальной настройке в рабочей БД создано отключённое подключение **ReSOURCE Retail**: businessId `216369454`, campaignId `148767496`, единственный целевой partnerWarehouseId `1993419`. Склад выполнения — «Варфоломеева 265». Прочитаны 336 существующих offers, карточки, цены и остатки. Товары CRM, связи и продажи автоматически не создавались. Исходящий обмен на этом этапе не включался.

Для подтверждённой пользователем связи «PS4 It Takes Two (rus sub)» включено управление и продажа. Цена, остаток и размеры приняты API; отдельное чтение подтвердило цену и остаток. Рабочие значения меняются при последующих операциях CRM, актуальные состояния показываются в интерфейсе и журнале.

Кабинет возвращает `onlyDefaultPrice=true`, поэтому выбрана цена бизнеса. Остатки доступны через v3 API складов партнёра. В настройках отдельно поддержаны цена магазина для кабинетов, где она разрешена, и v2 API групп складов; эти альтернативы на рабочем кабинете не использовались.

Секрет лежит в `.yandex-market-key` в виде шифротекста Fernet, использует существующий `.integration-encryption-key`. Оба файла вне Git; резервировать отдельно вместе с медиа. Переменная `YANDEX_MARKET_API_KEY` имеет приоритет. Форма показывает только факт настройки; парольное поле не возвращает введённое значение. Право смены ключа — `manage_settings`. Смена ключа через форму выключает обмен до проверки.

Перед миграциями создана согласованная копия SQLite: `backups/before_yandex_20260924_152513/db.sqlite3`, проверены integrity и foreign keys. Ранее изменённая пользователем рабочая БД сохранена, старые документы не очищались.

## Порядок работы

1. Открыть **Интеграции → Яндекс Маркет → Настройки**. Проверить идентификаторы, ответственного, дату начала импорта и склад выполнения. Исторические заказы до этой даты сохраняются без нового складского списания.
2. Выполнить проверку подключения. Она читает API и не изменяет Маркет.
3. На вкладке «Обзор» загрузить существующие товары. Это очередь чтения каталога, без создания номенклатуры и автоматического сопоставления.
4. В «Товарах Маркета» выбрать карточку, найти CD/Tech по названию, артикулу, ID, CUSA/PPSA или любому штрихкоду. Сравнить товар и подтвердить. Подтверждение подписано, привязано к пользователю и действует 30 минут. Перед записью API заново проверяет выбранный offer.
   Название в списке открывает товар магазина на витрине Маркета в новой вкладке. Используется сохранённая ссылка `showcaseUrls` типа `B2C`, полученная через [официальный API каталога](https://yandex.ru/dev/market/partner-api/doc/ru/reference/business-offer-mappings/getOfferMappings), с `businessId` подключённого кабинета. Общая ссылка из ID модели и SKU не используется: она может открыть предложение другого продавца. Дополнительного чтения API при показе страницы нет; если подходящая ссылка ещё не получена, название отображается без ссылки.
   На вкладках «Связи CRM» и «Расхождения» под названием связанного товара есть ссылка с названием магазина, открывающая его предложение. Название товара ведёт к настройкам связи в CRM. Ссылка сама по себе не подтверждает возможность покупки: скрытое предложение, отсутствие остатка и регион доставки могут влиять на показ товара покупателю.
5. У каждой новой привязки, включая перепривязку, обмен и «Продаётся на Яндекс Маркете» включены по умолчанию. Подтверждение привязки разрешает передачу цены, физического остатка и размеров; сервер требует `yandex_market.edit_content` и `yandex_market.retry_sync`, а подключение должно пройти проверку. Сразу после commit ставится индивидуальная задача без трёхсекундной задержки. Для передачи нужна сохранённая положительная цена. При первой в истории CRM привязке скрытого предложения (`DISABLED_BY_PARTNER` в выбранном магазине) после передачи цены и остатка также вызывается `deleteHiddenOffers`. При выключенном обмене магазина или отсутствии цены интерфейс объясняет, что необходимо заполнить. Загрузка каталога сама по себе не создаёт связи и не включает товары без привязки к CRM.
6. При необходимости отредактировать контент, выбрать категорию из дерева и заполнить полученные из API характеристики. Повторно включать управление после привязки не требуется. Флаг продажи можно выключить вручную; тогда CRM передаёт нулевой остаток. Последующие сохранения цены не включают флаг обратно. Отправка выполняется только при включённом фоновом обмене магазина.
7. Новую карточку подготавливать из карточки CD/Tech после проверки существующего каталога. Идентификатор `GB-CD-<id>` / `GB-TECH-<id>` стабилен; перед созданием проверяется его наличие на Маркете. Не использовать создание для замены существующей качественной карточки.

Выключение флага продажи отправляет нулевой остаток. Отвязка прекращает управление, но не удаляет offer и не обнуляет его на Маркете: если нужно остановить продажи, сначала выключить продажу и дождаться успешной отправки нуля. Отвязка/перепривязка недоступна при открытых заказах, непринятых возвратах и активной синхронизации. Ссылки старых строк заказа остаются на прежней связи.

Чтобы перенести товар в раздел Маркета «Скрыты вами» и сохранить передаваемые цену и физический остаток, используйте отдельный флаг «Скрыт вами на Яндекс Маркете» в блоке товара CRM или на странице связи. Он вызывает API скрытия или возобновления показа, не меняет `sell_on_yandex` и не отвязывает товар. Состояние флага читается из последнего снимка Маркета; после отправки изменения обновление статуса может занять несколько минут.

## Контент

`RemoteOffer` хранит полный прочитанный снимок отдельно от `OfferConnection.content`. При привязке существующей карточки её название, описание, характеристики, габариты и ссылки на изображения сохраняются в БД. Они доступны в раскрываемом блоке «Яндекс Маркет» карточки CD/Tech. Загрузка этой страницы читает только БД.

После включения управления автоматически передаются `yandex_market_price`, общий физический остаток и длина, ширина, высота упаковки из CRM. Размеры подготавливаются при привязке, включении управления и изменении общих габаритов; существующие связи также получают их при следующей синхронизации или сверке. Первая привязка скрытого предложения автоматически разрешает этот обмен и возобновление показа. Изменения названия, описания, артикула и фотографий в общей карточке CRM не заменяют содержание существующей карточки Маркета. Редактор показывает размеры из CRM как поля только для чтения; менять их нужно в карточке товара или расчёте FBS. Вес существующего offer сохраняется из Маркета (включая явную правку в отдельном редакторе); если его нет, используется вес CRM. Без трёх положительных размеров и веса неполный блок не отправляется, обмен ценой и остатками продолжается. Для новой карточки стартовый контент, размеры и вес берутся из CRM.

`CategorySchema` кеширует схему по categoryId с датой получения. В форме есть типизированные значения, enum/мультивыбор, произвольные разрешённые значения, единицы и обязательность. Сервер проверяет принадлежность parameterId/valueId категории, границы, multivalue и зависимости. Для изменения `parameterValues` всегда передаётся `marketCategoryId`. При смене категории локальные значения сбрасываются для заполнения заново. Кнопка обновления принудительно загружает свежую схему.

Пустое поле сохраняет прежнее значение. Очистка — отдельное подтверждённое действие через `deleteParameters`; очищаемый параметр исключается из того же запроса. Очистка `weightDimensions` недоступна: размеры управляются из CRM. Редактирование общего контента `HAS_CARD_CAN_NOT_UPDATE` запрещено сервером; цена, остаток и габариты упаковки offer управляются отдельно. Состояния модерации, ошибки, предупреждения и contentRating читаются через API. Принятие HTTP-запроса не является подтверждением публикации или прохождения модерации.

Файлы JPG/PNG/WebP проверяются Pillow, ограничены 20 МБ/40 Мп и перекодируются в JPEG. Они хранятся отдельно от PDF. Публичная ссылка содержит случайный UUID, доступен только соответствующий файл изображения. Первая фотография основная; порядок можно менять. Удаление из набора не ломает ранее переданную постоянную ссылку. Старые внешние фото можно оставить или явно заменить новым набором. Видео и инструкции передаются постоянными HTTPS-ссылками. Размеры упаковки передаются из CRM в сантиметрах. Вес из CRM переводится из граммов в килограммы через Decimal.

## Остатки, цены и очередь

Общий физический остаток: сумма `CDWarehouseStock.quantity` или `TechWarehouseStock.quantity` по всем складам. `quantity_on_consignment`, товар в пути и остаток одного склада выполнения в эту формулу не входят. Внешний остаток никогда не импортируется в складские строки CRM. Все количество отправляется ровно на один технический склад Маркета.

Цена — существующее `yandex_market_price`. Передаётся точным числом JSON без float. Прочитанная цена Маркета сохраняется отдельно. Для сверки берётся `AVAILABLE`, либо `max(FIT − FREEZE, 0)` при отсутствии AVAILABLE: FIT включает резерв, уже списанные в CRM заказы не добавляются обратно.

Сигналы складских строк и карточек вызывают постановку после commit. Debounce — 3 секунды, ключ задачи постоянный; поколение увеличивается при новых изменениях. Worker читает текущие значения перед HTTP, не использует устаревший снимок количества в задании. Изменение во время HTTP оставляет следующее поколение pending. Последнее принятое значение предотвращает повтор одинакового состояния, а сверка принудительно исправляет внешнее расхождение. Перемещение с неизменной общей суммой не требует новой отправки.

Для обмена только с Маркетом запускайте `.venv\Scripts\python.exe manage.py run_integration_worker --service yandex`. В настройках подключения должен быть включён «Фоновый обмен», у связи — подтверждено управление, включена продажа и сохранена положительная цена. Расчёт, который пока только показан в поле ценообразования, не отправляется.

`OfferConnection.resume_display_pending` хранит незавершённое снятие скрытия после первой привязки. Миграция `0005` оставляет его выключенным у существующих связей. Флаг снимается только после успешного API-запроса; временная ошибка повторяется штатной очередью, периодическая сверка подхватывает незавершённое включение даже при совпадении цены и остатка. Перед запросом заново проверяются активность, версия связи, разрешённая продажа и текущие цена/остаток. Ручное выключение продажи отменяет ожидающее снятие скрытия. После успешного первого включения последующие изменения цены и остатка не вызывают повторного возобновления показа. Снятие скрытия записывается в аудит; публикация на витрине Маркета может занять несколько минут и зависит от его проверок.

Пакетная коррекция — пачки до 100 товаров, отдельные запросы цен и остатков. Карточки с редактируемым контентом обслуживаются индивидуально. `ApiBudget` ограничивает частоту в БД между процессами по консервативному лимиту `none` из официальной спецификации. Для v3 stock — 50 запросов в минуту. HTTP вне транзакций; таймаут 20 секунд, редирект ключа запрещён, размер ответа ограничен.

429/420, сетевые ошибки и временные 5xx повторяются с backoff 60/180/300/900/1800 секунд и `Retry-After`. Валидационные ошибки, 401/403 и остальные постоянные ошибки заканчивают задачу состоянием error до ручного повтора. Задача с устаревшей арендой восстанавливается через 20 минут. Периодическая сверка — каждые 15 минут после успешного прохода; постоянная ошибка видна в журнале и требует исправления/повтора. Сначала читаются заказы, затем каталог и остатки. Старые открытые заказы опрашиваются отдельно. Плановая сверка не заменяет уведомления.

`ApiLog` содержит операцию, шаблон пути с идентификатором, объект, HTTP-код, код ошибки, длительность, requestId, исполнителя и задачу. В нём нет заголовка Api-Key, тела запроса/ответа или контактов покупателя. `AuditEvent` сохраняет действия пользователей; интерфейс не позволяет редактировать/удалять историю.

С 11.10.2026 периодическая сверка независимо обрабатывает заказы, возвраты, каталог и торговые снимки. Ошибка чтения цены не мешает чтению и коррекции остатков, ошибка каталога не блокирует торговые снимки. Коррекция использует только поля, заново прочитанные в текущей сверке; старый снимок не считается подтверждением. Частичная коррекция не снимает ошибку контента и не запускает его отправку. Полный успех отмечается только после завершения всех этапов и получения торговых снимков всех управляемых связей.

Пустые `OrderMetadata`, созданные как ссылки на исторические возвраты, не опрашиваются как открытые заказы. Для известного заказа запрос передаёт небольшой диапазон вокруг даты его создания: иначе API по умолчанию ищет за последние 30 дней даже при фильтре по ID. Отсутствие одного заказа сохраняется в его ошибке и не прерывает сверку остальных данных. Периодическая задача после ошибки остаётся запланированной: временные ошибки повторяются с backoff, остальные — через 15 минут. Остановленная старой версией задача автоматически возобновляется планировщиком. Ошибки API сохраняются в журнале; HTTP 500 нельзя выдавать за успешную проверку.

## Заказы, отмены и возвраты

С 22.10.2026 новые автоматически созданные Sale получают отдельную запись `MarketOrderAttention` и внутреннюю кнопку «Заказ принят». Она сохраняет сотрудника и время, не вызывает API и не меняет внешние статусы, оплату или склад. Старые связанные Sale массово не включаются в тревогу, повторный импорт не сбрасывает подтверждение. Счётчик и звук работают глобально через polling; неподтверждённый заказ остаётся в отдельном списке даже после завершения или отмены. Ручной выбор типа и цены Яндекс Маркета закрыт, автоматический импорт сохранён. См. [контракт уведомлений](market_staff_alerts.md).

Актуальный источник — `POST /v1/businesses/{businessId}/orders` (`getBusinessOrders`). Устаревшие getOrder/getOrders не используются. Совпадение только по точному offerId активной связи. Неизвестный товар сохраняется в ошибке заказа; fuzzy matching и автоматического Product нет.

Импорт вызывает существующий `sales.services.create_sale` внутри атомарной обработки заказа. Уникальный `(integration, order_id)`, первый сериализующий SQL UPDATE и связь OneToOne с Sale защищают повтор. Создаются штатные складское списание, аудит и снимки себестоимости. Сумма строки — `payment + cashback` из актуального API, относящиеся ко всем единицам строки; subsidy хранится отдельно и не меняет формулу прибыли. Точная line_total сохраняется даже когда деление на количество даёт дробную копейку. Старые строки по текущим ценам не пересчитываются.

При недостатке на складе выполнения импорт полностью откатывает продажу и предлагает внутреннее перемещение; другой склад автоматически не списывается. Тестовый заказ не создаёт Sale. Внутренний статус и внешние status/substatus разделены. Доставка не подтверждает выплату: банковская Sale остаётся неоплаченной до штатного ручного подтверждения фактической оплаты.

Поддержанные действия FBS: `PROCESSING/STARTED → PROCESSING/READY_TO_SHIP`; отмена из STARTED/READY_TO_SHIP через `CANCELLED/SHOP_FAILED`. Перед готовностью нужны продажа и коробки. Worker сначала перечитывает заказ, проверяет переход, отправляет API, затем перечитывает результат. Ручная смена доставки/состава/отмена такой Sale через обычный сервис заблокированы. Физическая доставка Маркетом отражается в локальной последовательности статусов монотонно.

Отмена до отправки возвращает списанный запас один раз штатной отменой Sale. После отправки отмена не возвращает товар. Возвраты и невыкупы читаются отдельно. Приём требует права `accept_return`, подтверждения физического получения всех строк документа и выбранного склада. Проверяются невозвращённое списание и суммарное ранее принятое количество. Условная запись accepted_at — первый SQL UPDATE; повтор, превышение количества и fastReturn откатываются. Учёт фактического возврата не создаёт вымышленную выплату или кассовую операцию.

Если Маркет изменил состав уже импортированного заказа, интерфейс показывает требование сверки. Реализация намеренно не переписывает прошлые снимки и не выполняет неявную корректировку продажи. Такой случай требует отдельного решения сотрудника; это ограничение текущего автоматического сценария.

## Коробки и официальные PDF

В списке «Незавершённые продажи» и в карточке связанной продажи доступны отдельные кнопки «Готов к отгрузке» и «Отменить заказ». Селектор действий и флажки убраны. Готовность отправляется одним нажатием; только отмена открывает диалог с номером заказа и кнопками «Не отменять» / «Да, отменить заказ». Подтверждение отмены также проверяется сервером. Требуются право просмотра продажи и `yandex_market.manage_orders`; доступность кнопок определяется фактическим статусом Маркета. Подпись статуса, номер с техническими кодами и ссылка на заказ не показываются в блоке продажи. Обычный переключатель статуса CRM у связанного заказа не показывается. При отсутствии переданных коробок готовность недоступна: заполните коробки на странице заказа в разделе интеграции Яндекс Маркета.

Запрос ставится в существующую очередь, текущий статус не подменяется заранее. Worker заново получает заказ и проверяет допустимость перехода перед отправкой. В продаже показываются ожидание и ошибка последнего запроса. Для FBS продавец может передать готовность `PROCESSING / READY_TO_SHIP` либо разрешённую отмену; доставку подтверждает Маркет. Оплата продажи остаётся отдельным учётным действием. [Официальные переходы API](https://yandex.ru/dev/market/partner-api/doc/ru/reference/orders/updateOrderStatus).

Кнопка «Напечатать стикер Яндекса» в продаже создаёт задание прямой печати на локальный принтер компьютера CRM, оставаясь на текущей странице. Выбор формата и подтверждение отсутствуют: используется официальный PDF `A9_HORIZONTALLY` — 58×40 мм для термопринтера. Нужны право просмотра продажи и `yandex_market.print_labels`. Worker ожидает PDF, печатает через Windows и проверяет результат. Повтор HTTP с тем же UUID не печатает второй экземпляр. Новое явное нажатие после завершения создаёт перепечатку. Ручная печать сама не меняет готовность. [Формат официального PDF](https://yandex.ru/dev/market/partner-api/doc/ru/reference/order-labels/generateOrderLabels).

На странице незавершённых продаж сканер выбирает старейший подходящий заказ и учитывает по одной штуке. После всего состава автоматически задаётся одна коробка (если коробки ещё не указаны), получается свежий PDF и выполняется печать. Готовность отправляется только после подтверждённого результата Windows, а не после создания задания или PDF. Ручная готовность в продаже тоже блокируется до печати. При ошибке или неизвестном результате статус не отправляется. Браузерные окна и iframe не используются. Размер бумаги задаётся для отдельного задания; содержимое пропорционально вписывается в печатную область драйвера без обрезания. Настройка и границы аппаратного подтверждения: [сборка сканером](market_scan_fulfillment.md).

В заказе задаётся полный состав нескольких коробок. Сервер сверяет количества и ID строк. Для крупного товара поддержаны последовательные части одной единицы; все части должны присутствовать без повторов. Маркировка отдельных экземпляров через UI пока не вводится: для товаров с обязательной маркировкой используйте кабинет Маркета. API не обходится фиктивными кодами.

Коробки отправляются до READY_TO_SHIP. PDF одной коробки запрашивается по orderId/shipmentId/boxId, PDF заказа — по orderId; ID коробок и отправления отображаются из API. Массовая печать использует официальный асинхронный отчёт, сохраняет reportId и опрашивает его без повторной генерации. После DONE документ немедленно скачивается и сохраняется, временная ссылка отчёта не используется как постоянная.

PDF отдаётся только авторизованному сотруднику с `print_labels`, с private/no-store. CRM печатает оригинальный ярлык Маркета. На отдельной странице заказа остаются расширенные запросы и скачивание PDF в форматах A4/A7/A9/A9_HORIZONTALLY.

## HTTPS и уведомления

Публичного адреса сейчас нет. После настройки HTTPS сервера задать `YANDEX_MARKET_PUBLIC_URL=https://<домен>` без завершающего `/`. URL уведомлений: `https://<домен>/integrations/yandex/notifications/`. Тот же origin используется для UUID-ссылок фотографий. Не публиковать целиком `protected_media`, БД или каталоги ключей.

Проверяется реальный IP источника из официальных диапазонов `5.45.207.0/25`, `141.8.142.0/25`, `5.255.253.0/25`. `X-Forwarded-For` принимается только если непосредственно подключившийся узел входит в явно настроенный `YANDEX_MARKET_TRUSTED_PROXIES`. Прокси должен корректно дописывать/очищать этот заголовок. Придуманная HMAC-подпись не используется. Диапазоны и требования сверять с текущей официальной документацией при развёртывании.

PING отвечает version/name/time. Остальные уведомления сохраняются в inbox с уникальным хешем содержимого, затем ставятся в очередь; сетевых запросов в обработчике нет. Заказ всегда перечитывается из API. Дубликат не создаёт повторный Sale. Планировщик восстанавливает событие, оставшееся без задачи после аварии между commit и callback. Неизвестные будущие типы событий сохраняются как ignored.

## Проверка и обслуживание

```powershell
.venv\Scripts\python.exe manage.py check
.venv\Scripts\python.exe manage.py makemigrations --check --dry-run
.venv\Scripts\python.exe manage.py test --noinput
.venv\Scripts\python.exe manage.py verify_inventory
.venv\Scripts\python.exe manage.py verify_cash
rg --files -g 'test_*.cjs' | ForEach-Object { node $_; if ($LASTEXITCODE -ne 0) { throw "Ошибка JS-теста: $_" } }
```

Worker запускается существующей командой `run_integration_worker` и обслуживает две независимые очереди Avito и Маркета. Не запускать рабочий worker ради теста. Подключение Маркета выключено до явной активации в настройках. Сайт с `--noreload` и worker требуют отдельного перезапуска после изменения Python. Проверять точные пути и PID; не останавливать все Python-процессы.

Команда первичной настройки `configure_yandex_market --key-file <путь> --business <id> --campaign <id> --partner-warehouse <id> --warehouse <id> --operator <id> --read-catalog` читает ключ из файла, сохраняет шифротекст, проверяет API и по флагу читает каталог. Не передавать секрет значением аргумента командной строки. Новое подключение создаётся выключенным.

Проверки выполняются с фиктивным ключом, подменённым transport/API и отдельной тестовой БД. Матрица и результат — в [отчёте](yandex_market_report.md). Визуальная проверка браузером не завершена: Computer Use остановился, потому что не смог надёжно определить текущий URL Windows-браузера. Рендеринг страниц проверен Django-клиентом, это не заменяет проверку внешнего вида и наведения.
