# Подключение резервных копий и интерфейс Local Agent 1.1

Причина прежнего HTTP 403: устройство подключено, но `can_request=False`,
серверное резервирование выключено и публичный ключ восстановления не задан.
Отказ был правильным; приложение скрывало его причину общим TransportError.

Теперь heartbeat возвращает безопасные признаки готовности, расписание и
доступность worker. Сервер возвращает отдельные коды `manual_request_forbidden`,
`recovery_not_configured`, `backup_disabled`; клиент показывает причину и следующий
шаг. Токены, публичный/приватный ключ и сырой HTML ошибок в ответ не включаются.
Уже подключённому устройству разрешение ручного снимка меняется отдельно,
без ротации токена, с superuser-проверкой и аудитом.

Главный экран показывает подключение, ключ, расписание, последнюю копию и
отдельный результат пробного восстановления. История содержит дату, размер,
результат проверки и защиту от удаления. Опасные и редко нужные действия скрыты
под «Дополнительные действия». Печать остаётся отдельной вкладкой и не включается
при настройке резервирования.

Пароль нового ключа вводится владельцем только в локальном окне. Приватный PEM
зашифрован им; при выбранной опции пароль в профиле дополнительно защищён DPAPI
CurrentUser. В CRM передаётся только публичный ключ. Потеря всех экземпляров ключа
или пароля делает архивы невосстановимыми; папку ключа следует скопировать на
отдельный носитель. Автозапуск сохраняет прежнее согласие владельца.

Серверные архивы и staging локального Docker размещаются в постоянном внешнем
volume `resource-crm-backups`, `/var/lib/resource-backups`. Рабочая БД и WAL/SHM
остаются в прежнем `/app`; volume не заменяет их. Подготовка запускается отдельным
контейнером без сети и без доступа к БД. Старые зашифрованные архивы копируются
с проверкой SHA-256; исходные архивы и незавершённые файлы не удаляются.
Причина переноса — крайне медленные многочисленные файловые операции Windows/9p
во время подготовки полного архива. Не удалять этот volume при переустановке CRM.
Проверка версий исходных файлов в `file_stamps` использует `os.scandir` и один
`lstat` на элемент вместо нескольких запросов к общему диску. Состав, inode/device,
размер, mtime/ctime, запреты ссылок и 15-секундное окно согласованности сохранены.
На читающем Linux-соединении для Online Backup включён `mmap_size=268435456`,
чтобы SQLite не делал десятки тысяч мелких чтений через общий диск. Рабочие
писатели не меняются; guard-транзакция и SQLite Backup API сохранены. Подход
сверен с [документацией SQLite](https://www.sqlite.org/mmap.html).

«Проверить восстановление» распаковывает копию в новый приватный каталог
`profiles/default/restore_checks/<UUID>` и проверяет GCM, манифест, хеши файлов,
SQLite integrity/FK и соответствие ключей зашифрованным полям. Ни сайт, ни worker
восстановленной копии не запускаются, рабочая SQLite не открывается из Windows.
`last-restore-check.json` содержит только результат проверки и путь, без секретов.
Пробное восстановление не заменяет сохранение ключа на отдельном носителе.

  исполняемая сборка и фактическая цепочка резервирования проверены отдельно.

Обновлённая программа опубликована в каталоге приложений CRM. Замена локальной
программы сохраняет прежний каталог под именем `LocalAgent-previous-<дата>`;
профиль, токены, журнал и ключи располагаются отдельно и не перемещаются.
