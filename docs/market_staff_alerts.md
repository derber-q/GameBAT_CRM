# Таблицы каналов продаж и внутреннее подтверждение заказов Яндекса

Задание пользователя от 22.10.2026: переключение каналов, запрет ручных продаж/цен Яндекса и обязательное внутреннее подтверждение каждого нового автоматически созданного заказа. Звуковой файл предоставлен пользователем: `dadsdasasdas (1).mp3`.

В шапках CRM и админ-панели счётчик представлен компактной кнопкой 40×40 px: значок Маркета и круглый бейдж с количеством непринятых заказов, включая 0. При наличии заказов меняется фон всей кнопки; число и доступное название обновляются через прежний опрос без перезагрузки. Полное назначение и число доступны при наведении и для экранного диктора. Значок `static/img/yandex-market.png` сохранён без изменений из favicon [официального сайта Маркета](https://market.yandex.ru/); загрузка страницы CRM не обращается за ним во внешний сервис.

## Модули и порядок реализации

| Модуль | Ответственность | Зависимости |
| --- | --- | --- |
| manual-sale-policy | Закрыть ручной выбор Яндекса, сохранить внутренний импорт | Текущие forms, sales.services, yandex_market.orders |
| order-attention | Сохранить необходимость подтверждения и атомарную отметку сотрудника | Первый модуль, OrderMetadata, существующий аудит |
| sales-channels | Видимость таблиц, порядок, пустые категории | Существующие списки и AJAX статусов |
| global-order-alerts | Счётчик, очередь звуков, интервалы, координация вкладок | order-attention, общий base.html |

Порядок: manual-sale-policy → order-attention → sales-channels → global-order-alerts → интеграционные и браузерные проверки.

## Серверный контракт

Подтверждение хранится отдельной записью `MarketOrderAttention`, связанной один к одному с существующим `OrderMetadata`. Поля: начало оповещения, дата подтверждения и подтвердивший сотрудник. Запись создаётся в транзакции первого успешного автоматического создания Sale. Повторные импорты не меняют её. У существующих Sale такие записи не создаются: отсутствие записи означает исторический заказ без нового требования, а не фиктивное подтверждение от имени сотрудника.

Чтение уведомлений требует `sales.view_sales`; подтверждение дополнительно требует `yandex_market.manage_orders`. GET возвращает серверное время, интервал 600 секунд, полный список неподтверждённых заказов и их количество. POST с CSRF сохраняет подтверждение один раз и записывает аудит. Сотрудник и время первого подтверждения сохраняются при повторах. Статусы, деньги, остатки, комиссии и API Маркета не затрагиваются.

Внутренний сервис автоматического создания получает существующий объект заказа и использует доверенные настройки интеграции. Обычный сервис создания и пользовательская форма отклоняют тип и цену Яндекса. Флаги из HTTP не открывают внутренний путь.

Неподтверждённые заказы остаются доступны в карточке и в отдельном списке независимо от завершения или отмены продажи. Счётчик ведёт в этот список.

## Клиентский контракт

Опрос сервера раз в 15 секунд на всех страницах, дополнительно при восстановлении сети и фокуса. События подтверждения между компьютерами распространяются очередным опросом. При ошибке связи прежний счётчик помечается устаревшим, аудио не продолжает работу по неизвестному состоянию.

Цикл отдельного заказа вычисляется из сохранённого серверного начала и серверного времени: `floor((now - started_at) / 600000)`. Локально сохраняется только сыгранный цикл, а не факт подтверждения. После долгого сна обрабатывается текущий цикл без воспроизведения всего пропущенного.

Вкладки одного origin координируются транзакцией IndexedDB: общая аренда звукового исполнителя и журнал сыгранных циклов. Разные браузерные профили имеют независимые журналы. Это подходит и для LAN по HTTP, где Web Locks может быть недоступен. Одновременно играет один сигнал; новые заказы не сбрасывают интервалы прежних. При недоступной координации показывается ошибка, без небезопасного запуска звука сразу во всех вкладках.

Аренда исполнителя действует 60 секунд и продлевается во время воспроизведения. При обычном закрытии вкладки она освобождается сразу; при аварийном завершении следующая вкладка продолжит после истечения аренды. Для координации вкладки должны использовать одинаковый адрес CRM: разные IP, домены, порты и профили имеют раздельные хранилища браузера. Начало сыгранного цикла записывается только после успешного запуска `play()`; блокировка не отмечает сигнал сыгранным.

Кнопка включения звука запускает предоставленный MP3 с `volume=1`. Успех определяется разрешением Promise `play()`, отказ autoplay виден пользователю. Системную громкость приложение не меняет. Сон ОС, закрытый браузер и ограничения фоновых вкладок не позволяют гарантировать физическое воспроизведение точно по расписанию.

В CRM и Django Admin включение доступно через один значок динамика справа в шапке. Он включает разрешённые сотруднику каналы Яндекс Маркета и Avito; отдельные кнопки проверки звука убраны. После успешного включения значок становится зелёным и больше не запускает пробные сигналы. При отказе браузера он выделяется жёлтым и снова позволяет включить звук; причина доступна в подсказке и сообщении для экранного диктора. Обычные пояснения о звуке не занимают место над страницей; ошибка получения актуальных уведомлений остаётся видимой. Выбор каналов определяется прежними правами просмотра, а интервалы, подтверждение заказов и координация вкладок сохраняются. Общую кнопку обслуживает `notification-sound-controls.js`; аудио и сохранение разрешения остаются в существующих обработчиках площадок. Браузерная проверка: `core.sound_browser_checks` с отдельной тестовой БД.

Источники платформы: [play() и подтверждение запуска](https://developer.mozilla.org/en-US/docs/Web/API/HTMLMediaElement/play), [IndexedDB и транзакции](https://developer.mozilla.org/en-US/docs/Web/API/IndexedDB_API/Basic_Terminology), [ограничение Web Locks безопасным контекстом](https://developer.mozilla.org/en-US/docs/Web/API/Web_Locks_API).

## Таблицы каналов

На незавершённых и завершённых: Все → Яндекс Маркет → Опт → Авито → Розница. Обычное открытие и обновление начинают с «Все»; выбранный канал не сохраняется. Опт включает совместимые исторические значения без изменения записей. Пустые секции не выводятся; при выборе пустой категории — компактное сообщение. В незавершённых отдельного блока реализации нет. Завершённая реализация остаётся доступна в общем режиме для сохранения доступа к истории.

## Проверки

Тесты Django: ручной запрет/автоимпорт, повторные события, старые записи, независимость от статусов, CSRF/permissions, конкурентное подтверждение, каналы и отсутствие побочных изменений. JS: интервалы и последовательная очередь. Браузер: несколько вкладок одного профиля и независимые контексты, отказ autoplay, восстановление, мобильная навигация и прежние действия. В финале: полный Django suite, все `test_*.cjs`, check, миграции; рабочая БД отдельно только для диагностики. Перед рабочей миграцией — согласованная SQLite-копия. Коммит/push отдельного разрешения не получали.
