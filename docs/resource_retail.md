# Розничная витрина ReSOURCE

## Состояние

Розничное оформление использует согласованный способ оплаты «Не определён». Заказ создаётся неоплаченным, без кассовой операции. В карточке продажи сотрудник с правом подтверждения оплаты выбирает «Наличные — постоплата» либо «Банковский счёт». Сам выбор не принимает деньги; затем доступно обычное подтверждение оплаты. Повторное подтверждение и изменение уже выбранного способа отклоняются сервисом. Ограничение БД запрещает оплаченный заказ с неопределённым способом.

## Архитектура

- Вход: `/retailer/<token>/`, затем перенаправление на `/retailer/`. Корень домена продолжает вести на вход CRM. Оптовые маршруты `/opt/` и внутренние `/crm/` сохранены.
- Namespace `retailer` — серверный признак розничного режима. Общие `views.py`, `catalogue.py`, шаблоны карточки/каталога/корзины/подтверждения и скрипт обслуживают оба режима. Параметры запроса не выбирают режим цены или продажи.
- `RetailSettings` содержит склад, источник цены `avito_price`, поколение допуска, хеш токена и его шифротекст. Начальный склад — точное совпадение «Варфоломеева 265»; если его нет, требуется настройка сотрудником. Положительный остаток только выбранного склада, положительная цена Avito; подстановки оптовой цены нет. Минимальной суммы заказа нет.
- Токен — `secrets.token_urlsafe(48)`: 48 случайных байт. Сопоставление по SHA-256, для показа ссылки сотруднику хранится Fernet-шифротекст с существующим ключом проекта. Токен не связан с покупателем.
- «Прайс» показывает блок «Розничный сайт» сотрудникам с `manage_retail_storefront`: ссылка, копирование, POST-перегенерация с CSRF и подтверждением. Настройки склада/цены доступны в admin по соответствующим permissions.
- Перегенерация атомарно заменяет токен и UUID поколения. Все розничные views, включая изображения, поиск, корзину, статус и подтверждение, проверяют поколение на сервере. Для checkout повторная проверка выполняется внутри транзакции. Старые покупки остаются в CRM. Оптовые ссылки не изменяются.
- Токен удаляется из URL после входа; `no-store`, `no-referrer`, `noindex` стоят на ответах. Фильтр журналов Django скрывает `/retailer/<token>/`. Аналитика не добавлена. При будущем production-развёртывании журнал reverse proxy также должен маскировать путь токена: приложение не управляет внешними access logs.

## Корзина и заказ

У каждого посетителя случайный UUID в его собственной Django-сессии. Корзина и черновик имеют отдельные ключи `retailer_*`; оптовые ключи `resource_*` не затрагиваются. Общий токен не служит ключом корзины. Browser sessionStorage разделён по режиму и владельцу сессии. Корзина живёт 30 дней, добавление не резервирует склад.

Форма: обязательные имя и телефон; Telegram/WhatsApp/звонок, совместный выбор мессенджеров, Telegram по основному телефону либо @username/номеру, необязательный отдельный WhatsApp и комментарий. Без выбора способа связи используется телефон. Никаких автоматических сообщений и новых оптовых контактов.

`RetailSubmission` привязывает UUID операции и UUID посетителя к продаже. Checkout блокирует конфигурацию, склад, товары и остатки, повторно проверяет снимок корзины, вызывает `sales.services.create_sale` и связывает результат в одной транзакции. Продажа — `SaleType.RETAIL`, `PriceType.RETAIL`, источник `resource_retail`. Цены, историческая себестоимость и списание формируются существующим сервисом. При ошибке всё откатывается. Статус операции восстанавливает результат после потери ответа; подтверждение доступно только сессии владельца и при действующем общем допуске.

Контакты сохраняются снимком на продаже: `buyer_name_snapshot`, `buyer_phone_snapshot`, `buyer_contact_methods`, `buyer_telegram`, `buyer_whatsapp`, `buyer_comment`. Детали CRM показывают источник «Розничный сайт» и все контакты. Повторная отмена через существующий сервис возвращает остаток только один раз.

## Миграции

- `resource_storefront.0004_retailsettings_retailsubmission` — настройки общего входа и идемпотентные операции.
- `resource_storefront.0005_initialize_retail_warehouse` — безопасная начальная настройка известного склада.
- `sales.0016_sale_buyer_contact_methods_sale_buyer_telegram_and_more` — снимки способов связи и контактов мессенджеров; исторические продажи получают пустые значения.

Перед применением создан снимок через SQLite Backup API: `backups/crm_before_retail_20261003_173052.sqlite3`, `integrity_check: ok`. Все четыре миграции применены. Локальный сервер перезапущен; склад — «Варфоломеева 265», цена — `avito_price`. Проверены HTTP 200 входа CRM и каталога/корзины после допуска, HTTP 403 без допуска, отсутствие исходного токена в журналах сервера. Production не обновлялся. Секретный ключ и фотографии остаются вне Git. Миграция `sales.0017_alter_sale_payment_method_and_more` добавляет способ «Не определён» и ограничение статуса оплаты.

Итог после добавления способа оплаты: 158 серверных тестов — `OK`, код процесса 0; 3 браузерных/конкурентных теста — `OK`, код процесса 0. Все 7 файлов `test_*.cjs` прошли. `check`, `makemigrations --check --dry-run`, `migrate --check` завершились успешно. Тесты выполнялись в изолированных базах. Журналы: `outputs/resource-retail/payment-tests-final.log`, `outputs/resource-retail/browser-payment-final.log`. Проверены права выбора способа оплаты, отсутствие движения кассы при выборе, наличная/банковская оплата и отказ повторного подтверждения.

- Серверные проверки: все защищённые GET/POST, отзыв старых сеансов, энтропия токена, редактирование ссылки только с правом; независимость посетителей и режимов; отсутствие оптовых цен в розничном HTML; отсутствие подстановки цены/остатка другого склада.
- Формы: телефон, Telegram, WhatsApp, оба мессенджера, отдельный номер и некорректные значения. Проверены снимки контактов в CRM.
- Оформление в тестовой БД: серверная цена независимо от присланных параметров, единичный заказ при retry, восстановление статуса, отказ чужой сессии, изменение цены с явным подтверждением, откат после ошибки, нулевая касса и однократный возврат при отмене.
- Конкурентный тест двух реальных подключений к отдельной файловой SQLite: розница и опт одновременно покупают последнюю единицу. Одна продажа, один отказ 409, нулевой остаток, касса не меняется.
