# Архитектура и правила учёта

Описание проверено по коду 23.09.2026. Количество карточек, пользователей и связей — рабочие данные, а не константы приложения.

## Устройство

Django 5.2.17 обслуживает HTML, формы, JSON и экспорт XLSX. SQLite хранит данные и очередь Avito. Отдельный процесс `run_integration_worker` забирает задания из БД; Celery/Redis не используются. Клиентская часть — шаблоны `templates/`, общий `static/js/app.js`, скрипты страниц и CSS ReSOURCE. Текущий проверяемый интерпретатор — Python 3.14, зависимости закреплены в `requirements.txt`.

Поток операции: URL → view с проверкой доступа → форма/валидация → сервис → атомарная запись и аудит → HTML/JSON. Сетевая синхронизация выполняется отдельно; `transaction.on_commit` ставит задание после успешного завершения бизнес-транзакции.

## Товар и цены

`CD` содержит платформу и игровую серию, `Tech` — бренд и тип техники. Общие поля находятся в `ProductBase`. Рабочие выборки обычно используют `.active()`, исключая архив. Совпадение названия не доказывает дубль: отличаются платформа, язык, обложка, издание и идентификаторы.

Множественные штрихкоды хранятся в `BarcodeRegistry`. Совместимое свойство `product.barcode` возвращает первый код; новый поиск должен учитывать весь реестр. CUSA/PPSA, артикул и штрихкод не взаимозаменяемы; ведущие нули штрихкода сохраняются.

`cost` — глобальная средняя себестоимость карточки, а не цена конкретного склада. Продажные поля: `avito_price`, `wholesale_price`, `yandex_market_price`. Розничный `PriceType.RETAIL` выбирает `avito_price`. `None` отличается от нуля.

`avito_markup_from_wholesale` и `yandex_markup_from_wholesale` имеют default 189 ₽. Проверка сравнивает разницу цены и опта с порогом и отдельно цену с себестоимостью. Пустой порог отключает только проверку наценки этого канала; ноль остаётся действующим значением. Предупреждение не запрещает сохранение и не меняет цену автоматически.

Коррекция рабочих данных 23.09.2026 установила геймпадам Sony наценку Avito 289 ₽ и 489 ₽ при Special/Limited в названии. Это не правило модели для будущих карточек. Вес новых CD по умолчанию 120 г; технике вес задаётся отдельно.

## Количества и места хранения

1. Физический остаток: `CDWarehouseStock`/`TechWarehouseStock`, отдельно по складам.
2. Реализация: `CDConsignmentStock`/`TechConsignmentStock`, все партии всех площадок.
3. В пути: строки ещё не принятых перемещений; исходный склад уже уменьшен.
4. Глобальная собственность для себестоимости: склад + реализация + перемещения created/assembled/shipped. Расчёт — `supplies.services.global_owned_quantity`.

`quantity_on_consignment` должен равняться сумме строк реализации. Это агрегат, а не отдельный запас. История движений и текущий запас различаются: после исторических импортов движения не обязательно восстанавливают начальные остатки.

Остаток для Avito — сумма физических складов (`integrations.services.global_stock`), без реализации и товара в пути. Выключенный флаг продажи задаёт нулевой целевой остаток.

Места хранения привязаны к локальной строке склада через назначения и нормализованный справочник адресов. При обнулении остатка сервисы очищают назначения. Фильтрация адреса структурная, а не простое сравнение подстрок.

## Реализация и партии

Передача уменьшает физический склад, увеличивает партию площадки и агрегат товара. Возврат делает обратное движение на выбранный склад. Реализация создаёт продажу с согласованным вознаграждением и штатной денежной логикой.

Уникальность партии включает площадку, исходный склад, товар и `lot_key`. Пустой ключ используется обычной передачей. `consignment.opening_balances.add_opening_balances` добавляет ранее переданные товары без повторного списания со склада. Ключ состоит из источника и номера строки; повторная загрузка отклоняется.

Одинаковый товар с разными вознаграждениями показывается отдельными строками. Операции используют `stock_id`. Подписанный токен содержит пользователя, строку, количество, вознаграждение и одноразовый ключ; срок — 24 часа. `ConsignmentActionReceipt` записывается первым внутри транзакции: повторный ключ или устаревший снимок откатывает всю операцию.

## Продажи и деньги

Статусы заказа: created → assembled → shipped → delivered. Оплата хранится отдельно. Завершённая продажа — delivered AND paid без отмены; одного `completed_at` недостаточно. Отменённые определяются `cancelled_at`. Списки группируются по `SaleType`, по 50 записей на страницу каждой группы.

Строки сохраняют цену и снимок себестоимости; новая себестоимость карточки не переписывает прошлую прибыль. Для старых строк без снимка статистика может показывать отсутствие данных. Переплата отделена от суммы товаров.

Наличные, наличная постоплата и банковский счёт имеют разные моменты оплаты. Сервисы создают денежное движение один раз. Отмена оформляет возврат и восстановление запасов, не просто удаляет Sale. Недостаток денег на возврат откатывает операцию целиком. Изменения статуса из таблицы используют штатные сервисы и проверку версии записи.

Каждый склад имеет `CashRegister` и `Safe`. `CashTransaction` — единый журнал с типами операций. Перевод между кассой и сейфом не создаёт выручку. Баланс проверяется входящими минус исходящие операции. Кредиторы и клиентские закупочные заказы используют свои сервисы, а не подменяют продажу.

## Приход и оценка

Приход рассчитывает среднюю стоимость с учётом глобальной собственности. Доставка по весу распределяется в целых копейках методом наибольших остатков. Редактирование принятого прихода сохраняет ревизию и воспроизводит оценку последующих поступлений. Отмена и финализация имеют отдельные ограничения.

Финализация применяется при нулевой итоговой неустойке, актуальной ревизии и корректных снимках входных данных. Не заменять её прямой правкой `cost`. Расчёты и отмены должны сохранять точность и атомарность.

## Avito

`AvitoProductProfile` относится к CD либо Tech; `AvitoRemoteListing` хранит полученное объявление; `AvitoListingConnection` связывает их один-к-одному. Реквизиты зашифрованы Fernet, ключ находится вне Git. Сами связи сохраняются в БД при переносе.

Обычный источник истины — CRM. При привязке пустая цена Avito заполняется из объявления; уже заданная цена CRM остаётся и синхронизируется наружу. Активное объявление включает флаг продажи. Одноразовый обратный импорт по поручению пользователя не меняет направление синхронизации.

Сигналы изменения карточки и складской строки ставят задания после commit. Прямые SQL/`update()` сигналы не вызывают. Задания объединяются по ключу; ручные/статусные имеют приоритет. Running-задача без обновления более 15 минут возвращается в ожидание. Плановая сверка повторяется через 5 минут, обновление списка — через 60 минут. Правила повторов HTTP и блокировки SQLite — в `tasks.py`.

Ручная сверка обновляет список, читает остатки, сравнивает активные связанные объявления, отправляет различия и повторно читает данные. Прогресс разделяет проверенные, исправленные, пропущенные и ошибочные позиции. Ошибка API не подтверждает нулевой остаток. Архив и удаление объявления различаются. Блок необходимых действий использует локальные данные и отдельное обновление статусов.

Успешная проверка соединения не гарантирует права изменения цены/остатка, доступность категории, отсутствие лимита или работающий worker. Мгновенное совпадение при сетевых сбоях не гарантируется: смотреть подтверждение результата и ошибки конкретных товаров.

## Авторизация и группы

`accounts.User` расширяет `AbstractUser`. Groups и индивидуальные permissions объединяются стандартным Django. Views проверяют права независимо от меню через `permission_required_any`, `permission_required_all`, стандартные декораторы и `superuser_required`.

`stuf` защищён тем же `superuser_required`, что управление пользователями. Получает реальные Groups с `Prefetch(user_set)` и стабильной сортировкой. Пользователь появляется во всех своих группах. Безгрупповые, включая заблокированных, показаны отдельно; пустые группы сохранены. Документы не выводятся, их скачивание защищено отдельным маршрутом.
