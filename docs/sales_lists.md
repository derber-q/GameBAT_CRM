## Навигация и списки

- Основная ссылка «Продажа» ведёт на существующую форму `/sales/new/` (`sales:create`).
- Выпадающее меню содержит новую продажу, незавершённые, завершённые, отменённые.
  Использованы существующие `nav-dropdown`, `:hover` и `:focus-within`; доступные ссылки
  зависят от прав. Право создания не выдаётся автоматически: прямой переход без него
  по-прежнему запрещён.
- Новые GET URL: `/sales/incomplete/`, `/sales/completed/`, `/sales/cancelled/`.
- Старый `/sales/` сохранён как совместимый адрес незавершённых продаж.
- Незавершённые: `cancelled_at IS NULL` и НЕ (`delivered` AND `paid`).
- Завершённые: `cancelled_at IS NULL`, `order_status=delivered`, `payment_status=paid`.
- Отменённые: `cancelled_at IS NOT NULL`. Это соответствует свойствам модели Sale;
  один только `completed_at` не используется как источник истины.
- Группы построены по `Sale.SaleType.choices`: Розница, Опт самовывоз, Опт доставка,
  Авито, Яндексмаркет и существующая Реализация. Последняя сохранена, чтобы не потерять
  продажи реализации. Каждая продажа принадлежит одной странице состояния и одной группе.
- Общий шаблон страницы использует partial группы и строки. Сохранены ID/ссылка,
  примечание (с полным текстом в title), дата, склад/площадка, позиции/единицы, сумма,
  способ оплаты, сотрудник, даты завершения/отмены, отменивший сотрудник и возврат.
  Тип обозначается заголовком отдельной таблицы. В отменённых есть badge «Отменена».
- В старом списке не было поиска/фильтров/пагинации. Теперь каждая группа имеет независимую
  пагинацию по 50 продаж с сохранением номеров страниц других групп, порядок — от новых
  к старым. Пустые группы показывают «Нет продаж».

## Статусы и подтверждение

Крупные текстовые badges/select: создан — серый, собран — синий, отправлен — оранжевый,
доставлен/оплачен — зелёный, не оплачен/отменена — бордовый. Цвет не заменяет текст.

На незавершённых доступны только следующий order status и `unpaid → paid`, если это
допускает существующая логика и права. Завершённые и отменённые — read-only.
Таблица переходов заказа вынесена из существующего сервиса в общую константу без
изменения переходов; сервис и интерфейс используют её. Детальная карточка сохранена.

Выбор не изменяет отображаемый фактический статус: select немедленно возвращается к
текущему значению, открывается существующий по стилю `<dialog>`. Текст называет продажу,
старый и новый статус. Отмена и Escape не отправляют запросов. Только «Подтвердить»
отправляет POST. Для наличной постоплаты в диалоге можно указать фактически полученную
сумму; пустое значение имеет прежний смысл — стоимость товаров.

## Backend, права и безопасность

Новый `POST /sales/<pk>/status/` (`sales:inline_status`) принимает `field`, `value`,
`version`, `confirmed=1` и при необходимости `cash_received_amount`.
CSRF включён, токен отправляется через FormData; GET запрещён.

Endpoint требует `sales.view_sales` и соответствующее право:
`sales.advance_order_status` или `sales.mark_sale_paid`. Без права изменения отображается
badge. Завершённый список сохраняет прежнюю комбинацию прав: `view_sales` и
`view_completed_sales`; отменённый — `view_sales`.

В `transaction.atomic()` заново читается Sale через `select_for_update`, проверяются
terminal state и точная версия `updated_at`. Устаревший запрос получает 409 и фактическое
состояние; версия передаётся как ISO-строка без преобразования часового пояса шаблоном.
При конкурирующей записи SQLite ошибка блокировки обрабатывается без автоматического
повтора финансового действия. Затем вызывается **существующий** `advance_order_status`
или `mark_sale_paid` — endpoint не присваивает статусы самостоятельно.

Проводки, завершение, проверки кассы, постоплата, банковская оплата, журналирование
остаются в существующих сервисах. Правила создания, списания остатков, редактирования
состава постоплаты и отмены не изменены. Схема БД и рабочие данные этой задачей не меняются.

Двойной submit блокируется в JS; backend повторно проверяет версию и статусы;
существующая кассовая защита от повторной оплаты сохранена. Проверяется сохранение
ровно одной CashTransaction при повторном POST.

JSON возвращает `success`, `message`, фактические `order_status`, `payment_status`,
`is_completed`, `is_cancelled`, `version` и серверный HTML строки. Ошибки валидации
и конфликтов также возвращают фактическую строку; для отсутствующей продажи — 404.
При отсутствии доступа/сессии или сетевой ошибке UI не показывает ложный успех и
просит обновить список перед повтором.

После ответа обновляется только строка, без перезагрузки страницы. Terminal Sale
удаляется из незавершённых по флагам backend; счётчик и empty state обновляются.
Тип продажи никогда не меняется. Если закончились строки текущей страницы, но есть
другие страницы группы, отображается пояснение о переходе к ним.

## Производительность и проверки

`select_related` загружает склад, автора, отменившего сотрудника и площадку;
`prefetch_related` — оба набора SaleItem. Количество запросов не увеличивается с
числом продаж внутри страницы (проверяется тестом). Не загружается весь архив.

9 новых Django-тестов: все шесть типов и три состояния, ссылки и старый URL,
строгие переходы, завершение, права, CSRF/GET/подтверждение, stale/double-submit,
постоплата/переплата/единственная проводка/неизменность остатков, rollback при проблеме
кассы или сумме, terminal states, N+1 и независимая пагинация.

Node-тест реального JS: отсутствие запроса до подтверждения, отмена/Escape,
возврат select, блокировка двойного submit, ошибка оплаты, серверная строка,
удаление завершённой продажи и пустая группа.

Выборочный прогон: 27 тестов — OK. JS-тест — OK.
`manage.py check` — без замечаний; `makemigrations --check --dry-run` — изменений нет.
Полный test suite: **442 теста, OK, 92,908 с** (`manage.py test --noinput --parallel 4`).
Все три списка дополнительно отрендерены read-only на текущей базе: HTTP 200.
Сайт перезапущен на `0.0.0.0:8000`; локальный адрес и загрузка JS по LAN проверены.

Коммит и пуш не выполнялись. Визуальная проверка в подключённом браузере не проводилась;
проверяются серверный HTML и JS-сценарии.
