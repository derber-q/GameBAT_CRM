# Согласованная установка Telegram сотрудников

Подготовлено 02.11.2026. Требование задания: «Не применять новые миграции к
действующей рабочей БД автоматически во время разработки». До отдельного
согласования рабочая БД не мигрируется, настоящий бот не включается и API
не проверяется. [Функции и руководство](telegram_staff_bot.md).

## Подготовка

1. Проверить итог тестов, diff и миграционный план; сохранить чужие изменения.
2. Сохранить защищённую `backups/current_state_20261031.sqlite3` без перезаписи.
3. После остановки пишущих процессов непосредственно перед применением создать новый снимок текущей `db.sqlite3`
   через SQLite Backup API: `backups/before_telegram_staff_20261102.sqlite3`.
   Проверить integrity/foreign keys, SHA-256 и JSON метаданных. Обычное копирование
   активного SQLite/WAL не использовать. Если подготовительный файл уже существует,
   создать новый с суффиксом времени, не перезаписывая его. Снимок, ключи и медиа — вне Git.
4. Проверить источник токена, не печатая его. Не добавлять исходный TXT в репозиторий.
5. Проверить, что физическая печать не выполняется. Print Agent остаётся отдельным
   процессом Windows. Не завершать все Python-процессы.

Снимок отражает момент создания, а не дальнейшие операции. Ротация защищённой
копии этой установкой не выполняется.

## Изменения схемы и загрузка кода

- `integrations.0010_alter_workercommand_service_alter_workerservice_code`:
  choice `telegram_staff`, технические поля сервисов расширены с 12 до 20 символов.
- `telegram_bots.0001_initial`: конфигурация, доступы, коды, квитанции и задания.

Данные продаж, товаров, кассы, партнёров и сетевые вызовы не затрагиваются.
Миграции не создают/включают конфигурацию настоящего бота.
После согласования на нынешней локальной Docker CRM:

```powershell
docker exec resource-crm-local python manage.py migrate --plan
docker stop --time 300 resource-crm-local
# После остановки — свежий согласованный снимок SQLite по operations.md.
docker compose -f deploy/local_live/compose.yaml run --rm --no-deps crm-local python manage.py migrate --noinput
docker start resource-crm-local
docker exec resource-crm-local python manage.py check
```

Единичная согласованная остановка и запуск нужны для миграции без параллельных
записей и загрузки нового кода сайта/supervisor,
которые находятся в одном контейнере. В дальнейшем настройка Telegram не требует
перезапуска четырёх прежних worker. Отдельный магазинный Print Agent не трогать.
При нативной Windows-установке использовать проектный интерпретатор и остановку
конкретных проверенных PID; не подменять это завершением всех Python-процессов.
При ошибке миграции не восстанавливать БД и не откатывать внешний Avito автоматически:
сначала исследовать состояние схемы. Пара кода/снимка откатывается отдельным решением.

## Настройка и проверка

1. Superuser открывает «Интеграции → Telegram-боты».
2. Вводит username первого бота без `@`, оставляет его выключенным.
3. Настраивает токен защищённой формой/файлом/окружением. Сохранение не вызывает API.
4. После отдельного разрешения живой проверки нажимает «Проверить подключение без
   сообщений»: только `getMe` и `getWebhookInfo`, без файлов и сообщений.
5. Разрешает конкретному сотруднику бота и отдельно проверяет его право оптового
   прайса. Другие сотрудники по умолчанию закрыты.
6. Включает бота; supervisor запускает только новый необходимый Telegram worker.
7. Сотрудник получает одноразовую ссылку в своей CRM и нажимает Start в Telegram.
8. С разрешённым сотрудником проверяет получение актуального XLSX в личном чате.
9. Проверяет heartbeat и состояние прежних сервисов; `verify_inventory` и
   `verify_cash` выполняются отдельно от тестов, без исправлений рабочих данных.

Если webhook уже используется, выяснить владельца и согласовать переключение.
Автоматически удалить webhook или запустить параллельный polling нельзя.
Не объявлять настоящую выдачу проверенной по одному mock-тесту.

## Будущий перенос на другой хост

Выключить бота на старой CRM, дождаться завершения процесса/активной отправки и
проверить PID/heartbeat. Перенести согласованную БД с offset и секрет по отдельному
плану PostgreSQL/Linux. При webhook отдельно согласовать его отключение. Настроить
единственного нового получателя и только затем включить его. Не запускать две
независимые БД с одним токеном: общей аренды между ними нет. При conflict остановить
получателей и сверить процессы. `sending` после аварии автоматически не повторять.

Production остаётся заблокирован прежними правилами этапа B. Эти команды не являются
разрешением разворачивать production или подтверждением проверки PostgreSQL.
