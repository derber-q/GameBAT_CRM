# Пополнения поставщика из сообщений цифрового бота

Пассивный получатель цифровых продаж принимает также явные квитанции поставщика
«Пополнение баланса/счёта», «Баланс пополнен», «Зачисление средств» с суммой и
новым балансом. Пример фактической структуры: заголовок, ОПТ/ID магазина,
`Сумма: … руб`, `Новый баланс: … руб`, дата. ID магазина не используется как ID
платежа. Свободная просьба пополнить счёт или переписка о реквизитах квитанцией
не является. Отменённые, ожидающие, неоднозначные и неполные сообщения не дают
кнопку пополнения. Чек-листы/готовность заказов сохраняют прежний приоритет.

Парсер сохраняет `topup_receipt`, `topup_amount`, `topup_issues` в прежнем JSON
`SupplierMessage.parsed`, `kind=balance`, без новой таблицы и миграций. Новый
баланс имеет приоритет над прежним балансом внутри квитанции. Суммы — Decimal,
не float. При первом сообщении-квитанции начальный остаток автоматически не
создаётся: поступление допустимо только после команды сотрудника. Для ранее
сохранённой как обычный баланс квитанции `receipt_details` может прочитать её
зашифрованный оригинал без переимпорта и изменения истории.

Прежние ограничения на числовые ID групп и отправителей, проверяемую пересылку,
offset, fingerprint и версии сообщения остаются в `ingestion.accept_update`.
Квитанция не создаёт DigitalOrder, Sale, кассовую проводку или баланс покупателя.
Если нового баланса нет, в outbox добавляется уведомление для ручной проверки;
конечный баланс не придумывается по объявленной сумме.

Карточка CRM-бота показывает поставщика, сообщённый баланс, объявленную сумму,
ожидаемый баланс и расхождение. Кнопка «Подтвердить пополнение +… ₽» вызывает
прежний callback `dbal` и `reconciliation.apply_topup`. Повторно проверяются
действующий сотрудник и права telegram_digital_sales, view_digital_reconciliation,
topup_digital_balances. Уведомления приходят через существующий Notification/outbox
сотрудникам, допущенным к цифровым продажам и сверке; отзывы доступа учитываются
перед отправкой. Чаты покупателей не используются.

Под блокировкой поставщика проверяются последняя редакция квитанции, порядок
событий, ранее учтённые закупки и доступная положительная разница. Объявленная
сумма должна полностью помещаться как в неучтённый остаток на момент квитанции,
так и в остаток по последнему самостоятельному снимку. Поступления по более
поздним явным квитанциям не погашают раннюю: их можно подтвердить в любом порядке.
Ручные внесения и общая сверка уменьшают остаток и защищают от повторного учёта.
Частично учтённая квитанция требует ручной проверки, сумма не меняется молча.

Для движения используется `move_balance(kind=topup, supplier_id=…)` и стабильный
UUID от поставщика, chat ID и Telegram message ID. Варианты редактирования одного
сообщения не создают повторное поступление. Одновременные подтверждения разными
сотрудниками сериализуются блокировкой; observation.topup_movement возвращает
ранее проведённое движение. Сохраняются сотрудник, причина, аудит и ссылка на
проводку; после успеха outbox обновляет карточку без активной кнопки.

Обычные самостоятельные снимки без явного пополнения сохраняют прежнюю функцию
«Выполнить поступление» по расхождению. Балансы внутри заказа по-прежнему не
создают финансовое уведомление. Новая логика не пересчитывает и не перепроводит
исторические движения.

Регрессионные сценарии подготовлены в `digital_sales/test_topup_receipts.py`;
прежние проверки — `test_reconciliation.py`. По действующему указанию владельца
тестовые наборы не запускаются. Для включения Python-кода требуется перезапуск
контейнера; создание новых миграций не требуется.
