# Наценки цифровых покупателей

Автоматическая отправка персональных комплектов после обновления:
[расписание, очередь и защита данных](digital_price_auto_dispatch.md).

## Подписи для пересылки прайса (13.11.2026)

CRM-бот отправляет каждую страницу с подписью: имя выбранного покупателя из снимка
комплекта, номер изображения, название раздела, время актуализации данных (МСК)
и контакт для заказа `@GameBAT_Store`. Первая подпись дополнительно перечисляет
типы товаров из фактически отправляемых строк. Это подпись самой фотографии
или высокого PNG-документа: она сохраняется при пересылке покупателю.

Названия страниц сохраняются в публичном JSON комплекта `page_titles` из тех же
`section`/`family`, по которым строятся изображения. Для прежних комплектов есть
чтение известного формата имени файла без повторного расчёта цен. Используется
`source_at`, а не текущее время отправки; неизвестная дата или устаревший снимок
помечаются явно. Себестоимость, наценки и имя поставщика в подписи не включаются.
Подписи отправляются тем же запросом, что и изображение, поэтому существующие
подтверждения `PageDelivery` и запрет повтора неопределённой отправки сохраняются.
Миграции и изменения рабочих записей цен не нужны.

Для покупателя «Подписки GNS»/«GNS» каждая подпись дополнена строкой
«🆕 Оформление на новый аккаунт: +150 ₽», для «Подписки Играть»/«Играть» —
«🆕 Оформление на новый аккаунт: +100 ₽». Это текст условий оформления,
он не меняет наценки, стоимость строк или денежные операции продаж.

В «Цифровых товарах» над каталогом находится выбор «Чьи наценки отображаются». «Общие наценки» сохраняет прежние настройки. Остальные варианты — существующие `digital_sales.Buyer`; отдельный розничный покупатель в этот список не добавляется. Выбор и фильтры передаются через GET, доступны прямые ссылки `?buyer=<ID>`. В формах AJAX и генерации прайса покупатель передаётся явно, поэтому открытые вкладки разных покупателей независимы. При переключении с несохранёнными строками браузер предупреждает об их потере.

`digital_prices.BuyerMarkup` хранит наценки конкретного покупателя ровно для одного `Product` либо `ManualPriceEntry`. Уникальные ограничения запрещают повтор пары покупатель/позиция. Отсутствующая запись или пустое индивидуальное поле означает использование актуальной общей наценки именно этого поля. Заполненное значение, включая 0, имеет приоритет. Первое сохранение создаёт только указанные индивидуальные значения; остальные режимы не заполняются копиями общих наценок. Очистка поля возвращает наследование. В форме показывается собственное значение (пустое при наследовании), в итоговой цене и предварительном расчёте используется эффективная общая или индивидуальная наценка. Рубли, процентные пункты и коэффициенты хранятся раздельно в `Decimal`, без отрицательных значений; округление клиентской цены осталось прежним.

Себестоимость, наличие, режим тарифа и оформление позиции общие. В профиле покупателя редактируются только наценки; сервер отклоняет попытку изменить себестоимость или режим. API и Google Sheets обновляют прежние поля себестоимости, не перезаписывая индивидуальные наценки. Обновления общих наценок не меняют уже сохранённые индивидуальные значения.

Изменение выполняет `buyer_pricing.edit_buyer_markup`, нужны действующий сотрудник и права `digital_prices.view_cost` + `digital_prices.edit_markup`. Внутри транзакции блокируется общий `CatalogState`, проверяется версия исходной позиции и версия индивидуальной записи. Версия `исходная:индивидуальная` защищает от сохранения старой вкладки, включая первое одновременное создание. Изменения увеличивают ревизию каталога и оставляют `AuditEvent` с ID покупателя и перечнем полей. Сервисы продаж, складов и денежных журналов не вызываются.

Таблица и `public.snapshot` получают эффективные наценки через один `profile_rows`: запрос каталога и одна выборка всех переопределений покупателя, без отдельного запроса на строку. Исходные ORM-объекты копируются в памяти; себестоимость не включается в публичный DTO. Веб-предпросмотр и скачивание формируют полный комплект выбранного покупателя. `PriceBundle` сохраняет покупателя и снимок его имени для подписи в CRM, сам PNG содержит прежние публичные поля без наценок и себестоимости. Старые комплекты остаются без покупателя и не регенерируются.

CRM-бот при запросе «Прайс цифровых товаров» сначала показывает цифровых покупателей (по 20 на страницу). До выбора очередь не создаётся. После выбора `BuyerPriceRequest` фиксирует покупателя для задания `StaffBotJob`; исполнитель передаёт его в тот же `generate_bundle`, который использует веб. Права повторно проверяются при запросе и отправке. У задания без выбора покупателя новый исполнитель не отправляет общий прайс: сотруднику нужно заново открыть меню и выбрать покупателя. Повтор одной Telegram update не создаёт второй запрос; существующий учёт частичной и неопределённой отправки не изменён.

Миграция `digital_prices.0010_buyer_markups` добавляет две таблицы и необязательные поля комплекта. Она не размножает старые наценки по покупателям, не меняет продажи, балансы и цены исторических документов. Перед применением к рабочему контейнеру — согласованная копия SQLite и проверка восстановления. Сценарии для последующего запуска: `digital_prices/test_buyer_markups.py`; прежние проверки отправки в `digital_prices/tests.py` учитывают новый шаг выбора. Без отдельной команды пользователя тестовые наборы не запускаются.


## Выдача заполненных блоков (13.11.2026)

Таблица CRM по-прежнему содержит полный активный каталог для заполнения наценок.
Перед рендерингом нового PNG-комплекта `public.populated_blocks` удаляет только
целые блоки без единой эффективной наценки. Ключ блока совпадает с `layout.group_key`
и дополнительно включает секцию services/codes; страны, платформы и типы аккаунтов
не смешиваются. Частично заполненный блок сохраняет все свои строки. Наценка 0
считается заданной. Наличие «Нет в наличии» и отсутствие подтверждённой себестоимости
не являются основанием скрывать блок, в котором наценка уже указана.

Если после отбора на странице нет блоков, рендерер не создаёт изображение и бот
его не отправляет. Если не осталось ни одного блока во всём комплекте, бот присылает
понятное сообщение о необходимости заполнить общие или индивидуальные наценки.
Веб-предпросмотр/скачивание используют тот же состав, что и CRM-бот. Число строк
в `PricePage` сверяется с отобранным снимком. Служебный флаг наличия наценки не
включается в сериализованный публичный снимок; суммы наценок и себестоимость
по-прежнему отсутствуют в клиентских изображениях и метаданных.

Сохранённые раньше комплекты и уже заполненные индивидуальные значения не
переписываются. Миграций и массового изменения БД для нового правила нет.
Сценарии: `digital_prices/test_price_inheritance.py`; запуск наборов — по команде владельца.
