# Эксплуатация, проверки и восстановление

Перенос системы партнёров: [миграции, совместимость и проверки](partners.md). Старые карточки, долги и документы автоматически не объединяются. Перед миграциями — согласованная SQLite-копия и проверка старых кредиторских проводок; после — `verify_inventory`, `verify_cash` и перезапуск проверенных процессов сайта/worker. `verify_cash` учитывает выдачи/погашения кредиторов отдельно по кассе и сейфу; банк и безденежные записи в кассовый журнал не входят.

Прямая печать ярлыков: [сборка сканером и подтверждение печати](market_scan_fulfillment.md). На компьютере CRM нужны Windows, драйвер принтера и зависимости `requirements.txt`; игнорируемый `.label-printer.json` содержит `{"printer_name": "Xprinter XP-365B"}`. Штатный `start_localhost.ps1` запускает отдельный скрытый `manage.py run_label_print_worker`; `-SiteOnly` его не запускает. Процесс обслуживает только печать и передаёт операции Маркета существующей очереди. В тестах Windows-печать и API подменяются. После изменений Python перезапускать соответствующий процесс по проверенной команде; печатающее задание после потери процесса автоматически не повторяется.

Перенос исторического статуса новинки описан в [catalog_procurement_controls.md](catalog_procurement_controls.md): сначала `backfill_product_newness --dry-run` с JSON-отчётом, затем применение только подтверждённых записей. Команда `--apply` создаёт согласованную SQLite-копию. Источник и дата создания должны подтверждаться; неизвестные карточки автоматически не меняются. Миграции `catalog.0032` и `price.0010` не выполняют этот перенос сами.

Все команды ниже выполняются из корня проекта в PowerShell. В рабочем окружении это `C:\Users\89085\Desktop\GameBAT_CRM`; в другой копии путь нужно заменить. Не копировать персональные абсолютные пути в бизнес-код.

## Сайт и worker

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\start_localhost.ps1 -SiteOnly
```

Локальный адрес — `http://127.0.0.1:8000/`, с другого устройства — `http://<IP компьютера>:8000/`. Устройства должны иметь сетевой доступ; проверить брандмауэр, привязку `0.0.0.0`, IP и ALLOWED_HOSTS. `DisallowedHost` означает, что сервер достигнут, но Host не разрешён. Не исправлять это бессрочным разрешением всех хостов.

Отдельный рабочий процесс интеграции:

```powershell
.venv\Scripts\python.exe manage.py run_integration_worker
```

Он выполняет реальные задания Avito, Яндекс Маркета и Google Sheets. `--once` означает один цикл обработки, а не безопасную имитацию. `--poll` задаёт паузу при пустой очереди. Без `-SiteOnly` скрипт `start_localhost.ps1` проверяет сайт и отдельно проверяет обработку `avito`, `yandex` и `google`. Недостающие сервисы запускаются скрыто с `--service`; общий worker без этого флага либо с `--service all` покрывает все три сервиса. Наличие только worker Яндекса не препятствует запуску Avito и Google. Журналы новых сервисных процессов сохраняются в `outputs/localhost/`. Затем открывается браузер. `-SiteOnly` не запускает и не останавливает обработчики; `-NoBrowser` отключает открытие браузера.

Для отдельного сервиса используйте `--service yandex`, `--service avito` или `--service google`. Без этого параметра сохраняется обработка всех интеграций. Например, `.venv\Scripts\python.exe manage.py run_integration_worker --service yandex` обслуживает только Маркет.

### Локальная сеть и MacBook

Ярлык «GameBAT CRM — локальная сеть» вызывает `start_localhost.ps1`. При каждом запуске скрипт выбирает действующие IPv4 физических адаптеров, исключая VPN, отключённые интерфейсы и адреса `169.254.*`. Он добавляет все найденные LAN IP в `DJANGO_ALLOWED_HOSTS` и сохраняет дополнительные явно переданные хосты. Проверка выполняется без системного прокси на loopback и каждом LAN IP. Если текущий адрес не разрешён, скрипт перезапускает только `runserver` этого проекта на порту 8000. Если все адреса отвечают штатным перенаправлением CRM на вход, процесс сохраняется. Журналы нового сайта записываются в игнорируемую Git папку `outputs/localhost/`.

Причина сбоя, подтверждённая 13.10.2026: сохранённая ссылка `192.168.0.101:8000` указывала на Wi-Fi компьютера с CRM. В журнале WLAN за 12.10.2026 есть повторные отключения этого интерфейса по политике автоматического подключения, в том числе через 96 секунд после подключения. При этом Ethernet продолжал работать на `192.168.0.131`. Перезапуск Wi-Fi временно возвращал старый адрес. По адресу Ethernet сервер дополнительно возвращал HTTP 400, поскольку этот IP отсутствовал в разрешённых хостах. После запуска с актуальным списком по Ethernet проверены вход (HTTP 200), склад (штатный HTTP 302 на вход) и успешное открытие с MacBook.

Предпочтение Ethernet и отключение лишнего Wi-Fi описаны в [документации Windows Connection Manager](https://learn.microsoft.com/en-us/windows-hardware/drivers/mobilebroadband/understanding-and-configuring-windows-connection-manager). Системную политику для исправления CRM не меняли: используется действующее кабельное подключение.

Используйте на MacBook адрес Ethernet, который открывает ярлык, пока компьютер с CRM подключён кабелем к тому же роутеру. Wi-Fi самого MacBook может оставаться включённым. Отключение серверного Wi-Fi тогда не прерывает доступ к CRM. Для постоянного адреса после перезапусков роутера закрепите DHCP-адрес Ethernet за его MAC в настройках роутера; скрипт этого не меняет. При изменении сети или IP повторно запустите ярлык и обновите ссылку на MacBook. Во время уже работающего процесса список хостов автоматически не меняется.

`connectionfailure` означает отсутствие соединения и отличается от ответа Django `DisallowedHost`/HTTP 400. При повторном сбое сначала сравните адрес в браузере с действующим IP сервера и проверьте `Get-NetTCPConnection -LocalPort 8000 -State Listen`. Системный журнал отключений Wi-Fi:

```powershell
Get-WinEvent -FilterHashtable @{LogName='Microsoft-Windows-WLAN-AutoConfig/Operational'; Id=8001,8003} -MaxEvents 12 | Select-Object TimeCreated,Id,Message
.venv\Scripts\python.exe manage.py test core.test_local_network --noinput
```

## Google Sheets

В `E1` листов «Номенклатура» и наличия записывается дата и время последней успешной синхронизации в формате `ДД.ММ.ГГГГ ЧЧ:ММ:СС`, по московскому времени. Метка одинакова на обоих листах и обновляется после записи данных и оформления. Ячейки `E2:E` и остальные столбцы вне `A:D` не очищаются. При ошибке синхронизации новая метка не публикуется.

1. Создать Service Account в Google Cloud, включить Google Sheets API и скачать JSON-ключ в защищённую папку вне репозитория.
2. Выдать адресу `client_email` из ключа право редактора на нужную таблицу. Одна ссылка на таблицу авторизацией не является.
3. Передать процессам сайта и worker переменную `GOOGLE_SERVICE_ACCOUNT_FILE`. При необходимости переопределить URL и имя листа переменными выше.
4. В «Интеграции → API ключи» проверить настройки и поставить ручную синхронизацию в очередь.

CRM полностью очищает и заново записывает диапазон `A:D` двух управляемых листов: «Номенклатура» и настраиваемый лист наличия (в рабочей таблице «Наличие»). Недостающие листы создаются автоматически; имя наличия не может совпадать с «Номенклатура». Остальные листы и столбцы вне `A:D` не очищаются. В номенклатуре остаются все активные позиции, в наличии — положительный остаток и подтверждённый нуль менее календарного месяца. Для нуля обязателен признак `has_been_in_stock`; никогда не поступавшие позиции и новые карточки с нулём за последний месяц исключены. Признак восстанавливает миграция `catalog.0023_product_stock_history` и поддерживают сигналы склада. Заголовки пустых групп не создаются, фильтр Google для этого не нужен. Плановое задание обновляет оба листа каждые 10 минут. При ошибке статус и `last_error` сохраняются, CRM продолжает работать, а периодическое задание повторяется. Не добавлять JSON-ключ в Git, резервную копию БД или журналы.

При `--noreload` после правок Python или шаблонов остановить проверенные процессы проекта и запустить заново. На Windows `.venv\Scripts\python.exe` может иметь дочерний процесс Python: два PID сами по себе не доказывают два сервера. Проверять слушателей порта:

```powershell
Get-CimInstance Win32_Process | Where-Object {
    $_.Name -match '^python' -and $_.CommandLine -match 'manage.py (runserver|run_integration_worker)'
} | Select-Object ProcessId,ParentProcessId,CommandLine
Get-NetTCPConnection -LocalPort 8000 -State Listen
```

`runserver` — сервер разработки. Эти инструкции описывают локальную сеть, а не готовое публичное размещение с TLS, резервированием и промышленным WSGI/ASGI-сервером.

## Проверки кода

Корректировка AED рейса использует миграцию `orders.0005_trip_supplier_price`: добавляется только nullable-время явного изменения цены, без пересчёта старых записей. Перед применением — согласованная SQLite-копия и проверка единственной ожидаемой миграции; затем перезапуск проверенного сайта с `--noreload`. Worker интеграций и печати этой функции не требуются. Серверные проверки: `manage.py test orders.test_trip_prices orders.test_trip_price_concurrency`; браузерная — `orders.trip_price_browser_checks` на отдельной тестовой SQLite. Не проверять сохранение цены на рабочих заказах. [Описание](trip_supplier_prices.md).

Оплата продаж, банковская постоплата и миграция истории: [правила и проверки](sale_payments.md). `sales.0020_payment_methods` применяется после согласованной SQLite-копии и краткой остановки конкретных процессов сайта/worker. Она сохраняет завершённые и отменённые банковские продажи, а действующие незавершённые переносит в банковскую постоплату по статусам, без изменения денег и остатков. При наличии продаж автоматический откат запрещён; восстанавливается согласованная пара кода и БД. Обратный шаг схемы разрешён только при пустой таблице продаж для миграционных проверок. Ранее работавший worker после обновления должен загрузить новый Python-код, чтобы автоматические заказы Маркета создавались с банковской постоплатой. Новый worker ради проверки интерфейса запускать не требуется.

## Диагностика данных

```powershell
.venv\Scripts\python.exe manage.py verify_inventory
.venv\Scripts\python.exe manage.py verify_cash
```

Первая команда проверяет сумму реализации и отсутствие отрицательного склада. Она не сверяет фактический пересчёт товара с Excel. Вторая сверяет кассы и сейфы с журналом. Обе ничего не исправляют. Расхождение требует исследования первичных записей; нельзя просто обнулить журнал или переписать баланс.

`verify_avito_sync` обращается к реальному API и обновляет локальные снимки/создаёт CSV. Без `--fix` не предназначен для исправления внешних данных; с `--fix` может отправлять изменения. Для обычного тестирования кода использовать подменённый API в тестах.

Если ручная синхронизация ожидает: проверить worker и соответствующую очередь (`AvitoSyncJob` или `GoogleSheetsSyncJob`), `run_after`, `last_error`, фазу и время обновления. Успешный HTTP проверки подключения не равен завершённой сверке. Для SQLite учитывать короткие блокировки записывающих процессов; не оставлять сетевой HTTP внутри долгой транзакции. Не запускать несколько worker без проверки конкурентного захвата заданий.

## Резервная копия

При установке внутреннего подтверждения Маркета применяется `sales.0023_market_order_attention`: она добавляет отдельную таблицу, без заполнения по старым продажам. Перед применением сохранить согласованную SQLite-копию и проверить план миграций. На время установки остановить только проверенный worker этого проекта; после миграции перезапустить его для загрузки нового пути автоматического создания Sale. Сайт с `--noreload` также требует перезапуска. Worker печати не затрагивается. Не запускать дополнительную синхронизацию или исправление Avito ради проверки уведомлений.

После установки проверить GET счётчика и страницы ожидающих подтверждения, затем включить звук на каждом рабочем месте. Для искусственных заказов использовать только изолированные тесты. Отметка «Заказ принят» — постоянное действие сотрудника, её нельзя выставлять рабочим заказам ради проверки. Опрос уведомлений — 15 секунд, повтор звука — 10 минут на заказ. Ошибка сети приостанавливает звук до получения актуального состояния. Подробности: [уведомления](market_staff_alerts.md).

Рабочий файл — `db.sqlite3`. Копия активного файла обычным копированием может не включить состояние журнала. Использовать SQLite Backup API либо остановить все пишущие процессы и убедиться в согласованности БД. Пример согласованного снимка с новым именем:

```powershell
.venv\Scripts\python.exe -c "import sqlite3; from pathlib import Path; from datetime import datetime; folder=Path('backups'); folder.mkdir(exist_ok=True); target=folder/('crm_'+datetime.now().strftime('%Y%m%d_%H%M%S')+'.sqlite3'); source=sqlite3.connect('file:db.sqlite3?mode=ro',uri=True); snapshot=sqlite3.connect(target); source.backup(snapshot); assert snapshot.execute('PRAGMA integrity_check').fetchone()[0]=='ok'; assert not snapshot.execute('PRAGMA foreign_key_check').fetchall(); snapshot.close(); source.close(); print(target)"
```

Сохранить отдельно `.integration-encryption-key`, `.django-secret-key`, используемые переменные окружения и `protected_media/`. Не выводить значения ключей в журнал. Снимок SQLite не содержит файлов фотографий/документов. Папки резервирования и секреты исключены из Git.

Рабочая `db.sqlite3` и резервные копии исключены из Git. Для контрольной точки сохранять хеш коммита вместе с именем согласованной локальной копии БД; код и снимок должны соответствовать друг другу. Старые коммиты содержали БД: прекращение отслеживания не удаляет эти файлы из истории Git. Рабочие данные CRM хранить отдельно от публичного репозитория.

## Восстановление

1. Выбрать проверенный коммит и сохранить текущее состояние отдельно.
2. Остановить сайт, worker и другие процессы записи. Проверить точные PID и пути.
3. В отдельной папке восстановить код из выбранного коммита, а базу — из соответствующей локальной резервной копии. Не смешивать старую БД с несовместимым набором миграций.
4. Вернуть секреты и медиа из защищённой копии; при другом ключе Avito потребуется заново ввести реквизиты. Связи товара и объявления остаются в БД.
5. Выполнить integrity/foreign-key проверки, `check`, просмотр миграций, `verify_inventory`, `verify_cash`. Миграции вперёд применять только после понимания версии восстановления.
6. Запустить сайт, проверить карточки и операции. Worker включать после проверки целевых цен и остатков.

Откат CRM не откатывает Avito: восстановленные цены и остатки могут быть устаревшими относительно внешнего аккаунта. Прерванные задания имеют механизм повторного запуска; это также нужно учитывать перед включением worker.


## Доступ к розничному сайту

Ссылка находится в CRM → «Прайс» → «Розничный сайт» (право `resource_storefront.manage_retail_storefront`). Перегенерация закрывает старую ссылку и ранее выданные розничные допуски, сохраняя заказы и оптовые ссылки. Склад и источник цены настраиваются в `RetailSettings` через admin. Секрет `.resource-token-encryption-key` резервировать отдельно от Git: он нужен для показа ранее выпущенных ссылок.

Для production журнал reverse proxy должен скрывать секретный сегмент `/retailer/<token>/`; фильтр Django скрывает его только в журналах приложения. Не подключать аналитику к URL входа. После обновления Python перезапускать конкретный процесс сайта с `--noreload`; worker для этой задачи не требуется.

## Avito Check и ReefAPI

Ручная проверка находится в «Ценообразование» → «Avito Check», ключ — в «Интеграции» → «API ключи» → «ReefAPI». При резервном копировании хранить ключ шифрования интеграций отдельно от SQLite; без него ранее сохранённый API key не расшифровать. Кнопка «Проверить подключение» выполняет внешний запрос и расходует кредиты ReefAPI. Тесты используют подменённый клиент.

Кнопка «Проверка» читает объявления (до 10 кредитов, повторный результат за сутки бесплатен), а «Далее» сохраняет изменённые цены через обычный сервис CRM. «Обновить сейчас» принудительно обновляет экономный результат; «Искать глубже» имеет отдельный лимит до 40 кредитов. После изменения цены Avito действующая событийная синхронизация работает своим прежним путём; запускать worker ради проверки интерфейса не требуется. Подробности отбора трёх предложений: [avito_check.md](avito_check.md).


## Коррекция доплат Tech в старом закупочном прайсе

После резервного копирования и проверки ID прайса и сотрудника сначала выполните предпросмотр:

```powershell
.venv\Scripts\python.exe manage.py backfill_procurement_tech_surcharges --price-list 1 --actor 1
```

Команда без `--apply` ничего не записывает. Для явно согласованной коррекции повторите её с `--apply`. Изменяются только доплата и постоплата старых строк Tech с пустым `postpayment_surcharge_rub`; сохранённые ручные ставки, предоплата, наценка, доставка, CD и товарная память сохраняются. Сотруднику требуется право изменения наценки. Использованный в заказе прайс заблокирует операцию; неизвестная ставка или ошибка записи откатывает всю коррекцию. Повторное применение после успеха не меняет данные. Проверить соответствие всех строк согласованным ставкам отдельно от тестовой БД.
