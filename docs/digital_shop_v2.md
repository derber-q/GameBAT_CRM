# Цифровой магазин API v2

Дата реализации: 13.11.2026. Переход применяется поверх существующих цифровых
продаж и балансов. Само применение схемы **не включает реальные закупки**.

## Границы

`digital_prices` отвечает за каталог, API-себестоимость, общие и индивидуальные
наценки, Sheets-тарифы и существующие изображения прайсов. `digital_sales`
сохраняет покупателей, поставщика, денежный журнал, реальные `Sale` и текущий
цифровой Telegram-бот. `digital_shop` добавляет корзины, резервирование,
устойчивые намерения закупки, сверку выполнения и очередь выдачи.

Физические CD/Tech, касса склада и реализация не используются для закупки
цифрового товара. У магазина нет второго денежного журнала: `BalanceHold`
учитывает суммы заказов в обработке отдельно от фактического баланса, допуская долг.

## Работа покупателя

1. Администратор привязывает группу к существующему цифровому покупателю,
   отдельно включает магазин для группы и разрешает реальные закупки.
2. Любой подтверждённый участник группы открывает `/shop`. Участие заново
   проверяется через `getChatMember`; анонимный отправитель и другие боты не
   могут использовать магазин. Бот должен иметь права администратора группы.
3. Меню показывает только доступные предложения v2 с заданной эффективной
   наценкой. Индивидуальное непустое значение имеет приоритет; пустое наследует
   общее; явный ноль допустим. Неподтверждённые и неоднозначные карточки скрыты.
4. Для кодов последовательно выбираются платформа и регион. Поиск игр обращается
   к v2; варианты без заведённой и оценённой карточки не получают выдуманную цену.
   Сотруднику приходит запрос проверить найденные варианты в CRM.
5. Корзина общая: покупатель + группа. Любой подтверждённый участник может
   продолжить состав, ввод данных и подтверждение. Устаревшая ревизия не меняет
   заказ: бот показывает актуальную общую корзину. Команда `/shop` каждый раз отправляет
   меню новым сообщением в конец чата, сохраняя корзину. После успешной отправки
   кнопки прежнего меню убираются. Переходы по кнопкам редактируют текущее меню.
   В корзине есть состав и удаление конкретной позиции, без кнопок количества.
   После подтверждения открывается следующая общая корзина в том же меню.
   Список заказов также общий для группы; инициатор подтверждения записывается в аудит.
6. С 14.11.2026 при наличии обоих режимов в `requirements.account_modes` бот
   предлагает **новый / существующий аккаунт**. Если режим один (например, у
   конкретной Xbox-подписки), используется только он. Выбора сохранённого
   аккаунта нет: каждое добавление услуги создаёт независимую группу реквизитов.
   На новом аккаунте реквизиты не запрашиваются: сразу выполняется расчёт,
   затем покупатель явно подтверждает окончательную сумму. Только это
   подтверждение создаёт намерение реальной покупки. На существующем аккаунте
   сразу запрашиваются свежие данные, без адресной книги и повторного использования.
7. Бот одним сообщением запрашивает реквизиты текущих услуг. Ответ может дать
   любой подтверждённый участник именно через reply на актуальный запрос. Обязательные поля
   проверяются. Для ручной услуги принимается свободное сообщение; для одной
   услуги не требуется шаблон. Исходный текст целиком передаётся в
   `credentials.additional_data`, а логин и пароль выделяются из подписанных
   строк, пары строк или пары «почта пароль». Неоднозначность требует уточнения,
   без выдуманных значений и без закупки. Согласно контракту API, подписки и игры
   всё равно требуют `credentials.login/password`; произвольный `data` разрешён
   только товарам с `account_format=text`. Автоматические услуги сохраняют
   структурированный шаблон, Steam — логин или короткую ссылку друга.
   В шаблоне группы обозначаются понятными номерами `[1]`, `[2]`; внутренние
   идентификаторы аккаунтов покупателю не показываются. Реквизиты зашифрованы
   только на время обработки заявки; это не адресная книга аккаунтов.
8. Реквизиты видны участникам общей группы — бот прямо предупреждает об этом.
   При наличии права удаления исходное сообщение удаляется после безопасного
   шифрования; это не обещание скрыть его от тех, кто уже прочитал сообщение.
9. Покупатель видит окончательные суммы GameBAT по строкам и общий итог.
   `expires_at` принимается как целое число или `Decimal` Unix-секунд с дробной
   частью: переход через `float` не используется. Значение должно быть конечным,
   находиться в будущем и укладываться в шестиминутный предел. Просроченный
   Telegram callback не прерывает действие; отказ расчёта дополнительно остаётся
   обычным безопасным сообщением в исходной группе и категорией в аудите.
   Просроченный или изменившийся расчёт требует нового согласия. Ошибка
   `price_changed` / `quote_expired` при первом документированном отказе до
   закупки освобождает резерв и сохраняет состав для нового расчёта.
10. После подтверждения фиксируется сумма заказа в обработке, а исполнение продолжается в
    фоне. Готовые результаты приходят в исходную группу. Длинный комплект
    кодов разбивается на сообщения без обрезания, с сохранением прогресса.
    Нулевой и отрицательный баланс покупателя не блокируют оформление:
    задолженность учитывается тем же журналом. `BalanceHold` отделяет сумму
    обрабатываемых заказов от уже списанных денег, но не ограничивает кредит.
    Окончательное списание выполняется один раз после подтверждённого выполнения.
    Внешний API самостоятельно проверяет свой баланс и право закупки; его отказ
    не обходится локальным разрешением отрицательного внутреннего баланса.

Ограничения контракта: до 30 строк, 20 аккаунтов, 50 единиц, 1–20 единиц в
строке с учётом API-шага и остатка; Steam topup/gift — по одной единице.

## API и общий лимит

Единственный сетевой адаптер — `digital_prices/provider.py`, корень
`https://yanstore.ru/api/external/v2/`. Поддержаны документированные balance,
products, search, detail/editions, steam-check, **POST quotes**, POST orders,
GET orders/detail/by client ID и PUT полных данных аккаунта. Для новой работы
нет запроса к v1 и нет сетевого fallback на прежний список кодов.

Ключ берётся из прежней зашифрованной `Integration`. Он не передаётся в URL.
Адреса фиксированы, редиректы выключены, ответы ограничены по размеру,
сетевые и бизнес-ошибки переводятся в технические категории без исходного текста.

`ProviderGate` хранит общее скользящее окно 20 запросов за 61 секунду в SQLite.
Оно охватывает все процессы и виды операций; 429 блокирует общее окно. Важные
операции временно уступают себе место у фонового каталога. Ожидание и сеть
выполняются вне транзакции. Длинные запросы продлевают аренду worker и намерения.

Общий список закупок опрашивается примерно каждые 12 секунд при наличии
активных заказов. Изменение статуса назначает запрос подробного результата;
резервный индивидуальный опрос — раз в две минуты. При большой очереди общий
лимит имеет приоритет перед желаемой частотой. Не создаётся второй получатель
`getUpdates`: добавлены callback-события существующего DigitalBot.

## Переход каталога

`Product` дополнен версией API, прежним ID, требованиями, способом исполнения,
лимитами количества и состоянием сопоставления. Непрозрачный ID v2 не
конструируется из номера v1. Автоматическое сопоставление кодов требует
однозначного совпадения семейства, региона, валюты, номинала и варианта.
При точном совпадении сохраняется прежний PK вместе со всеми FK и наценками.

Несколько кандидатов не получают разрешение покупки. В панели магазина
сотрудник может явно подтвердить соответствие; конфликты наценок блокируют
перенос. Старые карточки и исходные наценки не удаляются. При ручной связи
карточка получает `superseded_by`, а совместимые наценки переносятся без потери
исходной истории. Старые v1-коды исключены из новых клиентских PNG, чтобы не
образовывать второй набор предложений. В административном каталоге они остаются.

`plan_digital_v2` только читает v2 и выдаёт план: совпадения, неоднозначности,
отсутствующие и новые ID, количества общих и индивидуальных наценок. Реальный
отчёт нельзя подменять результатом анализа фикстур. Обычное согласованное
обновление каталога применяет только однозначные соответствия и сохраняет аудит.

API-себестоимость недоступна ручному редактированию через backend. Новое
непустое значение обновляет снимок. Ошибка, отсутствующая цена или исчезнувшая
карточка не затирает последнюю стоимость нулём и не разрешает покупку.
Тарифы Sheets в рублях, процентах и коэффициентах сохраняют прежний источник;
автоматическое объявление их эквивалентными произвольному товару API запрещено.
Исчезнувшие из прочитанной таблицы строки отмечаются «Нет в наличии» с сохранением
истории и наценок; остальные блоки продолжают обновляться. Подробности:
[восстановление обновления 14.11.2026](digital_prices_sync_recovery_20261114.md).

## Финансовый протокол

`quotes.lines[].price` — стоимость всей строки. Сумма строк плюс adjustment
сверяется с total. Копейки распределяются детерминированно; наценка применяется
на единицу и используется существующее правило округления. Сохраняются закупка,
клиентская цена, количество, правило, наценка и версия карточки. Пользователь
видит только клиентскую часть снимка.

Для нового аккаунта применяются согласованные клиентские доплаты из
`digital_prices.customer_terms.new_account_fee`: Играть — 100 ₽, GNS — 150 ₽
(включая имена «Подписки Играть»/«Подписки GNS»). Этот же источник используется
в подписи прайса. Неизвестному покупателю доплата автоматически не назначается.
Клиентская доплата прибавляется после округления базовой клиентской цены,
строго один раз на отдельный новый аккаунт. В корзине и подтверждении режим
виден явно, в подтверждении указано, что доплата уже включена.

Закупочная котировка сохраняет реальный `new` и весь `adjustment`. Для
клиентской базы запрашивается отдельная котировка на существующие аккаунты
там, где каталог разрешает этот режим: так закупочная плата/льгота нового
аккаунта не дублирует согласованную доплату покупателю. Для new-only товара
Xbox базой служит цена строки из актуальной котировки, без account-adjustment;
несовместимый existing не отправляется. Дополнительная котировка не является
покупкой. Снимок хранит реальный расход, клиентский итог, режим и доплату;
смена условий до подтверждения требует пересчёта. Старые завершённые продажи
не пересчитываются. Каждый новый аккаунт оформляется одной отдельной строкой.

Перед резервом выполняется запись `ShopConfig.write_revision`, сериализующая
SQLite-писателей до чтения общего баланса. Затем проверяется
`Buyer.balance − сумма активных remaining`. Два подтверждения не могут
зарезервировать один остаток. По решению владельца отрицательный баланс
допустим и для автоматического магазина; резерв учитывает обязательство,
а не устанавливает кредитный лимит.

В одной транзакции сохраняются `PurchaseIntent`, уникальный client_order_id,
шифрованное каноническое тело POST, SHA-256, `PurchaseLine` и `BalanceHold`.
Внешний POST происходит после commit. Повтор использует то же тело и ID.
Сбой после отправки переводит намерение в uncertain; сначала выполняется поиск
по client_order_id. Неизвестный исход, конфликт ID и частичный результат не
освобождают деньги и не порождают новый идентификатор закупки.

Подтверждённые созданные позиции регистрируют `SupplierPurchase`, числовой
`OrderReference` и расход в прежнем `BalanceMovement`, даже при paid=false и
ожидании исполнения. Завершение клиента не списывает эту закупку второй раз.
Сообщение Telegram с тем же purchase ID связывается с существующим API-заказом
и не создаёт повторную продажу или закупку. Гонка с ранее импортированным
сообщением останавливается на ручную сверку.

Только выполненная/active позиция с проверенным результатом создаёт и завершает
`Sale` через действующие сервисы. Списывается клиентский баланс и уменьшается
её резерв. Для партии создаются снимки каждой единицы с точным распределением
копеек, чтобы состав и статистика не превращались в одну условную штуку.
Покупательские накладные не получают внешний закупочный номер.

Автоматическое освобождение всего резерва допустимо при подтверждённом failed,
нулевом charged_total, отсутствии созданных и неподтверждённых позиций.
Внешний cancelled не равен возврату денег. Проверенный полный возврат отдельной
невыполненной позиции фиксируется сотрудником с правом корректировки балансов,
основанием и отдельным `ConfirmedRefund`; журнал получает связанное сторно,
освобождается резерв строки. Отмена API-продажи прежней веб-кнопкой запрещена.

## Конфиденциальность

Проверены отдельные границы:

| Граница | Разрешённые данные |
|---|---|
| Кнопки и карточки магазина | Очищенное название, платформа/регион, клиентская цена |
| Подтверждение корзины | Название, количество, суммы GameBAT, срок расчёта |
| Ошибка покупателю | Фиксированное сообщение или проверенный пользовательский текст |
| Результат | Точный комплект codes, completed=true или строго разобранные поля login/password/email |
| Чек и баланс | Номер Sale CRM, клиентский состав/итог, внутренний баланс покупателя |
| PNG и подпись | Публичный DTO, актуальность, контакт GameBAT, имя покупателя |

Закупочные суммы, наценки, имя/ссылки поставщика, технические product/quote/order
ID и исходный ответ API в эти DTO не передаются. Название с закрытыми словами
заменяется целиком — после удаления имени рядом не остаётся секретная сумма.
Публичный снимок PNG ограничен списком допустимых ключей, проверяется перед
каждой отправкой. Нормализация Unicode и дополнительные фильтры блокируют
закрытые подписи и URL. Изображения/описания/ссылки поставщика напрямую не
пересылаются. Свободный `result.data` не транслируется в чат: неизвестный формат
или подозрительный фрагмент блокирует результат целиком, без исправления кодов.

Реквизиты, оригинальное тело POST, ответ и выдача хранятся зашифрованными прежним
ключом digital_sales. Пароли не обрезаются, ключи и секреты не логируются.
После окончательного результата очищается тело POST и дубли реквизитов корзины.
Просмотр защищённого ответа в CRM требует отдельного права и оставляет аудит.
Обычная панель не расшифровывает результаты автоматически.

Перед выдачей заново проверяется привязка исходного чата к тому же покупателю и
отсутствие чата в списке поставщиков. Outbox помнит части и Telegram message ID.
Неизвестный исход отправки блокирует повтор кода; сотрудник должен проверить
чат и явно разрешить повтор. При подтверждённой миграции Telegram-группы
переносятся привязка, корзины и неотправленные результаты. При конфликте или
неподтверждённых правах магазин приостанавливается для ручной сверки.

Это проверка устройства и исходников, а не заявление о пройденных end-to-end
испытаниях. Тестовые сценарии подготовлены, но по указанию владельца не запущены.

## Интерфейс и разрешения

«Контрагенты → Баланс цифровых продаж → Магазин в группах» либо
`/crm/digital-shop/`. Требуются `digital_shop.manage_shop` и
`digital_prices.view_cost`. Включение реальных закупок дополнительно проверяет
разрешения действующего сотрудника на создание/завершение цифровых Sale.
Отзыв этих прав останавливает автоматическое проведение, а не обходит защиту.

Панель содержит выключатели, группы, внешний снимок баланса без перезаписи
журнала, поиск/издания, ручные сопоставления, заказы/резервы и неоднозначную
выдачу. Детальная страница заказа позволяет показать защищённый ответ,
подтвердить безопасно подготовленный результат и явно повторить выдачу.

## Включение и эксплуатация

1. Проверить публичные границы и сохранить согласованную SQLite-копию **в Docker**,
   отдельно сохранить используемые ключи. Защищённую current_state не удалять.
2. Применить схему к отдельной копии, сверить сохранность исходных бизнес-таблиц.
   Это проба миграции, а не замена полного тестового набора.
3. Остановить старые процессы контейнера, сохранить точную предмиграционную копию,
   применить миграции служебным контейнером без сети. БД и её пути не заменять.
4. Запустить прежний контейнер, проверить login, план миграций и новые отметки
   worker/ботов. Не отправлять покупателям пробные сообщения и товары.
5. После отдельного разрешения запустить план каталога, рассмотреть соответствия,
   выполнить обычное обновление, назначить отсутствующие индивидуальные цены.
6. Выбрать ответственного сотрудника/поставщика, включить нужные группы, затем
   отдельно разрешить реальные закупки. До этого POST orders заблокирован.

Команда плана после применения схемы: `docker exec resource-crm-local python
manage.py plan_digital_v2`. Она обращается к реальному API, расходует общий лимит,
но не меняет каталог/наценки/балансы и не отправляет клиентские прайсы.

## Проверки и ограничения

Подготовлены `digital_shop/test_contracts.py`, `test_checkout.py`,
`test_recovery.py`, `test_concurrency.py`, `digital_prices/test_v2_mapping.py`.
Они используют fake-транспорт, синтетические ключи и отдельную тестовую БД.
Проверки адаптера прежнего каталога обновлены под единый транспорт.
Полные Django/JS suites в этом внедрении не запускались по прямому указанию.

У API нет подтверждённого endpoint для OTP/2FA и возврата произвольной покупки.
Такой сценарий не объявляется полностью автоматическим. Неизвестный формат
результата, требование нового типа данных, конфликт закупки и отсутствие
подтверждения возврата остаются на сверке. PUT полной замены аккаунта реализован
в адаптере, но не даёт обхода режима выполнения или автоматического ввода OTP.
Настоящая покупка и выдача в рабочую группу в процессе разработки не выполнялись.
