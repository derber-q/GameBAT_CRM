# Автоматическая отправка цифровых прайсов

После нового успешного `SyncJob` (ежедневного или ручного «Обновить цены»)
`digital_prices.services.apply_catalog` в своей транзакции создаёт
`BuyerPriceDispatch`: по одному комплекту для каждого покупателя, связанного
с `digital_sales.BuyerBalanceChat`. Старые задания не переигрываются.
Правка наценок сама по себе рассылку не запускает.

Расписание используется прежнее, из `digital_prices.Integration`: `daily_at`
и `timezone_name`. На момент включения — 09:00 Europe/Moscow. Отдельного
таймера рассылки нет: без успешного обновления отправки не будет.

## Условия отправки

- Обновление API завершено, активного обновления нет. Если подключена таблица
  тарифов, её обновление тоже успешно, без пропущенных/неполученных значений.
- Генератор — действующий сотрудник с привязкой к CRM-боту и правом выдачи
  цифровых прайсов; эти права проверяются заново при отправке.
- Чат — сохранённая отрицательная Telegram group ID с прежней связью покупателя.
  Группы поставщиков исключаются независимо от привязки.
- Текущий `CatalogState.source_at` совпадает со временем данного обновления.
  Новый запуск обновления блокирует оставшуюся отправку старого комплекта.

`digital_sales.worker` отправляет не больше одной страницы за цикл через уже
проверенный цифровой бот. Дневная рассылка не использует токен CRM-бота и не
создаёт второй polling. В большие PNG сохраняется отправка документом.

Комплект строится прежним `generate_bundle(actor, buyer)`: индивидуальная
наценка, наследование общих значений, отбор заполненных блоков и подписи
`presentation.page_caption` одинаковы с выдачей через CRM-бот. В том числе
сохраняется текст оформления на новый аккаунт для GNS и «Играть».

## Секретность

Источник генерации — публичный DTO `PublicCatalog`, без ORM закупок и балансов.
Автоматическая очередь хранит только ссылки на готовые публичные PNG и подписи.
Перед отправкой дополнительно запрещаются внутренние поля и упоминания
поставщика/себестоимости/наценок в публичном снимке. Сырые исключения, ключи,
ответы API и URL поставщика не попадают ни покупателю, ни в предупреждения.
Санитайзер удаляет также сокращённое имя поставщика без суффикса Store.

## Доставка и восстановление

После подтверждения отправки **всех** изображений нового комплекта бот закрепляет
каждое из них, затем снимает закрепы изображений предыдущих комплектов этого же
покупателя в этом же чате. Используются только сохранённые Telegram message ID,
`unpinAllChatMessages` не вызывается. Чужие закрепы и сообщения о балансе не
затрагиваются. При неполной доставке прежние закрепы сохраняются.

Страницы имеют последовательность состояний `done` → `pinned` → `unpinned`:
во всех трёх изображение уже доставлено, повторная отправка запрещена.
Состояние комплекта `pinning` означает обновление закрепов. Pin/unpin выполняются
по одной операции за цикл, с проверкой действующей привязки и права администратора
`can_pin_messages`. Подтверждение Telegram проверяется как `True`; уведомление
о новом закрепе подавляется. При временном сбое можно повторить закрепление
того же message ID, не отправляя картинку заново. Ошибка прав направляется
сотрудникам через CRM-бот. Удалённый или уже снятый известный закреп считается
снятым; произвольный последний закреп никогда не используется вместо message ID.

Дополнительная миграция для закрепов не требуется: используются существующие
состояния журнала доставки. Для уже отправленных актуальных комплектов предусмотрен
явный сервис `queue_current_pins(actor)` с правом `configure_integration` и аудитом:
он ставит на закрепление только подтверждённые сообщения, без повторной отправки
изображений. Полномочия методов сверены с
[Telegram Bot API](https://core.telegram.org/bots/api#pinchatmessage).

Уникальная пара `(sync_job, buyer)` исключает повторное создание рассылки одного
обновления. Для каждой картинки `BuyerPriceDispatchPage` фиксирует `pending`,
`sending`, `done` и Telegram message ID. После прерывания в `sending` результат
становится `uncertain`: ни эта картинка, ни оставшийся комплект автоматически
не пересылаются. После достоверного отказа по ограничению частоты допускается
повтор с задержкой, а подтверждённые картинки не повторяются.

Ошибка обновления создаёт предупреждение в существующем outbox
`digital_sales.Notification` для сотрудников с доступом к цифровым прайсам.
Префикс `price_dispatch:` проверяется по этим правам, отдельно от прав продаж.
Ожидаемые повторы получения API группируются в одно предупреждение; окончательный
отказ — отдельное сообщение. Ошибка получения Google-таблицы также блокирует
рассылку, даже если основной API уже сохранён. Старые клиентские сообщения
не удаляются, баланс и продажи не меняются.

На странице цифровых товаров отображаются последние отправки. Неизвестную
доставку следует проверить в Telegram; принудительного автоматического повтора
нет. Следующее самостоятельное успешное обновление создаёт новый комплект.

Миграция `digital_prices.0012` добавляет только две таблицы outbox и ограничения.
Для внедрения сначала создаётся согласованный проверенный снимок SQLite,
миграция проверяется на отдельной восстановленной копии, затем применяется
к рабочей базе в Docker. Тестовые наборы не запускались по указанию владельца;
сценарии для последующего запуска — `digital_prices.test_auto_dispatch`.
