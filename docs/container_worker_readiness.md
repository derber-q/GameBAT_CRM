# Готовность контейнера и обработчиков

## Подтверждение работы

PID и heartbeat показывают только существование процесса. Новые поля `WorkerProcess` разделяют независимый heartbeat и результаты основной работы:

- `progress_at` — основной цикл завершил итерацию или обработал ошибку;
- `verified_at` — основной цикл завершился успешно;
- `health_error` — безопасная категория текущей ошибки, без токена/URL/сообщений;
- `executor_at` — завершённый цикл отдельного исполнителя документов CRM-бота.

Heartbeat не обновляет эти подтверждения самостоятельно. Начальная готовность — False. В Telegram успешных `getMe` / `getWebhookInfo` недостаточно: нужен успешный `getUpdates` и обработка результата текущим процессом. Успех прошлого экземпляра не переносится на новый.

Начальное подключение цифрового и оптового ботов повторяет только безопасные чтения API при `timeout`, `network`, `rate_limited`. Отправки не повторяются. Неверный токен/username, webhook и конфликт получателей показываются как «Требуется настройка». CRM-бот дополнительно проверяет поток документов; завершение этого потока вызывает штатный выход для восстановления supervisor.

У очередей подтверждается завершённая итерация штатного исполнителя, включая пустую очередь. Это доказательство работы исполнителя, а не успешности всех исторических заданий или доступности внешнего API при отсутствии запроса. Ошибки бизнес-заданий сохраняются и видны отдельно.

## Пороги и восстановление

Общая функция `integrations.worker_health.process_health` используется supervisor, страницей и проверкой Docker. Пороги возраста успешного цикла: CRM-бот 120 с, цифровой/оптовый 180 с, Avito/Маркет/Google/печать 600 с, API цифровых цен 900 с. Отдельный исполнитель документов CRM-бота — 900 с. После первого подтверждения сохраняется окно стабильности 60 с.

Если процесс жив, но цикл не подтверждён, статус не становится «Работает». Для зависшего подтверждённого Linux-worker запрашивается только SIGTERM. Команда, UUID и время рождения сверяются по инвентаризации этой установки; `pidfd` защищает от повторного использования PID. Старые/неподтверждённые процессы не останавливаются. Принудительного SIGKILL нет, новый экземпляр не запускается до исчезновения старого. Длинная операция может продолжить штатное завершение; её нельзя автоматически повторять. Сохраняется предел трёх попыток и техническая пауза. Этот механизм не завершает процессы Windows.

## Загрузка контейнера

Страница и healthcheck сравнивают прочитанные отметки со временем окончания чтения
снимка. Иначе heartbeat, обновившийся во время SELECT, ошибочно считался бы отметкой
из будущего и давал ложный `unknown`. Явное тестовое время сохраняется без изменения.

Перед supervisor `container_runtime` выполняет `migrate --check` и `configure_worker_monitoring --new-boot`. Миграции при старте автоматически не применяются.

`--new-boot` под блокировкой supervisor сбрасывает только техническую паузу и незавершённое намерение запуска необходимых настроенных сервисов. Старые команды управления завершаются результатом `restart`. Бизнес-очереди и учётные данные не меняются. Отключённые и ненастроенные интеграции не включаются. При уже работающем supervisor сброс запрещён.

## Docker healthcheck и печать

`python manage.py check_worker_health` только читает локальные состояния и проверяет HTTP страницы входа на `127.0.0.1`. Новые задачи и запросы Telegram/Avito не создаются. Используется лёгкий снимок без истории очередей. Успех требует свежего supervisor, подтверждённых необходимых сервисов, связи с включёнными Print Agent и доступности их принтеров.

Compose: интервал 30 с, timeout 20 с, начальное окно 150 с, три неудачи до `unhealthy`. Docker healthcheck сам не перезапускает контейнер из-за внешней ошибки: восстановлением worker владеет существующий supervisor. Неверный токен не должен вызывать бесконечный перезапуск всей CRM.

`start_local_container.ps1` запускает настроенный Windows Print Agent через прежний скрипт с защитой от дублей и отдельно ожидает `healthy`. Доступность сайта и готовность обработчиков сообщаются отдельно. Если подтверждений нет, выводится предупреждение с указанием страницы «Интеграции → Обработчики».

При прямом запуске Docker Desktop Windows-агент не может стартовать внутри Linux. Сохраняется его автозапуск при входе в Windows. Отсутствие агента или принтера блокирует подтверждение готовности печати. Проверка не отправляет пробный стикер и не доказывает физическое качество печати.

## Применение и проверки

Если резервирование включено, healthcheck также требует свежую отметку существующего
`run_backup_worker` (до 900 с). Его независимый процесс по-прежнему запускает и
восстанавливает `container_runtime`. Отключённое резервирование не включается этой проверкой.

Миграция `integrations.0015_worker_functional_health` добавляет только технические поля. Перед рабочим применением нужна согласованная SQLite-копия в Docker с integrity/FK-проверкой и пробным восстановлением. Для изменения healthcheck нужен `docker compose up -d` с прежним Google override; одного `docker restart` недостаточно. База и ключи остаются в прежних bind mounts.

Регрессии описаны в `integrations/test_worker_health.py`, дополнены тесты supervisor и CRM-бота. По инструкции владельца suite при внедрении не запускаются. После старта проверяются новые UUID и свежие подтверждения всех процессов, успешный polling трёх ботов, цикл исполнителя документов, агент и Docker healthcheck. Искусственные сбои рабочих ботов, тестовые сообщения и пробная печать не выполняются.
