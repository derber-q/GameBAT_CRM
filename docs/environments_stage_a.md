# Этап A: режимы и тестовая CRM

Результат относится к **этапу A** общего контракта A–F. PostgreSQL, обновления,
Linux-worker, Print Agent и HTTPS-origin расширения ещё не реализованы.
Готовность к реальному хостингу не подтверждена: нужен выбранный VPS и этапы B–F.

## Режимы

| GAMEBAT_ENV | Поведение |
| --- | --- |
| Не задан / local_live | Прежние SQLite, ключи, пути, сессии, интеграции, принтер и сине-серая навигация |
| local_test | Отдельные данные, ключи, сессии, блокировки, оранжевая навигация; внешние эффекты запрещены |
| production | Распознаётся, но запуск явно запрещён до проверенного этапа B; fallback на рабочую SQLite невозможен |

Режим определяется серверным окружением до чтения секретов. DEBUG не выбирает режим.
GET, cookie и клиентский JavaScript не меняют настройки приложения.

В этой итерации production намеренно не является запускаемой серверной конфигурацией.
Нельзя применять к нему migrate/переносить данные. Проверка check --deploy и запуск
с фиктивными production-секретами относятся к этапу B и пока не выполнялись.

## Отдельный запуск на Windows

Рабочий ярлык и `start_localhost.ps1` не меняются. Рабочие процессы не нужно
останавливать. Новую тестовую CRM запускать из корня проекта:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\start_local_test.ps1 -Instance acceptance -Port 8001 -Initialize -NoBrowser
```

`-Initialize` мигрирует **только отдельную тестовую БД**, создаёт синтетический склад
и пользователя `test-admin`. Случайный пароль находится в
`outputs/local_test/acceptance/secrets/test-admin.json`; он не печатается в журнал.
Повторная инициализация не сбрасывает пароль и не очищает данные.
Никакая рабочая БД, пользователь, товар или ключ не копируется.

По отдельному прямому поручению от 31.10.2026 в instance `acceptance` затем
добавлены две учётные записи из основной БД: профили, существующие хеши паролей,
статусы и права. Источник открывался только для чтения, перед импортом сохранён
снимок тестовой БД. Документы, сессии и ключи интеграций не переносились; общий
запускатель по-прежнему ничего из основной БД не импортирует. Программные запреты
тестового режима не ослаблялись.

Обычный последующий запуск — без `-Initialize`. Если порт уже занят, запускатель
завершается с ошибкой и никого не останавливает. Порт 8000 запрещён, привязка — только
loopback. Запускатель ждёт HTTP-подтверждение `X-GameBAT-Environment: local_test`.
`--insecure` обслуживает локальную статику runserver при DEBUG=False только в тесте;
это не способ production-запуска.

Отдельный entry point не совпадает с сигнатурой рабочих процессов:

```powershell
.venv\Scripts\python.exe -m GameBAT_CRM.local_test check
.venv\Scripts\python.exe -m GameBAT_CRM.local_test migrate --check
```

Он очищает унаследованные рабочие настройки **в собственном дочернем процессе**.
Ни системное окружение Windows, ни работающий сайт не меняются. При прямом запуске
`GAMEBAT_ENV=local_test` без этого entry point обнаруженные переменные рабочих ключей
вызывают отказ, а не молчаливое наследование. Подмена `--settings` entry point запрещена.

## Пути, ключи и БД

`GAMEBAT_TEST_ROOT` разрешён только в отдельном подкаталоге `outputs/local_test/`.
Корень репозитория, protected_media, backups, символьные ссылки и перенаправления
каталогов не принимаются. Каталог без метки окружения обязан быть пустым.
Метку environment.json с UUID создаёт тестовый режим; чужой тип метки не принимается.

Внутри собственного каталога:

- test.sqlite3 и отдельная suite.sqlite3;
- media/, tmp/, logs/, workers/;
- secrets/django.key, integrations.key, storefront.key — новые случайные ключи;
- отдельные session/CSRF cookie с суффиксом UUID, отдельный cache namespace.

Рабочие fallback-файлы ключей не используются. Пустые настройки Sheets не превращаются
в рабочую таблицу по умолчанию. Ключи Яндекса и принтера указывают только внутрь
тестового secrets/, Google Service Account не задан. Утрата тестового ключа не
исправляется подменой рабочего.

Дополнительный CPython-guard запрещает открытие чужой SQLite независимо от имени,
включая URI, и запрещает ATTACH чужого файла для стандартных sqlite3.connect/
dbapi2.connect. Подмена БД ссылкой/жёсткой ссылкой отклоняется. Общая memory-БД
допускается только при настоящем mode=memory. Рабочие БД/ключи/медиа/backups
защищены также от обычного Python open. Прежняя защищённая резервная копия не затронута.

## Запрет внешних эффектов

Центральный `core.external_policy.require_live_operation` проверяет режим перед:

| Направление | Места проверки |
| --- | --- |
| Avito | Создание клиента, токен, request_json, транспорт |
| ReefAPI | Создание клиента и _post |
| Sheets | _google_service и sync_price_sheet до сохранения попытки |
| Яндекс | Чтение ключа, создание клиента, call, download_public до DNS |
| Курсы | Прямые fetch Rapira/Coinbase; шапка возвращает «недоступно» без сети |
| Ключи | Сохранение Avito/ReefAPI/Яндекс запрещено |
| Принтер | Настройка, print_pdf, Windows DC, StartDoc, spool-команды и проверка результата |
| Windows-процессы | Инвентаризация и запуск рабочего адаптера запрещены |

Даже явно переданный API key и инъекция transport не обходят проверку.
Необработанное специальное исключение в тестовом HTTP получает понятный ответ 403.
Ошибки не переводят выполнение на настоящий API как fallback.

Отдельно запрещены реальные webhook Яндекса, выдача живого контекста расширению и
запись найденной цены из живой очереди расширения. Ручная ссылка Avito в тесте
заменяется локальным якорем, интерфейс сообщает об отключении живого сценария.
Фиктивные события и бизнес-логику можно проверять изолированными тестами сервисов,
не через публичный рабочий webhook.

На уровне стандартного Python runtime блокируются DNS, исходящие socket, urllib,
subprocess, os.system/exec/kill/startfile и загрузка ctypes-библиотек. Прямой импорт
модулей Windows-печати запрещён. В частности, тестовый сервер не может обращаться
к живой CRM на loopback:8000.

В браузере действует CSP, запрещающий внешние connect/img/script/media и формы:
тестовые страницы не получают фотографии/скрипты из реальных аккаунтов.
Никаких настоящих API-ответов ради испытаний не запрашивалось.

## Мониторинг

Существующие таблицы, статусы, API, звук и алгоритм восстановления сохранены.
Тестовая БД независима. Политика A намеренно отключает реальные четыре сервиса;
их отсутствие не считается аварией. Рабочий Windows-адаптер и команды реальных
worker в тестовом entry point запрещены. Тестовый процесс имеет другое имя запуска
и не попадает в распознаватель live-supervisor.

Алгоритм восстановления проверяется фиктивным FakeProcesses на отдельной тестовой
БД, включая тест с local_test-политикой. Длительные моделируемые worker и Linux-адаптер
относятся к этапу D; их наличие в runtime этапа A не заявляется.

## Оранжевая навигация

Сервер подключает отдельный test-environment.css только для local_test. Основная
панель #B85C12, dropdown и мобильное меню согласованы по оттенкам. Метка
«ТЕСТОВЫЙ РЕЖИМ» сохраняется на обычных страницах, входе, Admin и витрине; внутри
мобильного диалога есть отдельная метка. Режим не окрашивает товары, денежные
поля и стандартные кнопки. local_live сохраняет прежние цвета.

## Инфраструктурная граница

Python audit hooks **не являются ОС-песочницей против произвольного враждебного
Python/C-кода**. Это прямо оговорено в
[документации Python](https://docs.python.org/3.14/library/sys.html#sys.addaudithook).
Нативный local_test предназначен для текущего доверенного кода CRM и искусственных
данных. Запуск непроверенного кандидата обновления/стороннего кода здесь запрещён.

Dockerfile и compose используют для CRM единственную internal-сеть с gateway mode
isolated, read_only, cap_drop ALL, no-new-privileges, непривилегированный UID и
отдельный named volume. Адреса моста в этой сети нет. Рабочий репозиторий, база,
media, ключи и Docker socket не монтируются.

Docker 29 не публикует порт контейнера, подключённого только к internal-сети.
Поэтому отдельный доверенный Nginx-прокси подключён к входной и internal-сетям;
он принимает запросы только на 127.0.0.1:8002 и передаёт их фиксированному
crm-test:8001. У него нет исходников CRM, тома с данными, ключей или произвольного
forward proxy. CRM не получает вторую сеть. Корень обоих контейнеров доступен
только для чтения, временные файлы находятся в /tmp. Версии базовых образов
закреплены digest. Это локальный тестовый runserver, а не production.
Для CRM включён init-процесс Docker: он передаёт SIGTERM серверу и позволяет
останавливать его без принудительного SIGKILL.

Перед сборкой создаётся отдельный контекст только из разрешённых исходников:

```powershell
.venv\Scripts\python.exe scripts/prepare_local_test_container.py outputs/test-container-build
docker build -t resource-local-test:stage-a outputs/test-container-build
docker build -f outputs/test-container-build/Dockerfile.ingress -t resource-local-test-ingress:stage-a outputs/test-container-build
docker compose -f deploy/local_test/compose.yaml config --quiet
docker compose -p resource-local-test -f deploy/local_test/compose.yaml up -d
.venv\Scripts\python.exe scripts/verify_local_test_container.py --project resource-local-test --live-ip 192.168.0.131
```

Сборка требует сети для базового образа/зависимостей, но не содержит рабочих данных.
Runtime-сеть не имеет внешнего маршрута. Проверка выхода выполняется **без импорта
Django**, чтобы отсутствие интернета не обеспечивалось одним программным флагом:

```powershell
docker compose -p resource-local-test -f deploy/local_test/compose.yaml exec crm-test python -c "import socket; socket.create_connection(('1.1.1.1',443),timeout=2)"
```

Ожидается ошибка соединения, а не успех. Проверить также DNS и доступ к живой LAN-CRM.
Не выполнять команды проверки до проверки состава контекста. Не добавлять CRM
вторую сеть/host network или широкие bind mounts. В --live-ip указывать текущий
LAN IPv4 рабочей CRM. Скрипт проверяет настройки Docker, отсутствие маршрута,
сырые TCP/DNS без Django, HTTP и невозможность использования входа как CONNECT-прокси.

Остановка сохраняет тестовую БД и ключи:

```powershell
docker compose -p resource-local-test -f deploy/local_test/compose.yaml stop
```

Не применять down -v, если нужно сохранить данные. Контейнерная база независима
также от Windows-instance acceptance: прежний импорт пользователей не переносится
в неё автоматически.

**Состояние проверки на 31.10.2026:** сборка, миграции отдельной SQLite, браузерный
вход/оранжевая навигация, запрет внешних TCP/DNS/LAN без Python-guard, права и
сохранение БД/ключей при перезапуске испытаны на Docker Desktop с Engine 29.8.0.
[Протокол](local_test_docker_acceptance_20261031.md). После приёмки контейнеры остановлены
по действующему пожеланию пользователя. Этапы B–F не выполнены, механизм допуска
кандидатов обновлений отсутствует. VPS не выбран; серверная готовность не подтверждена.
