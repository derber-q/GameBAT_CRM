## Исправления после реального запуска

Предыдущий compose публиковал 8002 непосредственно для CRM в единственной
internal-сети. Docker принял настройку, но NetworkSettings.Ports оставался пустым:
сайт был доступен только внутри контейнера. Такое поведение обсуждается
[в репозитории Docker Engine](https://github.com/moby/moby/discussions/53256).

Теперь CRM остаётся в одной internal-сети с gateway_mode_ipv4=isolated, без адреса
моста и внешнего маршрута. Отдельный доверенный Nginx принимает вход только на
127.0.0.1:8002 и передаёт запросы фиксированному crm-test:8001. Вторая сеть есть
только у прокси; исходников CRM, ключей и тома с БД у него нет. Произвольные URL
не выбирают upstream, CONNECT отклоняется. Общие настройки Docker, Firewall и
сеть рабочей CRM не менялись. Официальные описания:
[режим isolated](https://docs.docker.com/engine/network/port-publishing/),
[фиксированный proxy_pass](https://nginx.org/en/docs/http/ngx_http_proxy_module.html#proxy_pass).

Оба контейнера работают без привилегий, с cap_drop ALL, no-new-privileges,
корнем только для чтения и временными файлами в /tmp. Рабочая CRM Windows и её
данные не монтируются. Базовые образы Python и Nginx закреплены digest.

Первая попытка Nginx выявила дополнительные каталоги fastcgi/uwsgi/scgi в read-only
корне; все временные пути перенесены в /tmp. Исправлена и гипотеза проверочного
скрипта, что первый IP подсети всегда является мостом: в isolated-сети моста нет,
а первый IP может принадлежать самой CRM. Итоговая проверка требует отсутствия
gateway в Docker и маршрутах, проверяет недоступность моста отдельной входной сети.

Первая остановка Django с PID 1 завершалась SIGKILL (код 137). Для CRM включён
Docker init, после чего SIGTERM передаётся серверу: повторная остановка — код 143,
Nginx — код 0. Целостность SQLite и внешние ключи проверены на временной копии
после остановки; исходный named volume в проверочном контейнере смонтирован
только для чтения. Прямое открытие WAL-БД на полностью read-only томе потребовало
бы создания служебных файлов SQLite, поэтому проверяется копия в tmpfs.

## Итог и границы

Контейнерная проверка этапа A выполнена на этой машине. После испытаний оба
контейнера остановлены, named volume сохранён. Windows-сайт на 8001 не запускался.
Рабочие процессы не останавливались и не перезапускались; рабочая SQLite не
мигрировалась, реальные интеграции и печать не запускались.
При проверках этой сессии сайт на порту 8000 уже не слушал соединения; он не запускался
автоматически. Это отличается от исторического состояния предыдущего отчёта.

Это не проверка VPS и не выпуск production. PostgreSQL, обновления GitHub,
серверные worker и Print Agent остаются этапами B–F. Механизм допуска, сборки,
проверки происхождения и отката кандидатов обновления ещё не реализован.
Нативный Python-guard по-прежнему не считается ОС-песочницей для стороннего кода.
