# Рабочая локальная CRM в Docker

По прямому поручению пользователя рабочий сайт перенесён в контейнер с основной
db.sqlite3, а не независимым снимком. Режим local_live сохраняет обычные учётные
записи, пароли, права, цвета, медиа и ключи. Это локальный запуск текущей CRM;
production и готовность VPS этим не подтверждаются.

| Имя контейнера | Назначение | Адрес |
| --- | --- | --- |
| resource-crm-local | Рабочий сайт, основная БД | http://127.0.0.1:8000/ |
| resource-crm-test | Изолированный тестовый сайт | Через тестовый прокси |
| resource-crm-test-proxy | Фиксированный вход тестовой CRM | http://127.0.0.1:8002/ |

Для текущего Ethernet рабочий сайт также доступен на http://192.168.0.131:8000/.
Разрешённые LAN IPv4 определяет стартовый скрипт. При изменении адресов его нужно
повторить; для уже запущенного сайта использовать -Restart.

## Данные и процессы

Рабочий контейнер монтирует текущий каталог проекта в /app с правом записи:
основная SQLite, её WAL/SHM, protected_media и существующие файлы ключей остаются
на прежних местах Windows. Это доверенный рабочий контейнер с доступом к данным
установки. Тестовая CRM такого mount не получает: её прежний named volume,
сессии, ключи и закрытая сеть сохранены.

Образ рабочего контейнера содержит только Python и зависимости. В него не
копируются БД, секреты, медиа или репозиторий. Существующий внешний JSON Google
монтируется отдельным read-only файлом; его путь хранится в игнорируемом
outputs/local_container/google.compose.json, содержимое ключа в compose не записывается.

Windows-сайт и Windows-worker нельзя запускать одновременно с рабочим контейнером
на этой SQLite. [SQLite требует общего хоста для процессов WAL](https://sqlite.org/wal.html).
Перед запуском скрипт проверяет штатные нативные процессы этой установки и отказывает
при их наличии. Старый start_localhost.ps1 при активном resource-crm-local открывает
его адрес и не запускает нативный сайт, configure_worker_monitoring или worker.
Если после передачи БД состояние Docker проверить нельзя, старый ярлык отказывает
до обращения к Django. Метка владельца: outputs/local_container/owner.json.

Контейнер автоматически запускает сайт и контроллер. Контроллер поднимает
настроенные worker Avito, Яндекс Маркета и Google Sheets и восстанавливает их
после остановки. Это реальные очереди и обмен с площадками, включённые по прямому
поручению пользователя. Печать выполняет [Windows Print Agent](print_agent.md):
контейнер готовит очередь, агент получает задания и обращается к принтеру на
компьютере магазина. Состояния мониторинга не подменяются.

Страница [«Обработчики»](http://127.0.0.1:8000/crm/integrations/workers/) показывает
реальные heartbeat. Под superuser можно нажать «Запустить» у остановленного
или приостановленного обработчика либо «Восстановить все». Backend сохраняет
проверку прав, CSRF, идемпотентный UUID команды и проверку PID/времени создания.
При неизвестном статусе живого процесса дубликат не запускается. После трёх
неудач автоматика приостанавливается, ручная попытка остаётся доступна.

GameBAT_CRM.container_runtime управляет сайтом и контроллером в одной группе
процессов; доступ к Docker socket не нужен. Завершившийся контроллер запускается
повторно. При сбое сайта контейнер перезапускается по unless-stopped. Обычная
остановка docker stop остаётся остановкой, пока пользователь не запустит его снова.
SIGTERM прекращает получение новых заданий worker, давая завершить текущую операцию.
Родитель ждёт до четырёх минут; Docker даёт пять минут на остановку. При превышении
срока процесс завершается принудительно с сообщением в журнале: незавершённые задания
нужно проверить, особенно если результат внешнего запроса неизвестен.

Передача БД не применяет миграции: запуск сначала выполняет migrate --check и
отказывает при несовместимой схеме. Файлы ключей и основная БД обязательны;
пустая установка автоматически не создаётся.

## Сборка, запуск и остановка

Из корня проекта, в PowerShell:

```powershell
New-Item -ItemType Directory -Force outputs/local_container/image-context | Out-Null
Copy-Item requirements.txt outputs/local_container/image-context/requirements.txt
Copy-Item deploy/local_live/Dockerfile outputs/local_container/image-context/Dockerfile
Copy-Item deploy/local_live/.dockerignore outputs/local_container/image-context/.dockerignore
docker build -t resource-crm-local:current outputs/local_container/image-context
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\start_local_container.ps1 -NoBrowser
```

При первом запуске передать привычную GOOGLE_SERVICE_ACCOUNT_FILE, если она нужна
этой установке. Последующие запуски используют сохранённый read-only mount.
Повторный запуск принимает уже работающий контейнер. После изменения Python или
кешируемых шаблонов:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\start_local_container.ps1 -Restart -NoBrowser
docker stop resource-crm-local
```

Остановка не удаляет основную БД или медиа. Перед возвратом на Windows убедиться,
что resource-crm-local действительно остановлен; затем можно использовать прежний
ярлык. Нативные worker при этом включать только осознанно: они выполняют настоящие
внешние действия. Не переключать две установки параллельно.

Тестовые контейнеры сохраняют прежний compose-проект и том:

```powershell
docker compose -p resource-stage-a-20261031 -f deploy/local_test/compose.yaml up -d
docker compose -p resource-stage-a-20261031 -f deploy/local_test/compose.yaml stop
```

## Проверка передачи 31.10.2026

Перед стартом создан согласованный SQLite-снимок
backups/before_local_container_20261031_182051/ с отдельными ключами и 859
медиафайлами. Integrity/FK проверены. Защищённая прежняя резервная копия сохранена.
После старта все таблицы основной БД совпали с этим снимком; бизнес-записи,
пользователи, пароли и очереди при запуске не изменялись.

Отдельная искусственная SQLite на том же bind mount прошла проверку блокировки
двух Linux-процессов, commit и integrity_check. Это не гарантия совместной работы
с Windows-процессами; такая работа запрещена. Файловая система Windows также
может быть медленнее Linux volume, что описано в
[рекомендациях Docker Desktop](https://docs.docker.com/desktop/features/wsl/best-practices/).

Проверены HTTP 200 страницы входа через loopback и Ethernet, отсутствие тестового
заголовка/метки в рабочей версии и наличие метки в тестовой, check, отсутствие
новых миграций и безопасный повторный вызов старого ярлыка. Логи проверок находятся
в outputs/local_container/. Для реального хостинга остаётся обязательным план A–F.

Первый полный Linux-прогон не завершился успешно: SQLite-раннер Django не принял
стандартный forkserver Python 3.14; повторный прогон с fork остановился на импорте
win32print в существующих Windows-тестах печати. Полный Linux suite не считается
пройденным. Это подтверждает необходимость отдельного переноса печати; тесты
не отключались и бизнес-логика ради зелёного результата не менялась. Веб-образ
также намеренно не содержит Git: генерация справочников и проверки Git выполняются
на хосте, а не требуют установки инструментов разработки в рабочий контейнер.

## Включение обработчиков 31.10.2026

Перед включением создана новая согласованная копия с ключами и медиа:
backups/before_container_workers_20261031_155541/. Проверены integrity и внешние ключи.
Тестовые контейнеры в этой итерации не запускались и не перенастраивались.

Новые проверки сначала воспроизвели отсутствие управляющего процесса и ограничения
печати. Затем Linux-прогон core.test_container_runtime, integrations.test_linux_processes,
integrations.test_worker_monitoring, core.test_environments и core.test_external_isolation
завершился: 52 теста, OK, 15,954 с, код 0. Фиктивные процессы подтвердили перезапуск
контроллера и завершение его дочернего worker после текущей работы; внешние API в
этих тестах не вызывались. Отдельно проверены команды superuser, CSRF, отказ обычному
сотруднику, защита от дубликатов и ручное восстановление после лимита неудач.

Внутри рабочего контейнера запущены три настоящих интеграционных worker. Их
первоначальный статус «Восстанавливается» меняется на «Работает» только после
стабильных heartbeat; сам факт создания PID успехом не считается. Файлы журналов
worker остаются в outputs/localhost/, общие события — в docker logs resource-crm-local.
Протокол проверок текущей итерации: outputs/local_container/workers/.

После включения контроллер подтвердил три статуса running, у каждого failures=0;
печать имеет disabled. В Avito было пять заданий с ошибкой, обновлённых до старта
контейнера; новых ошибок на момент приёмки не было. Их не удаляли и не исправляли
массово. Браузерные проверки integrations.worker_browser_checks на отдельной БД:
2 теста, OK, 6,464 с, код 0. Основная БД в браузерных проверках не использовалась.
Обратная совместимость на Windows: 39 тестов, OK (один POSIX-тест пропущен),
1,050 с, код 0. Повторный запуск рабочего скрипта сохранил PID/время создания
контроллера и всех трёх worker; дубликатов не появилось.
