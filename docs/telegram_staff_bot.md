# Telegram-бот сотрудников: оптовый прайс наличия

Реализация от 02.11.2026. Приложение `telegram_bots`. Подключается только бот
с кодом `staff`. Контакты `User.telegram` и Telegram партнёров не импортируются.
Рабочие миграции применены с разрешения пользователя 02.11.2026, бот
`ReSOURSE_CRM_BOT` включён в локальной Docker CRM. Подробности:
[отчёт внедрения](telegram_staff_bot_report_20261102.md),
[порядок установки на другой экземпляр](telegram_staff_bot_installation.md).

## Инструкция для администратора и сотрудника

Администратор открывает «Интеграции → Telegram-боты» и нажимает «Разрешить бота»
для нужного сотрудника. В колонке «Оптовый прайс» должно быть «Разрешён».
Иначе в штатных правах пользователя/группы нужно выдать «Прайс: создание оптового
файла» (`price.generate_wholesale_price`). Разрешение бота само по себе не выдаёт
право формирования прайса. Администратор для собственного использования также
разрешает бота себе и выполняет привязку.

Сотрудник входит в CRM под своим аккаунтом и открывает «Интеграции → Telegram-боты»
(для администратора — кнопка «Мой Telegram»). Прямой путь:
`/crm/integrations/telegram/connect/`. Затем нажимает «Привязать Telegram»,
«Открыть бота и подключиться» и Start/«Запустить» в Telegram. Ссылка одноразовая,
действует 10 минут; если истекла, нужно создать новую в CRM.

После подтверждения привязки в личном чате с `@ReSOURSE_CRM_BOT` сотрудник нажимает
«Скачать оптовый прайс наличия», выбирает склад, если их несколько, и получает XLSX.
Кнопка расположена в постоянной панели у поля ввода, сохраняется после нажатия
и получения файла. Для повторного использования достаточно открыть чат бота;
меню вызывается `/menu`. После обновления со старого меню нужно один раз отправить
`/menu`, чтобы Telegram получил новую панель. Выбор склада остаётся под сообщением.
Основной компьютер с CRM, контейнер Docker и доступ в интернет должны работать.
Обработчик запускается supervisor автоматически, отдельное окно Python не требуется.

## Функция

В личном чате сотрудник открывает `/start`, `/menu` или `/help` и нажимает
«Скачать оптовый прайс наличия». При одном складе начинается формирование.
При нескольких — показаны реальные склады и «Назад». ID склада заново проверяется;
остатки разных складов не суммируются.

`documents.wholesale_document` вызывает прежний
`price.excel.generate_wholesale_price_xlsx(warehouse_id=…, actor=…,
partner_id=None, partner_name='')`. Новый файл строится в памяти при каждом
принятом запросе, без постоянного кэша. Имя: `ReSOURCE Price List Опт <дата>.xlsx`,
дата в часовом поясе Django. Формулы, отбор, группировки, новинки, фирменная шапка
и скрытый `_resource_meta` остаются ответственностью прежнего генератора.
При импорте возвращённого заполненного безымянного файла CRM запрашивает заказчика.

Бот не создаёт продаж, не резервирует/списывает товары, не меняет цены и не
запускает Avito, Маркет или Sheets. Сотрудник получает документ и пересылает его
заказчику самостоятельно. Размер ограничен 45 MiB; серверная настройка
`TELEGRAM_STAFF_MAX_DOCUMENT_BYTES`. Файлы не сохраняются в общедоступном каталоге.

## Устройство

| Компонент | Ответственность |
| --- | --- |
| `StaffBot` | Username, enabled, интервал, offset, диагностика, аренда получателя |
| `StaffBotAccess` | Единственная пара бот–сотрудник, допуск, числовой Telegram ID, привязка/отзыв |
| `StaffBotLink` | Только SHA-256 одноразового кода, срок и время использования |
| `StaffBotUpdate` | Уникальная квитанция `(bot, update_id)`, без полного сообщения |
| `StaffBotJob` | Сотрудник, склад, update, личный chat ID, фазы и итог отправки, без XLSX в БД |
| `configuration.py` | Ленивое чтение/атомарное сохранение секрета, запрет в local_test |
| `access.py` | Права, привязки и административный отзыв |
| `menu.py` | Реестр; пока только `wholesale_stock_price` |
| `handlers.py` | Проверка личного контекста, квитанция и постановка задания |
| `documents.py` | Адаптер прежнего Excel |
| `client.py` | Фиксированный Telegram API, конечные timeout, безопасные ошибки |
| `jobs.py`, `worker.py` | Исполнитель документов отдельно от long polling |
| `monitoring.py` | Читаемый снимок существующему мониторингу |

Маршруты: `/crm/integrations/telegram/` — superuser-настройки/допуски/журнал;
`/crm/integrations/telegram/connect/` — только собственная привязка сотрудника.
POST защищён CSRF, GET не обращается к Telegram. Токен никогда не показывается.
Обычный сотрудник не видит чужие ID, журнал и управление. Ответы со ссылками
не кешируются; `Referrer-Policy: same-origin` сохраняет CSRF обычных форм и
не передаёт контекст на внешний Telegram. Ссылки имеют `noreferrer`/`noopener`.

## Допуск и одноразовые ссылки

Для файла одновременно нужны активный User, включённый бот, явный
`StaffBotAccess.allowed`, действующая числовая привязка, Django permissions
`telegram_bots.use_staff_bot` и `price.generate_wholesale_price`.
«Разрешить бота» добавляет первый permission и явный допуск. Право формирования
прайса выдаётся отдельно через штатные права/группы. Даже superuser должен быть
явно допущен и привязан.

Сотрудник входит в CRM и получает ссылку на 10 минут. Администратор также может
выдать её из своей таблицы. Случайный base64url-код длиной 43 символа передаётся
в `/start`, в БД хранится только SHA-256. Новый код отменяет прежние; повторный
или истёкший не принимается. Telegram ID берётся из подтверждённого события
Telegram, chat должен быть личным и иметь тот же ID. Username — лишь подпись.

Один Telegram ID нельзя связать с двумя сотрудниками одного бота. Для замены
аккаунта администратор сначала отключает привязку. «Отключить и отвязать» отменяет
допуск, ссылки и числовую связь; повторное разрешение требует новой ссылки.
Коды, токен и полный входящий payload не журналируются.

Свежие permissions и привязка проверяются перед генерацией и перед отправкой.
Отзыв во время генерации блокирует выдачу. Начатую HTTP-отправку уже невозможно
отозвать задним числом.

## Очередь и восстановление

Квитанция update, offset и задание сохраняются одной транзакцией с блокировкой
бота. Уникальность защищает от повторного update и от двух активных заданий
сотрудника. На SQLite сохранён IMMEDIATE и `core.db_retry`. Сеть — после commit.
Начальный интервал новых запросов — 30 секунд, в форме доступно 5–3600 секунд.

Фазы: `queued → generating → sending → done`, либо `error`/`uncertain`.
`sending` фиксируется **до** API. HTTP-клиент не повторяет файл при timeout/обрыве
или неизвестном серверном ответе. После аварии `sending` становится `uncertain`,
прерванная генерация — `error`; автоматической повторной отправки нет. Сотрудник
проверяет чат и при необходимости создаёт новый явный запрос.

Polling и исполнитель работают в разных потоках с разными соединениями к БД и
HTTP-сессиями. Долгое построение Excel не задерживает приём updates. SIGTERM/SIGINT
прекращает новые запросы; начатая отправка завершается с конечным timeout.
Сохранять существующий пятиминутный grace period контейнера.

## API и мониторинг

Используется [официальный Bot API](https://core.telegram.org/bots/api):
`getUpdates`, `sendMessage`, multipart `sendDocument`, `answerCallbackQuery`.
При явной проверке/старте — `getMe` и `getWebhookInfo`. Автоматических
`setWebhook`/`deleteWebhook` нет. Существующий webhook блокирует polling.
Получаются только `message` и `callback_query`. Polling timeout — 20 секунд,
HTTP connect — 5, read — 30 для получения, 12 для коротких операций и 65 для файла.
Адрес фиксирован: `https://api.telegram.org`, редиректы отключены. Исключения
содержат категорию без URL с ключом и без тела ответа. Используется уже имевшийся
`requests`, новых зависимостей нет.

`telegram_staff` — пятый сервис прежнего supervisor: те же heartbeat, PID/birth/
instance, три попытки запуска, ручное восстановление, «Восстановить все» и звук.
Файловая блокировка дополнена арендой общей БД на 180 секунд. Аренда обновляется
при polling/приёме и проверяется перед отправкой. Несвязанные копии БД не образуют
общую распределённую блокировку: при переносе обязательно выключить старую.

Ошибка API не объявляет живой процесс исчезнувшим. После трёх последовательных
ошибок обращения приостанавливаются; conflict, неверный токен/username и webhook
блокируют сразу. Диагностика показана на странице бота и в мониторинге. Для нового
подключения исправьте причину, выключите бота, дождитесь выхода и включите снова.
Нет токена — «Не настроен»; выключен — «Отключён». Это не аварии. Мониторинг
проверяет только наличие источника, не читает секрет и не проверяет API.

## Секрет и режимы

Приоритет: `GAMEBAT_TELEGRAM_STAFF_BOT_TOKEN`, затем локальный
`.telegram-staff-bot-token`. CRM не загружает `.env` автоматически. Форма сохраняет
файл атомарно с 0600 на поддерживающей ОС; Windows также использует ACL каталога
пользователя. Файл игнорируется Git, запрещён repository checker даже при `add -f`
и исключён из Docker-образа. Локальный контейнер получает его через прежний `/app`
bind. Для Linux с read-only root используйте смонтированный секрет/окружение;
путь задаётся серверной настройкой `TELEGRAM_STAFF_TOKEN_FILE`, не HTTP-параметром.

Сохранение токена не вызывает сеть. Перед его заменой/сменой username выключите
бота и дождитесь выхода. «Проверить подключение без сообщений» — отдельная явная
кнопка администратора. Не отправляйте секрет через параметры командной строки.

В `local_test` только заглушка «Тестовый режим. Взаимодействие с Telegram отключено.»
Файл/переменная не читаются, клиент/worker заблокированы, сервис disabled.
Наследуемая live-переменная добавлена в запрещённые секреты окружения; штатный
test entry point её очищает. Audit guard запрещает рабочий файл токена. Сетевая
политика не ослаблена. Production по-прежнему закрыт до этапа B.

После согласованной установки настроенного бота запускает прежний supervisor.
`-SiteOnly` сохраняет прежнюю семантику. Ручная диагностика только при остановленном
другом получателе: `.venv\Scripts\python.exe manage.py run_telegram_staff_bot`.
Будущий Linux: `python manage.py run_telegram_staff_bot`. Linux-адаптер поддерживает
команду, бизнес-логика не зависит от Windows; production/PostgreSQL этим не объявлены
проверенными. Порядок переноса — в плане установки.

## Проверки

`manage.py test telegram_bots integrations.test_worker_monitoring integrations.test_linux_processes --noinput`
проверяет права, коды, повторы/конкуренцию, свежий Excel/импорт, размер, неизвестную
отправку, независимость polling, блокировки и восстановление. Транспорт фиктивный.
`manage.py test telegram_bots.browser_checks --settings=sales.system_browser_settings --noinput`
проверяет формы Chromium на отдельной SQLite и блокирует всю внешнюю сеть.
Настоящую выдачу файла подтверждать отдельно с разрешённым сотрудником.
