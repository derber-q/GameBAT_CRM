# Цифровые продажи: установка и работа сотрудников

Этот документ относится к исходникам новой функции. Само наличие файлов не
означает, что миграции рабочей БД применены или получатель Telegram включён.
Применение к рабочей CRM и перезапуск требуют отдельной команды владельца.

## Перед установкой

1. Не запускать второй polling для токена цифрового бота. Существующий бот
   сотрудников продолжает работать со своим токеном и offset.
2. Создать согласованный SQLite-снимок штатным механизмом резервирования, проверить
   integrity/FK и пробное восстановление в отдельную БД. Сохранить защищённую
   `backups/current_state_20261031.sqlite3`.
3. Сохранить существующие секреты отдельно от Git. Миграции не меняют старые
   суммы/себестоимости продаж и не переносят историю переписки в рабочую БД.
4. Просмотреть `manage.py migrate --plan`. Новые миграции:
   `sales.0036_alter_sale_payment_method_alter_sale_sale_type_and_more`,
   `digital_sales.0001_initial`, `digital_sales.0002_supplierpurchase_superseded_by`,
   `integrations.0012_alter_workercommand_service_alter_workerservice_code`.
5. После согласования выполнить `migrate --noinput`, затем `check`, `verify_cash`,
   `verify_inventory`. Обновлённые web/supervisor/бот сотрудников должны загрузить
   новый код; отдельный получатель цифрового бота запускается прежним supervisor.

## Ключ и токен

Явная подготовка на сервере (не передавайте сам токен аргументом команды):

```powershell
.venv\Scripts\python.exe manage.py configure_digital_sales --initialize-key
.venv\Scripts\python.exe manage.py configure_digital_sales --token-source "C:\защищённый-каталог\bot.txt"
```

Команда не включает бота, не получает сообщения и не меняет деньги. Уже
существующий ключ/токен не перезаписывается. По умолчанию используются
`.digital-sales-key` и `.telegram-digital-bot-token`, исключённые из Git.
Они не попадают в образ local_live: образ содержит зависимости, код/данные
подключаются прежним bind mount. В другом развёртывании используйте явные секреты.

Поддержаны переменные процесса:

| Настройка | Назначение |
|---|---|
| `GAMEBAT_DIGITAL_SALES_KEY` | Fernet-ключ вместо файла |
| `DIGITAL_SALES_KEY_FILE` | Серверный путь к исходному Fernet-ключу |
| `GAMEBAT_TELEGRAM_DIGITAL_BOT_TOKEN` | Токен нового бота вместо файла |
| `TELEGRAM_DIGITAL_TOKEN_FILE` | Серверный путь к файлу токена |
| `DIGITAL_SALES_CRM_URL` | Доступный сотрудникам адрес CRM для ссылок бота |

`.env` не загружается автоматически. Для телефона адрес `127.0.0.1` указывает на
сам телефон: задайте доступный LAN/HTTPS-адрес CRM. В развёрнутом окружении для
просмотра аккаунтов нужен HTTPS. `local_test` не наследует рабочие секреты и не
запускает настоящий polling.

Локальный `start_local_container.ps1` передаёт в Compose адрес первого найденного
LAN-интерфейса через `GAMEBAT_LOCAL_CRM_URL`; контейнер использует его как
`DIGITAL_SALES_CRM_URL`. Если LAN-интерфейс отсутствует, применяется localhost.
При смене сети повторите запуск скрипта, чтобы обновить адрес в ссылках бота.

Ключ товара не хранится в записи БД и никогда не создаётся автоматически вместо
потерянного. Сохраните его отдельную защищённую копию до первой закупки.
Полный зашифрованный CRM-архив включает эффективный ключ в отдельном
`recovery/secrets.json`, защищённом ключом владельца архива. Проверка полного
архива расшифровывает `digital_sales_suppliermessage.encrypted_payload` именно
цифровым ключом, а не ключом интеграций. Одной незашифрованной копии SQLite для
восстановления цифровых товаров недостаточно.

## Чат поставщика

1. В BotFather включить Bot-to-Bot Communication Mode у цифрового бота.
2. В нужной группе либо выдать боту административные права, либо отключить Group
   Privacy Mode и при необходимости добавить бота заново. Сам факт членства не
   гарантирует получение сообщений другого бота.
3. Узнать числовые ID группы и отправителей. Username — подсказка, а не ключ учёта.
   Пока получатель выключен и аренда освобождена, доступна команда:

```powershell
.venv\Scripts\python.exe manage.py discover_digital_chat --sender SupplierExampleBot --sender SupplierEmployee
```

Она не подтверждает offset, не отправляет сообщения и выводит только ID/username
из ожидающих событий. Telegram не предоставляет произвольную старую историю
чата; при отсутствии событий нужно дождаться нового сообщения. Отключённый режим
privacy/bot-to-bot может мешать и этой диагностике.

4. Открыть «Контрагенты → Баланс цифровых продаж → Настройка бота»:
   `/crm/digital/configuration/`. Создать поставщика с отрицательными chat ID и
   положительными ID разрешённых отправителей. Не добавлять посторонние чаты.
5. Нажать «Проверить подключение без сообщений». Проверяются личность, наличие
   webhook, privacy и статус участника в разрешённых группах. Существующий webhook
   автоматически не удаляется. Bot-to-Bot Mode проверяется отдельно в BotFather.
6. После согласованного включения проверить счётчики обычных, bot и forwarded
   сообщений, последний chat ID, успешный приём после перезапуска. Они подтверждают
   только реально полученные события; пропущенную Telegram историю CRM не выдумывает.

Входящее сообщение ограничено 32 KiB; одно вложение — 5 MiB. Вложения скачиваются
только с фиксированного Telegram API, шифруются и хранятся вместе с оригиналом в БД.
Ошибка вложения видна в карточке и мониторинге; сотрудник может повторить получение.
Пока нужное вложение не сохранено, автоматического запроса оформления нет.

## Права и сотрудники

Обычные Django permissions выдаются через существующих пользователей/наборы прав.
Новая функция не выдаёт их всем автоматически.

| Действие | Новое право, помимо штатных прав Sale |
|---|---|
| Просмотр страницы/заказов | `digital_sales.view_digital_sales` |
| Создание/общий черновик | `digital_sales.create_digital_sales` + `sales.create_sale` |
| Оформление в Telegram | `digital_sales.telegram_digital_sales` + права создания |
| Завершение | `digital_sales.complete_digital_sales` + `sales.mark_sale_paid` |
| Отмена | `digital_sales.cancel_digital_sales` + `sales.cancel_sale` |
| Покупатели | `digital_sales.manage_digital_buyers` |
| Пополнение | `digital_sales.topup_digital_balances` |
| Начальный остаток/корректировка | `digital_sales.adjust_digital_balances` |
| Расшифровка оригиналов/файлов | `digital_sales.view_digital_secrets` + просмотр |
| Сверка поставщика | `digital_sales.view_digital_reconciliation` |
| Настройка получателя/чата | `digital_sales.configure_digital_bot` |

Сотруднику нужна прежняя активная привязка к `ReSOURSE CRM BOT`, явный
`StaffBotAccess.allowed` и `telegram_bots.use_staff_bot`. После обновления один раз
отправить `/menu`: на постоянной панели появятся «Цифровые продажи» при наличии прав.

Чек-лист сразу вызывает интерактивную карточку, но сам по себе не создаёт продажу:
для окончательного подтверждения должен быть связан готовый товар. Обычное
обновление статуса того же чек-листа без изменения состава, суммы и номеров не
требует ручной перепроверки закупки; прежние замечания об ожидающем статусе снимаются
после его подтверждения. Ожидающая оплата поставщику допустима: отрицательный баланс
разрешён, а отметка оплаты сохраняется в исходном сообщении/результате разбора.
Все уполномоченные привязанные сотрудники получают карточку. Покупатель и
цена общие; устаревшая версия формы не перезаписывает чужие изменения. В Telegram
можно выбрать/создать покупателя, указать общую цену и подтвердить создание одной
незавершённой Sale. Покупателя и цену можно заполнить в любом порядке и заранее;
кнопка подтверждения появляется после заполнения обоих полей и готовности товара.
`/menu` и `/cancel` прекращают ожидающий ввод. Повторное подтверждение не создаёт дубликат. Секреты в карточку
бота не включаются. После изменения статуса сохранённые карточки обновляются
через `editMessageText`; если исходное сообщение удалено, ошибка видна в outbox.

## Веб-сценарий и учёт

На странице балансов доступны покупатели, пополнения/корректировки, заказы,
наблюдения поставщика, движения и ручное создание. Привязка покупателя к Partner
необязательна и не создаёт долг/кредитора автоматически.

Ручная форма принимает строки `Название | себестоимость RUB | номер поставщика`;
последний столбец необязателен. Общая цена одна, с точностью до копейки. Данные
аккаунта сохраняют исходные переводы строк и не возвращаются в HTML при ошибке
формы. Дополнительные комплекты можно сохранить в карточке всего заказа.

Номера поставщика уникальны в пределах поставщика, в том числе после отмены.
Совпадающее Telegram-событие прикрепляется к прежнему заказу; пересечение части
группы с оформленной Sale требует проверки. Если ручная продажа не имела номера,
сотрудник может явно связать цифровые заказы. Совпадающие закупки не удаляются:
дубликат помечается `SupplierPurchase.superseded_by` и исключается из контрольной
суммы. Название игры само по себе не является доказательством совпадения.

При неоднозначности доступны просмотр оригиналов по отдельному праву, ручная
связь сообщения/заказов и подтверждение проверки с причиной. До создания Sale
можно явно уточнить нераспознанный состав; после создания снимки Sale не заменяются.
Просмотр секретов — только POST с CSRF, no-store и записью `AuditEvent`.

Завершение выполняет одной транзакцией проверку текущих прав и состава,
полное списание с покупателя и себестоимость с внутреннего счёта поставщика.
Оно одновременно фиксирует оплаченный/доставленный статус Sale. Незавершённые
продажи баланс не резервируют. Два параллельных завершения сериализуются SQLite
IMMEDIATE и блокировками владельцев. Балансы покупателя и поставщика могут быть
отрицательными: завершение списывает полную цену и себестоимость независимо от
доступного остатка. Минус означает задолженность владельца счёта. Начальный остаток
и корректировка допускают отрицательные суммы, пополнение остаётся положительным.
Бот распознаёт отрицательный баланс поставщика в отдельном снимке и чек-листе.
Отмена возвращает ровно списанные суммы; другие движения по счетам сохраняются.
Новый кассовый приход и долг в общем реестре кредиторов при этом не создаются.

Для покупателя из базы карта обозначает классификацию использования ранее внесённых средств. Нового
банковского/кассового прихода нет. В общей статистике выручка и прибыль считаются
по снимкам `SaleCustomItem`, а «новые фактически полученные деньги» равны нулю.
CD/Tech, остатки, рейсы и складская cost не участвуют.

Вариант «Розничный покупатель» доступен без создания счёта. Выберите его в боте,
укажите цену и нажмите «Создать продажу»: продажа сразу оплачена картой и завершена.
Здесь цена является новым банковским поступлением в статистике; баланс покупателя
не используется. Счёт поставщика уменьшается на закупочную стоимость однократно.
Для этого нужны права создания и завершения цифровой продажи и отметки оплаты.
Кнопка создания видна всегда, но неполный или требующий проверки заказ сервер
создать не позволит. Кнопок создания покупателей и перехода в CRM в карточке бота
больше нет; справочник покупателей редактируется только через CRM.

Для покупателя с цифровым балансом новая продажа сразу получает «Доставлен» и
«Не оплачен»: товар уже выдан, но оплата ещё не подтверждена. До подтверждения
движений балансов нет. В таблице незавершённых цифровых продаж доступен обычный
переключатель оплаты, если сотруднику разрешены `sales.mark_sale_paid` и
`digital_sales.complete_digital_sales`. Выбор «Оплачен» с подтверждением вызывает
цифровой `complete_sale`: списывает цену с покупателя, себестоимость с поставщика
и переносит продажу в завершённые. Остаток может стать отрицательным. Поле новых
полученных денег и взаимозачёт обычного партнёрского долга здесь не используются.
Повторная оплата не создаёт повторных списаний. Статусы существующих продаж
автоматически не переписываются; их оплата также завершает цифровую продажу.

Отмена штатной `sales.services.cancel_sale` направляет новый тип в цифровое сторно.
Обе исходные записи остаются; добавляются обратные движения с `reversal_of`.
Повторная отмена ничего не возвращает повторно. Внешние снимки не переписываются:
отмена в CRM не подтверждает возврат денег поставщиком. При необходимости
создаётся уведомление о сверке.

## Сверка и восстановление связи

Закреплённые балансы и копии в группах покупателей:
[привязка, очередь и восстановление](digital_sales_chat_balances.md).

Внешний сообщённый остаток — `BalanceObservation`. Внутренний остаток — сумма
`BalanceMovement`. Контрольный ожидаемый остаток учитывает закупки поставщика,
даже пока Sale не завершена. Завершение Sale не уменьшает внешнее наблюдение.
Первый достоверный снимок задаёт начальную точку, если ручной учёт ещё не начат.
Опоздавшие/непроверенные пересылки помечаются неопределёнными, а не превращаются
в выдуманную хронологию. Совпадение разницы с ценой другой покупки не считается
объяснением само по себе.

Outbox сохраняется до сети. При отказе Telegram заказ не теряется. Определённый
rate limit повторяется ограниченно; timeout/неизвестный исход требует проверки
чата и явного повтора в интерфейсе. Незавершённая отправка после перезапуска
помечается uncertain. Уже созданная Sale от повторной отправки не дублируется.

Настройка бота не отправляет тестовые сообщения в чат поставщика. Проверки
программного кода используют синтетические updates и транспорт; работу настоящей
группы необходимо подтверждать отдельно после согласованной установки.
