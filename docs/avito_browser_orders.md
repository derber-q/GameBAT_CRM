# Заказы Avito в расширении Opera / Chromium

Дата внедрения: 01.11.2026. Исходники расширения — `browser_extensions/avito_check`, версия 1.6.1.

## Сценарий сотрудника

На странице Avito «Заказы и заявки» расширение добавляет к продавцовским строкам
кнопки «Создать продажу» и «Напечатать отправительный код». Распознаются реальные
`data-marker="order-row"`, статус, заголовки изображений и ссылка `/orders/<id>`.
Номер заказа передаётся строкой: он может превышать точность JavaScript Number.
Кнопка отправительного кода отсутствует для «Самовывоз», общего «Доставка»,
доставки силами продавца и «Достависта»/Dostavista; создание продажи доступно. Остальные службы
(Почта России, Яндекс Доставка, СДЭК и другие) сохраняют печать. При изменении
способа в уже показанной строке доступность кнопки обновляется.

Создание открывает обычную форму CRM. До её сохранения не создаётся Sale,
не меняются склад, деньги или долг. В форме можно изменить состав и количество,
добавить товар, применить скидку и выбрать оплату. По умолчанию выбраны тип «Авито»,
цена Avito и банковская постоплата — продажа остаётся незавершённой.

Точный заголовок уже привязанного объявления помогает подобрать товар CRM.
Если совпадение отсутствует или неоднозначно, карточка товара не создаётся и
случайное совпадение не подставляется. Отсутствующие строки сотрудник добавляет
сам. Число штук каждого товара в списке Avito не известно: подставленное 1 надо
проверить. Сумма из списка показывается справочно, цены берутся из CRM.

После сохранения в строке Avito отображается ссылка `SALE-…`. Связь хранится
в БД, поэтому сохраняется между вкладками и перезапусками браузера. Ключ заказа,
OneToOne с Sale и транзакция защищают от двойного списания при повторе сохранения.
Отменённая связанная продажа остаётся связанной; новая автоматически не создаётся.

## Фото и фон строки (1.6.1)

`order-presentation.js` добавляет увеличенные фото с названиями из `img.alt`.
Исходный блок фотографий сохраняет свои размеры в потоке, но становится невидимым;
новый абсолютный блок располагается в свободном месте справа. Поэтому высота строки
с существующими кнопками CRM не меняется. `ResizeObserver` пересчитывает доступную
ширину/высоту; соседние управляющие элементы учитываются, а при недостатке места
сохраняется исходный блок. Фото ограничено высотой 108 px, название — двумя строками
и tooltip; несколько товаров прокручиваются горизонтально внутри этого же блока.
Источник картинки и переход на заказ берутся из исходной страницы, произвольные
товары/ссылки не придумываются. DOM меняется только для продавцовских строк.

`orders.css` задаёт фон с приоритетом сверху вниз:

| Условие | Состояние | Фон |
| --- | --- | --- |
| Заказ Avito или связанная продажа CRM отменены | cancelled | `#fde8e8` |
| Успешный lookup подтвердил отсутствие связанной продажи | unlinked | `#fff1de` |
| Есть продажа; «Едет к покупателю» или «Ждёт/Ждет выдачи покупателю» | transit | `#edf8ee` |
| Есть продажа; «Получите оплату» | payment | `#eaf3ff` |
| Есть продажа; остальные продавцовские статусы, включая «Отправьте заказ» | ready | `#ffffff` |

До первого ответа CRM состояние связи неизвестно: оранжевый фон не выставляется
по одному отсутствию ответа. При последующей ошибке сохраняется последнее известное
состояние. Смена статуса/фото/названия в Avito и возврат от команды CRM обновляют
представление; окраска не проводит операции и не меняет внешние статусы.

## Управление связанной продажей (1.6.0)

В строке заказа показаны отдельные поля «Доставка CRM» и «Оплата CRM». Расширение
получает текущие значения, подписи, разрешённый следующий статус и версию
`Sale.updated_at` через lookup. Состояния без соответствующих прав отображаются
без возможности изменения; без права просмотра статусы не передаются.
Завершённые продажи требуют `sales.view_completed_sales`, остальные —
`sales.view_sales`. Общий вход в bridge по-прежнему требует `sales.create_sale`.

Доставка меняется последовательно: created → assembled → delivered,
через `advance_order_status` и право `sales.advance_order_status`.
Оплата меняется unpaid → paid, через `mark_sale_paid` и право
`sales.mark_sale_paid`: подтверждается полная актуальная сумма продажи по её
сохранённому способу оплаты. Произвольная сумма, частичный расчёт и изменение
способа оплаты остаются в штатной форме CRM. Подтверждение наличных создаёт
штатное кассовое движение; банковская постоплата не пополняет кассу.

Кнопка «Удалить продажу» по уточнению владельца означает штатную отмену
`cancel_sale`, а не физическое удаление. Нужны `sales.cancel_sale`, подтверждение
и причина до 2000 символов. Сервис возвращает фактически списанный товар,
сторнирует собственные деньги/долг и сохраняет историческую запись, снимки и
привязку. После отмены отображаются красный статус и ссылка с пометкой «отменена».
Все прежние ограничения сервиса (снимки себестоимости, достаточность наличных
для возврата, права на долговой расчёт) продолжают действовать.

Обе команды принимают только строковый `order_id`, находят связанную продажу в
БД и не используют клиентский `sale_id`. Под блокировкой проверяются версия,
тип Avito и допустимость операции. Устаревший запрос возвращает 409 без повторного
платежа/возврата. После сетевой ошибки интерфейс сверяется с CRM; повторного
проведения вслепую нет. Меняется только связанная продажа CRM: внешний заказ,
его оплата и доставка на Avito автоматически не меняются.

Цвета не дублируются в расширении: сервер передаёт локальный доверенный
`static/css/sales-list.css`, Shadow DOM применяет те же классы `sale-status-*`.
CSS кешируется в Python-процессе, после изменения файла нужен перезапуск сайта.
Неизменившийся lookup не пересоздаёт поля и не сбрасывает открытый диалог.

## Отправительный стикер

По нажатию расширение сначала проверяет уже открытые вкладки именно этого заказа.
Если исходный код найден, он используется без изменения вкладки. Иначе создаётся
фоновая пустая вкладка, к которой подключается `chrome.debugger`. До перехода
на мобильный заказ задаются Android User-Agent вместе с `userAgentMetadata`,
экран 412×852 и сенсорный ввод. Это полноценная эмуляция телефона: одной подмены
UA-заголовка главного запроса, использовавшейся в 1.5.0, недостаточно для мобильных
проверок JavaScript и Client Hints. Прочитанный источник —
`/web/1/barcode/generate`. В блоке `finally` отладчик отключается и созданная
вкладка закрывается даже при ошибке; уже открытые вкладки не закрываются.
Обычные вкладки, cookies и безопасность соединения не меняются.
Разрешение `debugger` шире обычного доступа к страницам; код использует только
три команды Emulation для собственной временной вкладки. Не выполняются команды
ввода, обход защиты, отключение предупреждений или доступ к другим вкладкам через
отладчик. Браузер может показать штатное уведомление о подключении отладчика.
API: [chrome.debugger](https://developer.chrome.com/docs/extensions/reference/api/debugger),
[команды Emulation](https://chromedevtools.github.io/devtools-protocol/tot/Emulation/).
Для подтверждённого Code 128 воспроизводятся тип `128` и точное содержимое
параметра `content`, включая ведущие нули. Номер из списка или номер продажи
не используются как предполагаемый штрихкод. Для других типов исходного
символа принимается изображение PNG/JPEG этого же генератора Avito.
Неизвестная разметка, отсутствие исходного кода или отказ получения изображения
останавливают печать с сообщением сотруднику.

CRM создаёт PDF 58×40 мм с исходным символом и названием перевозчика под ним.
Изображение проходит ограничение размера и декодирование PIL; HTML/SVG и
произвольные удалённые URL сервер не загружает. PDF хранится в защищённых медиа.
Кнопка ставит задание без браузерного диалога печати. Поддерживаются штатный
Windows worker и существующий Print Agent, в том числе при CRM в Docker.

Отправка в spooler не означает успешную печать. Состояние `done` выставляется
после подтверждения Windows/агента. При неопределённом результате повторная
печать автоматически не производится; повторный запрос возвращает прежнее
неопределённое задание. Нужна проверка сотрудником. Печать не меняет оплату,
остаток или статус заказа на Avito и не вызывает готовность Яндекс Маркета.

## Границы доступа

Расширение использует отдельную открытую вкладку `/crm/sales/avito-extension/`,
вход сотрудника и CSRF. Нет CORS, API-ключа CRM в Avito или `externally_connectable`.
Background принимает сообщения только своих content scripts из главного frame
разрешённых HTTPS-хостов Avito. CRM проверяет `sales.create_sale`; в `local_test`
живой сценарий блокируется. Привязка к заказу и печать доступны сотрудникам с
этим правом; внешние пользователи/покупатели доступа к ним не получают.

Перед действием background проверяет отдельным `resource-orders:ping` готовность
приёмника и CSRF-поля во вкладке связи. После перезапуска расширения существующий
content script теряет контекст: в этом случае один раз перезагружается только
фиксированный `/crm/sales/avito-extension/` на том же разрешённом origin.
Ожидание готовности общее для параллельных запросов строк. Бизнес-действие до
готовности не отправляется. Вкладка входа не перезагружается циклически: сотруднику
показывается просьба войти. Ошибка связи в строке удаляется после успешного lookup,
не затирая сообщений текущей печати. Связи с продажами читаются из БД заново.

В БД хранятся только идентификатор заказа, заголовки товаров, справочная сумма,
перевозчик, автор, ссылка на продажу и задания печати. Полный DOM, cookies,
переписка и данные покупателя не импортируются. Присланные страницы не входят
в Git или технические справочники.

## Файлы и проверки

- `sales/avito_order_models.py`, миграция `sales.0035_avito_browser_orders` — новые таблицы без пересчёта истории.
- `sales/avito_orders.py`, `avito_order_views.py` — подготовка, lookup и форма продажи.
- `sales/avito_sale_controls.py`, `browser_extensions/avito_check/order-controls.js` — права, статусы, подтверждения, отмена и действующая палитра CRM.
- `browser_extensions/avito_check/order-presentation.js`, `orders.css` — фото, подписи, геометрия и фоновая индикация строк.
- `sales/avito_shipping.py` — PDF, очередь и обработка подтверждений.
- `sales/print_agents.py`, `print_agent_views.py` — подключение новой очереди к действующему протоколу агента.
- `browser_extensions/avito_check/orders*.js` — извлечение страницы, bridge и кнопки.
- `sales.test_avito_orders`, `sales.test_print_agents`, `sales.test_market_scanning`, `sales.test_label_printing` — проверки без реальных API и оборудования.
- `sales.avito_orders_browser_checks` — настоящее MV3-расширение в Chromium с искусственными страницами Avito. Код в fixture появляется только при мобильных navigator/Client Hints, viewport и touch; проверяются создание очереди, закрытие временной вкладки и сохранение desktop-окружения исходной страницы.
- `browser_extensions/avito_check/test_orders_background.cjs` — дополнительно проверяет повторное использование открытого кода, ведущие нули и освобождение временной вкладки/отладчика при ошибке эмуляции.

После обновления исходников надо перезагрузить расширение в `opera://extensions`,
затем обновить вкладки Avito и CRM. Физическое сканирование распечатанного стикера
в пункте перевозчика не заменяется серверными или браузерными тестами.
