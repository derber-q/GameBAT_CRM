# Балансы цифровых покупателей в Telegram

## Текущее поведение — 07.11.2026

Один цифровой `Buyer` связан с одной явно выбранной группой. При изменении
его баланса цифровой бот отправляет новое сообщение в конец чата:

`Текущий баланс на 07.11.2026 15:00: +1 250,00 ₽`

Прежние сообщения не редактируются, не удаляются и не закрепляются.
Знак выводится всегда, включая `+0,00`; минус означает долг покупателя.
Дата и время — Москва. У виртуального розничного покупателя нет счёта и группы.
При первой привязке отправляется одно сообщение с текущим балансом.

Это заменяет прежнюю схему «редактируемый закреп + копия». При переходе
`unpin_previous_balance` снимает только известный закреп бота по точному ID.
Чужие закрепы и старые сообщения остаются. Контракт Telegram:
[unpinChatMessage](https://core.telegram.org/bots/api#unpinchatmessage).

## Привязка и права

1. Добавить цифрового бота в группу с возможностью отправлять сообщения.
   Для проверки команды привязки через `getChatMember` рекомендуется роль
   администратора, но права закрепления/удаления для публикаций не нужны.
2. От личного аккаунта сотрудника, привязанного к CRM-боту, отправить
   `/balance_bind ID`, где ID — цифровой покупатель из CRM.
3. Проверяются действующий StaffBotAccess, право `manage_digital_buyers`,
   роль администратора/владельца группы у сотрудника и участие бота в группе.

Название группы и пригласительная ссылка не раскрывают баланс. Группы
поставщиков запрещены; перепривязки на другого покупателя автоматически нет.
Владелец CRM может использовать `bind_chat_as_owner` для уже обнаруженной
группы; требуются superuser, права настройки и покупателей, проверка токена,
участия бота и отсутствия конфликтующих привязок. Действие записывается в аудит.

## Очередь и учёт

В inline-меню CRM-бота сотрудников под логотипом доступна кнопка
«Отправить баланс покупателю». Требуются `use_staff_bot`, действующая привязка,
а также `view_digital_sales`, `manage_digital_buyers`, `telegram_digital_sales`.
Кнопка открывает список цифровых покупателей по 20 с переходами между страницами.
У покупателей без `BuyerBalanceChat` есть пометка «нет чата»; выбор объясняет,
что сначала нужна привязка. Розничный покупатель без баланса в список не входит.
Чтобы открыть обновлённое меню после внедрения, отправить `/menu`.
Нажатия меняют подпись и кнопки текущего сообщения. Каждое новое открытие списка
получает отдельный ключ: повтор одного выбора не дублирует отправку, а новое
открытие позволяет выполнить следующую отправку при том же Telegram message ID.

После выбора `digital_sales.staff_balances.request_balance` в транзакции
сохраняет снимок суммы/московского времени в прежнюю `BalanceChatPublication`,
не создаёт движений денег и не меняет баланс. Сообщение отправляет цифровой бот
в привязанную группу, используя прежний `publish_one`, без закрепления и изменения
старых сообщений. Ответ CRM-бота честно сообщает постановку в очередь, а не
гарантирует состоявшуюся доставку. Новый worker и миграция не нужны.

Ключ публикации привязан к StaffBot, StaffBotAccess и ID сообщения со списком:
повтор update или двойной клик не создают копию, а выбор другого покупателя
из уже использованного списка просит открыть новый. Для новых запросов действует
`StaffBot.cooldown_seconds`. Перед каждым выбором свежие права проверяются заново.
Нельзя обойти прежнюю ошибку/uncertain в чате новым запросом: сначала проверяется
ошибочная отправка в настройках CRM. Выключенный цифровой бот также не принимает
новую ручную отправку. Аудит `buyer_balance_requested` содержит покупателя,
группу, публикацию и сотрудника. Сетевых запросов в обработчике update нет.
Смена покупателя у чата перед отправкой по-прежнему блокируется в `publish_one`.

Вход в этот сценарий обрабатывается до ожидаемого ввода цены цифровой продажи:
отменяется только временное ожидание текста `StaffConversation`, сам заказ и
черновик не меняются. Кнопка не выдаёт доступ к оформлению продаж и не создаёт
новых покупателей. Группы/получатели не выбираются из произвольного Telegram ID.

`enqueue_balance` вызывается в транзакции `move_balance`, завершения цифровой
продажи и сторно оплаченной продажи. Непроведённая оплата сообщений не создаёт.
Повторное завершение или отмена не дублируют событие. Сумма и время — снимок
события, финансовая история не переписывается ради отправки сообщения.

`BalanceChatPublication` хранит уникальный event key, снимок текста, состояние,
ID отправленного сообщения и ошибки. Этапы новой отправки: send → create → sent.
Поля `copy_message_id` и старые edit/pin/copy сохранены для совместимости:
известный ID уже отправленной копии завершает событие без нового сообщения;
иначе старая ожидающая задача отправляет одно новое сообщение без edit/pin.
`BuyerBalanceChat.message_id` больше не является редактируемым оригиналом;
старый ID используется только для точного снятия прежнего закрепа при переходе.

Timeout/неизвестный исход sendMessage не доказывает отсутствие сообщения.
Событие получает uncertain и автоматически не повторяется. Незавершённые
create/copy после перезапуска также требуют проверки, если отправленный ID
не сохранён. Сетевые ошибки до отправки и rate limit повторяются ограниченно.
Ошибка раннего события блокирует последующие только в том же чате.

В настройках цифрового бота администратор после проверки чата может указать
ID уже полученного сообщения: задача завершится без редактирования или повторной
отправки. Если сообщения точно нет, можно явно разрешить повтор без ID.
Ошибка доставки не отменяет оплату или баланс. Нового polling-процесса нет:
доставка встроена в прежний цифровой worker. Внедрение режима без закреплений
не требует изменения схемы БД. Сценарии `test_chat_balances.py` обновлены,
но по действующему поручению владельца не запускаются.
