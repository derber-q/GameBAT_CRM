# Ревизия конкретного склада

## Как пользоваться

Откройте «Склад» → нужный склад → **Ревизия** (`/crm/warehouse/<id>/revision/`). При первом открытии сотрудник с полным доступом к складу может сразу отметить товар: первый POST атомарно создаёт начальный цикл и сохраняет отметку. GET не создаёт цикл. **Новая ревизия** открывает подтверждение: «Начать новую ревизию? Все текущие отметки этого склада будут сброшены.» Отмена и Escape ничего не изменяют.

Нажимайте большую область **Остаток сходится**. Карточка становится зелёной только после подтверждения сервера. Повторное нажатие снимает отметку. Состояние и прогресс видны после перезагрузки, выхода/входа и на другом устройстве. Для получения чужих последних отметок достаточно обновить страницу; фонового опроса и websocket нет.

Панель с прогрессом, началом цикла и режимом закрепляется сверху. Основной интерфейс — карточки с названием, полным местом хранения и локальным количеством; зона переключения не менее 50 px. На широком экране карточки располагаются в две колонки. Горизонтальная прокрутка карточек не нужна. Сохранение не меняет складские количества, цены, себестоимость или очередь Avito.

## Данные и ограничения

- `WarehouseRevision`: склад, автор/время начала, `is_active`, время закрытия. Частичный уникальный индекс допускает только один активный цикл на склад. CHECK связывает активность с отсутствием/наличием времени закрытия.
- `WarehouseRevisionItem`: цикл, ровно одна ссылка на CD или Tech, `checked`, автор/время подтверждения и `invalidated_at`. Отдельные уникальные ограничения `(revision, cd)` / `(revision, tech)` исключают дубли и различают совпадающие числовые ID CD и Tech. CHECK требует дату у подтверждённой отметки.
- Товарные ссылки защищены `PROTECT`. Существующий механизм удаления номенклатуры распознаёт историю ревизии и архивирует использованную карточку вместо удаления истории. Пользователь при удалении учётной записи заменяется на NULL; отметка остаётся.
- Список не копирует остатки: при каждом открытии вычисляется по `CDWarehouseStock` / `TechWarehouseStock` выбранного склада с `quantity > 0`. Нулевой остаток, другая площадка, реализация и товар в пути не участвуют. Непроверенная позиция может ещё не иметь `WarehouseRevisionItem`.
- Товар, поступивший во время цикла, появляется непроверенным. При обнулении или удалении локальной строки сигнал ставит `invalidated_at` только в текущем цикле этого склада. Исходная отметка и её автор/время остаются в БД; эффективное состояние при возврате товара — непроверенное. Следующая ручная отметка снимает эту пометку. Изменение положительного количества без обнуления сохраняет отметку и показывает новое количество.
- Новая ревизия атомарно закрывает старый цикл и создаёт новый. История не удаляется. В POST передаётся ожидаемый номер цикла: запрос из устаревшей вкладки и повторная отправка не создают лишний цикл и не меняют текущие отметки.

## Порядок карточек

**По товарам:** сначала CD по Platform, затем Tech по ProductType. Группы и имена сортируются по алфавиту с `casefold`, при совпадении — по ID.

**По местам хранения:** назначения загружаются в существующем порядке `position, id`. Только первое определяет группу и ключ сортировки. Существующий `parse_storage_location` даёт компоненты `(room, rack, shelf, columns)`, где номера сравниваются численно: A2 перед A10. Полный список отображается через `storage_locations_for_stock`. Одна складская строка создаёт одну карточку, дополнительные места не дублируют товар. Без места — отдельная группа в конце. Смена режима ничего не записывает в БД.

## Доступ и сохранение

Использованы действующие права страницы склада: `warehouse.view_warehouse_stock` либо `catalog.view_cd` / `catalog.view_tech`. Права на тип товара проверяются как для чтения, так и внутри сервиса отметок. Для начала общего цикла требуется полный `warehouse.view_warehouse_stock` (либо superuser), чтобы сотрудник с доступом только к CD не сбрасывал скрытые от него отметки Tech. У такого сотрудника прогресс считается только по доступным типам, что явно указано на странице. Отдельных назначений доступа к конкретным складам в текущем проекте нет; ревизия сохраняет существующую модель доступа.

Изменения принимаются только POST с CSRF. Сервер проверяет склад, действующий цикл, тип/ID товара и положительный локальный остаток; количество из клиента не используется. Начало цикла и отметка выполняются в транзакциях с общим порядком блокировки Warehouse → Stock. SQLite использует проектный `transaction_mode=IMMEDIATE`; краткая конкуренция записи обрабатывается ограниченным повтором всей транзакции. При закрытом цикле/исчезнувшем остатке ответ 409, а интерфейс предлагает обновить страницу.

Fetch отправляет только идентификаторы и желаемое состояние, блокирует повторное нажатие до ответа. До успеха остаётся прежний цвет и флаг; при ошибке отображается сообщение. Запросы одной страницы выполняются последовательно, чтобы старый ответ не затёр прогресс нового. Прогресс вычисляется сервером по видимым положительным остаткам и действующим отметкам. localStorage/sessionStorage/cookies не используются для хранения ревизии.

### Исправление первого запуска

В рабочей базе не было ни одного цикла, а шаблон отключал все флажки до явного начала. По обращению пользователя первый флаг теперь доступен сотруднику с полным правом склада: сервер атомарно создаёт первый цикл и сохраняет отметку. Если товар исчез, транзакция откатывает и создание цикла. При существующем цикле запрос без его номера отклоняется: старая вкладка не может незаметно сбросить или изменить новую ревизию. JS получает номер цикла, обновляет последующие запросы и форму подтверждения; версия скрипта повышена до 2.
