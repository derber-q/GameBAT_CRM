# Оптовая витрина ReSOURCE

Витрина реализована в приложении `resource_storefront` внутри CRM. Она использует те же модели `CD`/`Tech`, фотографии каталога и оптовые цены. Остаток считается только по складу, выбранному в настройках витрины. Из карточки браузера не принимаются цена, склад или контакт для продажи.

## Маршруты

- Покупатель входит по персональной ссылке `/opt/<token>/`; после проверки секрет из адреса заменяется обычным `/opt/`.
- `/opt/`, каталог, поиск, карточки, новости, корзина, checkout и защищённые фотографии требуют активного допуска.
- Внутренняя CRM работает под `/crm/`: вход `/crm/accounts/login/`, админка `/crm/admin/`.
- Старая публичная точка уведомлений Яндекс Маркета `/integrations/yandex/notifications/` сохранена. Публичные файлы Маркета также оставлены на прежнем `/integrations/yandex/media/<uuid>/`; служебный интерфейс Маркета находится под `/crm/integrations/yandex/`.
- Контакты и ссылки доступны из `/crm/price/`; редактор витрины — `/crm/integrations/storefront/`.

При переносе сайта нужно настроить reverse proxy на корень приложения: `/crm/`, `/opt/`, `/static/` и существующие публичные URL Яндекс Маркета должны попадать в Django. Статические файлы раздаются от `/static/`. Старые адреса CRM теперь не обслуживают её страницы.

## Миграции и склад

Перед применением миграций к рабочей БД сделайте согласованную резервную копию SQLite по инструкции из `docs/operations.md`. Новые миграции добавляют признак публикации в каталог, контакт/допуск/редакционные модели, снимки покупателя в продаже и возможность системного происхождения продажи (`created_by = NULL`). Старые продажи сохраняют прежние значения.

Миграция выбирает склад витрины автоматически только при единственном точном совпадении `Варфоломеева 265`. Если название не найдено или неоднозначно, склад оставляется ненастроенным: сотрудник с `resource_storefront.manage_storefront` должен выбрать его в редакторе. Новый склад миграция не создаёт.

```powershell
.venv\Scripts\python.exe manage.py migrate
.venv\Scripts\python.exe manage.py check
.venv\Scripts\python.exe manage.py verify_inventory
```

Для локального безопасного прогона используйте тестовую БД, а не рабочую базу. Витрина скрывает товар, если он снят с публикации, архивирован, не имеет положительной оптовой цены или его остаток на выбранном складе равен нулю. Новинки и подборки хранят выбор товара, но не цену и не запас.

## Ключ, права и первый контакт

Ссылка содержит криптографически случайный секрет длиной 48 байт. Для повторного копирования в CRM сохраняются digest и обратимо зашифрованный токен. Локально ключ Fernet создаётся автоматически в `.resource-token-encryption-key` и переиспользуется после перезапуска. На сервере можно задать `RESOURCE_TOKEN_ENCRYPTION_KEY` или путь к файлу через `RESOURCE_TOKEN_ENCRYPTION_KEY_FILE`.

```powershell
.venv\Scripts\python.exe -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"
$env:RESOURCE_TOKEN_ENCRYPTION_KEY = '<сохранённый ключ>'
```

Используйте одно и то же значение во всех экземплярах Django, храните отдельно от Git и резервируйте по правилам хранения секретов CRM. Файл локального ключа добавлен в `.gitignore`. Если ключ потерян, действующие buyer-ссылки нельзя скопировать повторно; перевыпустите их новым ключом. Ключ не записывается в БД или журнал.

Выдайте сотрудникам только нужные permissions:

- `resource_storefront.manage_wholesale_contacts` — контактные лица и персональные ссылки;
- `resource_storefront.manage_storefront` — содержимое витрины и склад.

При создании контакта CRM сразу выпускает персональную ссылку. Список пользователей и ссылки показаны в блоке страницы «Прайс»; там ссылку можно скопировать или перевыпустить. Перевыпуск отключает предыдущий токен и уже открытые сессии; отключение действует при каждом запросе. Не публикуйте ссылки в общедоступных местах.

## Каталог и содержимое

В редакторе выберите склад, заполните тексты главной и добавьте товары в «Новинки», подборку главной или тематические подборки. Создавайте новости в статусе «Черновик», проверьте текст и обложку, затем публикуйте. Форматированный HTML намеренно не принимается: текст автоматически экранируется. Кнопка главной принимает только внутренний путь или HTTPS URL. Фотографии проверяются по формату и содержимому, покупательские изображения выдаются через проверку допуска и наличия.

Начальные рекламные тексты не задают сроки, гарантии, скидки или адреса. Заполните реальные контакты и условия до передачи покупательских ссылок. Демонстрационных товаров и заказов миграции не добавляют.

## Создание продажи

Checkout создаёт обычную незавершённую продажу через `sales.services.create_sale`: оптовая цена, тип «Опт», «Наличные — постоплата», не оплачена, исходный статус «Создан», склад из настройки. CRM-сервис одной транзакцией повторно проверяет остаток, списывает товар и сохраняет снимок себестоимости. Кассовая проводка при создании не появляется. Покупательские контактные данные копируются в поля снимка продажи; комментарий покупателя хранится отдельно от заметки сотрудника. Отмена и редактирование продолжают использовать существующие сервисы продаж.

SQLite работает с `transaction_mode=IMMEDIATE`, а сервис продаж проверяет строки остатков внутри своей транзакции. Проверки SQLite подтверждают поведение используемой конфигурации, но не являются доказательством конкурентной блокировки PostgreSQL.

## Проверки

```powershell
.venv\Scripts\python.exe manage.py test resource_storefront --noinput
.venv\Scripts\python.exe manage.py check
.venv\Scripts\python.exe manage.py makemigrations --check --dry-run
```

Персональные страницы и изображения имеют `no-store`, `noindex` и `no-referrer`. Сторонняя аналитика не подключена.
