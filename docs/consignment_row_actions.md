## Как работают кнопки

В каждой активной строке доступны «Товар реализован» и «Снять с реализации», если
есть соответствующие права. Обе открывают подтверждение в стандартном dialog CRM.
Название товара и площадка всегда видны, показывается актуальный для строки остаток.

- При количестве 1 ввод количества скрыт; отправляется 1, итог подтверждения это указывает.
- При количестве больше 1 поле обязательно и изначально пустое: пользователь должен
  самостоятельно указать количество. `min=1`, `step=1`, `max` — отображаемый остаток.
- Возврат всегда требует вручную выбрать существующий склад. Значение по умолчанию
  пустое; исходный склад не подставляется автоматически.
- Для продажи сохраняется выбор наличных / банковского счёта, как в старой форме.
- Отмена и Escape ничего не отправляют. Только «Подтвердить» вызывает POST.
- UI не уменьшает остаток самостоятельно: после ответа сервер заменяет строку
  фактическим HTML. Нулевая строка исчезает, счётчики и пустые группы обновляются.
- Полной перезагрузки нет; поиск, прокрутка и свёрнутые блоки сохраняются.
- При отказе backend показана причина и фактическая строка. При сетевой ошибке
  не показывается ложный успех — требуется обновить список перед повтором.

## Данные, количество и выбранный склад

Новый endpoint: `POST /consignment/stocks/<kind>/<id>/action/`.
Он определяет именно конкретную исходную запись (тип, площадка, склад-источник, товар),
а не произвольную позицию с тем же названием.

`return_from_consignment` расширен необязательными параметрами `target_warehouse_id`
и `stock_id`. У старых Python-вызовов остаётся прежний возврат на исходный склад.
Новый UI обязательно передаёт выбранный склад назначения. Исходная запись реализации
остаётся связанной со своим исходным складом, уменьшается только её количество;
увеличивается остаток именно выбранного склада. Отсутствующая строка складского
остатка создаётся, новый Warehouse не создаётся.

В модели Warehouse нет флага закрытия и объектных ограничений по складам: действуют
общие права. Поэтому доступны все реальные склады. Несуществующий или невыбранный
склад отклоняется сервером.

Положительное целое количество проверяется сервером и затем сравнивается с текущим
остатком внутри существующих сервисов. Ноль, отрицательные, дробные и превышение
остатка отклоняются. Проверка целочисленности не допускает усечения float до int.

Продажа использует `record_consignment_sale(quantity=...)`: прежние Sale/SaleItem,
завершённый статус, снапшот себестоимости, вознаграждение за единицу, сумма за указанное
количество, кассовая проводка только для наличных, product audit. Повторного списания
со склада нет. Вознаграждение и себестоимость новые операции не меняют.

## Атомарность, конкуренция и повторные запросы

`perform_row_action` — транзакционная обёртка над существующими сервисами, а не новая
реализация движения остатков. Используются `transaction.atomic` и `select_for_update`.

Каждая строка получает подписанное сервером подтверждение: пользователь, тип/ID строки,
количество, вознаграждение и уникальный UUID. Подпись нельзя перенести на другую строку
или пользователя. Перед операцией количество и вознаграждение повторно сверяются с БД;
при изменении нужно проверить актуальную строку и подтвердить заново.

Таблица `ConsignmentActionReceipt` хранит уникальный ключ выполненного действия.
Первая запись внутри транзакции резервирует ключ, сериализуя также записи SQLite.
Повтор того же POST не проводит ни возврат, ни продажу повторно: получает 409 и текущую
строку. Receipt откатывается вместе со всеми движениями, если операция не удалась.
При блокировке БД нет автоматического повтора финансового действия.
В браузере кнопки блокируются на время запроса, повторный submit игнорируется.

Проверены конкурентные пары на двух отдельных соединениях: возврат/возврат,
продажа/продажа, возврат/продажа. При попытке обоих сотрудников израсходовать один
остаток успешно выполняется только одна операция, отрицательного остатка нет.

## История и права

Возврат по-прежнему создаёт ConsignmentMovement и ConsignmentMovementItem с товаром,
площадкой, выбранным складом возврата, количеством, пользователем и временем.
В product audit сохранены изменения складского и суммарного остатка реализации;
дополнительно записывается количество конкретной строки реализации до/после.
Продажа сохраняет прежнюю историю Sale и движения денег.

Права: `consignment.return_stock` для возврата, `sales.create_sale` для продажи,
соответствующее `view_cdconsignmentstock` / `view_techconsignmentstock` для доступа
к типу строки. Superuser — штатное исключение. Проверки есть и в UI, и в endpoint.
CSRF не отключён, GET не изменяет данные. Без `confirmed=1` операция не проводится.

## Поиск

Используются существующие `catalog/_product_filters.html`, `product_filter_context`,
`filter_product_querysets` и общий `product_search`: GET `search`, тот же внешний вид,
«Применить», «Сбросить», фильтры платформы/бренда/типа и глобальное сканирование штрихкода.
Поиск работает по ID, названию (включая регистр кириллицы), артикулу, CUSA/PPSA для CD,
любому штрихкоду из BarcodeRegistry, включая дополнительные штрихкоды.

На странице площадки queryset ограничен её ID, на общей — видимыми площадками;
группировка по площадке → CD/платформа либо Tech/тип сохранена. Нет совпадений —
«Товары не найдены». Нулевые и архивные позиции в активный список не включаются.
`select_related` загружает продукт, категорию, площадку и склад. Рост числа строк
и площадок не добавляет запрос на каждую строку; это проверено тестом.
