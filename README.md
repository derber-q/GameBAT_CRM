## Возможности

- собственная модель пользователя, роли администратора и работника;
- наборы прав на основе Django Group и индивидуальные permissions;
- защищённые подтверждающие документы пользователей;
- несколько физических складов с независимыми остатками CD и техники;
- общие остатки, межскладские перемещения и отдельный учёт товара в пути;
- поставщики с серверным сокрытием реквизитов;
- атомарная приёмка поставок на выбранный склад, распределение расходов и средневзвешенная себестоимость физического складского остатка;
- редактирование принятых поставок через ревизии, отмена и финализация;
- атомарная передача товара с выбранного склада на реализацию и возврат на выбранный склад;
- отдельные касса и сейф на каждом складе, атомарные переводы между ними и единый неизменяемый журнал;
- ценообразование с розничной, оптовой, маркетплейсной и текущими поставщицкими ценами;
- генерация складских и закупочных XLSX-прайсов, полный импорт актуальных цен поставщиков в AED;
- импорт заполненного оптового XLSX в стандартную форму продажи без автоматического проведения;
- отдельные клиентские закупочные заказы со снимками цен и поставщиков, приёмкой и возвратами;
- ручные подборки заказов поставщикам с агрегацией выбранных клиентских заказов;
- продажи со снимками цен, строгими статусами, наличной и банковской оплатой с общим механизмом постоплаты;
- несколько штрихкодов, вес, игровые серии, места хранения на складах и защищённые галереи товаров;
- интеграция Avito: привязки, очередь синхронизации, подтверждённая сверка цен/остатков;
- односторонний Google Sheets-прайс по физическому остатку с ручной и десятиминутной синхронизацией;
- статистика продаж и обзор пользователей по группам `stuf`;
- курсы USDT/RUB (Rapira) и USDT/AED (Coinbase) в шапке;
- единый интерфейс CRM и стилизованный Django Admin.

## Быстрый запуск

```powershell
python -m venv .venv
.venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt
python manage.py migrate
python manage.py createsuperuser
python manage.py runserver
```

Откройте `http://127.0.0.1:8000/`. Первый администратор создаётся только штатной командой `createsuperuser`; готовых логинов и паролей в проекте нет.

Для production задайте `DJANGO_SECRET_KEY`, `DJANGO_DEBUG=0` и `DJANGO_ALLOWED_HOSTS`. При локальной разработке секрет автоматически создаётся в игнорируемом файле `.django-secret-key`.

## Основные разделы

- `/warehouse/` — общие остатки (совместимый старый адрес);
- `/warehouse/global/` — общие остатки;
- `/warehouse/<id>/` — положительные локальные остатки конкретного склада;
- `/warehouse/transfers/` — межскладские перемещения;
- `/supplies/` — история и приёмка поставок;
- `/consignment/` — товар на реализации, передача и возврат;
- `/pricing/` — ценообразование;
- `/price/` — XLSX-прайсы, настройки документов и версии закупочных прайсов;
- `/sales/` — продажи;
- `/sales/incomplete/`, `/sales/completed/`, `/sales/cancelled/` — списки по состоянию;
- `/statistics/` — статистика;
- `/nomenclature/` — карточки CD/Tech;
- `/integrations/avito/` — подключение и синхронизация Avito;
- `/integrations/` — ключи интеграций и настройки Google Sheets;
- `/orders/` — клиентские закупочные заказы и подборки поставщикам;
- `/cash/<warehouse_id>/` — касса, сейф и общий денежный журнал выбранного склада;
- `/suppliers/` — поставщики;
- `/accounts/users/` — пользователи;
- `/accounts/stuf/` — отдельные таблицы пользователей по Django Groups;
- `/accounts/permission-sets/` — наборы прав;
- `/admin/` — справочники, товары, площадки и валютные курсы.

Platform, Brand, ProductType, SalesPlatform и CurrencyRate управляются через Django Admin. Рабочие операции поставки и реализации выполняются только в собственном интерфейсе CRM.

Кнопка «Продажа» ведёт на новую продажу, её меню содержит списки продаж и «Касса». Меню `stuf` содержит статистику, пользователей и поставщиков; клик по `stuf` открывает обзор групп. Текущие ограничения видимости меню для несуперпользователя описаны в `docs/development.md`.

`start_localhost.ps1` запускает сайт в локальной сети и отдельный обработчик Avito. Обработчик может отправлять цены и остатки в реальный аккаунт. Для изолированной проверки интерфейса запускайте только `runserver`, без рабочих ключей интеграции.

## Проверки

```powershell
python manage.py test
python manage.py check
python manage.py makemigrations --check
python manage.py verify_inventory
python manage.py verify_cash
```

`verify_inventory` только диагностирует расхождения между агрегированным полем товара и остатками площадок, ничего не исправляя автоматически.

JavaScript-проверки запускаются Node.js: все файлы `test_*.cjs`, перечисленные в `docs/operations.md`. Актуальный результат полного прогона см. в `docs/verification.md`.

## Рабочие данные

Рабочая база `db.sqlite3` исключена из Git. Она содержит учётные данные CRM и зашифрованные реквизиты интеграций; для контрольных точек создаётся отдельная согласованная SQLite-копия. `.django-secret-key`, `.integration-encryption-key`, `.env`, `protected_media/`, резервные копии и сгенерированные отчёты также не добавляются в Git. Старые коммиты могут содержать прежние снимки базы. Для восстановления подключения Avito нужны исходный ключ шифрования, сохранённый отдельно, либо повторный ввод реквизитов. Сами связи объявлений с товарами хранятся в БД.

## XLSX и закупочные заказы

Розничный и оптовый прайсы формируются отдельно для выбранного склада и содержат только положительный локальный остаток. В оптовом файле клиент меняет только количество; при загрузке CRM игнорирует цены из файла, повторно проверяет текущий остаток и переносит позиции в обычную форму новой продажи. Продажа возникает только после подтверждения сотрудником.

Для поставщика скачиваются два шаблона: диски и техника, каждый с активной номенклатурой своего типа независимо от остатка, кроме товаров с флагом «Не отображать в шаблоне для поставщиков». Флаг доступен при создании и редактировании карточки. На странице «Импортные прайсы» есть пустые шаблоны и отдельные файлы каждого поставщика с его последними сохранёнными ценами. Новые товары включаются автоматически, без цены при отсутствии предложения. Для скачивания заполненных шаблонов нужны оба права: `price.download_supplier_template` и `price.view_supplier_prices`. Можно загрузить один файл или оба, включая ранее скачанные шаблоны: обновляются цены активных товаров из файла, пустые цены удаляют их предложения и остаются пустыми при следующем скачивании. Цены отсутствующих в файле товаров сохраняются, архивные строки пропускаются. Товарные строки должны соответствовать служебному листу; заполнять нужно только «Цена AED». Если при совместной загрузке один файл ошибочный, цены обоих типов остаются прежними.

Закупочный прайс фиксирует курс, выбранного поставщика и его цену. При создании вводятся три тарифа доставки USDT/кг, привязанные к типам техники: общий, для консолей/мини-ПК/VR/AR и для памяти/накопителей. Для дисков отдельно вводится фиксированная доставка в RUB за штуку. Доставка техники рассчитывается по весу с упаковкой и курсу USDT → RUB; недостающий вес программа запрашивает до генерации. Тарифы, вес и группа сохраняются в снимке без пересчёта старых версий. Сохранённая наценка в рублях подставляется в следующую версию; предоплата рассчитывается как новая база + доставка + сохранённая наценка, а постоплата — по текущему правилу. Отрицательная наценка выделяется красным и требует подтверждения при сохранении расчёта. Доплата за постоплату Tech определяется типом и моделью, для CD действует правило 60/80/100 ₽. Ручная доплата редактируется после постоплаты и запоминается за товаром; [согласованные ставки](docs/procurement_postpayment.md). Для клиента выгружаются отдельные XLSX дисков и техники без сведений о поставщиках даже на техническом листе. Один или оба заполненных файла одной версии загружаются в общий предварительный состав заказа. Созданный после подтверждения заказ проходит только цепочку `Создан → Подтверждён → Принимается → Выполнен`. Предоплата и постоплата поступают в кассу выбранного склада один раз; уменьшение предоплаты при приёмке создаёт атомарный возврат, не затрагивая сейф.

Все действия разделены Django permissions и доступны через существующие наборы прав. Для денежных переходов дополнительно нужны права кассы, а сведения о поставщиках защищены отдельными правами просмотра.

При переходе на мультисклад старые физические остатки переносятся миграцией в подтверждённый склад `Варфоломеева 265`, после чего прежнее поле `CD/Tech.quantity` удаляется. Перед применением миграций к рабочей базе рекомендуется создать резервную копию SQLite.
