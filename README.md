# GameBAT CRM

Автономная внутренняя CRM для учёта видеоигр и техники GameBAT Store. Первая версия построена на Django Templates и Django ORM, не использует внешние API и сторонние интеграции.

## Возможности

- собственная модель пользователя, роли администратора и работника;
- наборы прав на основе Django Group и индивидуальные permissions;
- защищённые подтверждающие документы пользователей;
- несколько физических складов с независимыми остатками CD и техники;
- общие остатки, межскладские перемещения и отдельный учёт товара в пути;
- поставщики с серверным сокрытием реквизитов;
- атомарная приёмка поставок на выбранный склад, распределение расходов и глобальная средневзвешенная себестоимость;
- неизменяемая история принятых поставок;
- атомарная передача товара с выбранного склада на реализацию и возврат на выбранный склад;
- отдельные касса и сейф на каждом складе, атомарные переводы между ними и единый неизменяемый журнал;
- ценообразование с розничной, оптовой, маркетплейсной и текущими поставщицкими ценами;
- генерация складских и закупочных XLSX-прайсов, полный импорт актуальных цен поставщиков в AED;
- импорт заполненного оптового XLSX в стандартную форму продажи без автоматического проведения;
- отдельные клиентские закупочные заказы со снимками цен и поставщиков, приёмкой и возвратами;
- ручные подборки заказов поставщикам с агрегацией выбранных клиентских заказов;
- продажи со снимками цен, строгими статусами, наличной оплатой, постоплатой и банковским счётом;
- ручные курсы USD/RUB, AED/RUB и USD/AED;
- единый интерфейс CRM и стилизованный Django Admin.

## Быстрый запуск

```powershell
python -m venv .venv
.venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt
python manage.py migrate
python manage.py createsuperuser
python manage.py runserver
```

Откройте `http://127.0.0.1:8000/`. Первый администратор создаётся только штатной командой `createsuperuser`; готовых логинов и паролей в проекте нет.

Для production задайте `DJANGO_SECRET_KEY`, `DJANGO_DEBUG=0` и `DJANGO_ALLOWED_HOSTS`. При локальной разработке секрет автоматически создаётся в игнорируемом файле `.django-secret-key`.

## Основные разделы

- `/warehouse/` — общие остатки (совместимый старый адрес);
- `/warehouse/global/` — общие остатки;
- `/warehouse/<id>/` — положительные локальные остатки конкретного склада;
- `/warehouse/transfers/` — межскладские перемещения;
- `/supplies/` — история и приёмка поставок;
- `/consignment/` — товар на реализации, передача и возврат;
- `/pricing/` — ценообразование;
- `/price/` — XLSX-прайсы, настройки документов и версии закупочных прайсов;
- `/sales/` — продажи;
- `/orders/` — клиентские закупочные заказы и подборки поставщикам;
- `/cash/<warehouse_id>/` — касса, сейф и общий денежный журнал выбранного склада;
- `/suppliers/` — поставщики;
- `/accounts/users/` — пользователи;
- `/accounts/permission-sets/` — наборы прав;
- `/admin/` — справочники, товары, площадки и валютные курсы.

Platform, Brand, ProductType, SalesPlatform и CurrencyRate управляются через Django Admin. Рабочие операции поставки и реализации выполняются только в собственном интерфейсе CRM.

## Проверки

```powershell
python manage.py test
python manage.py check
python manage.py makemigrations --check
python manage.py verify_inventory
python manage.py verify_cash
```

`verify_inventory` только диагностирует расхождения между агрегированным полем товара и остатками площадок, ничего не исправляя автоматически.

## XLSX и закупочные заказы

Розничный и оптовый прайсы формируются отдельно для выбранного склада и содержат только положительный локальный остаток. В оптовом файле клиент меняет только количество; при загрузке CRM игнорирует цены из файла, повторно проверяет текущий остаток и переносит позиции в обычную форму новой продажи. Продажа возникает только после подтверждения сотрудником.

Шаблон поставщика содержит всю номенклатуру независимо от остатка. Успешная загрузка полностью заменяет текущий снимок цен выбранного поставщика; пустые цены удаляют предложение, а любая ошибка оставляет прежний снимок целиком.

Закупочный прайс фиксирует курс, выбранного поставщика и его цену. Клиентский файл не содержит сведений о поставщиках даже на техническом листе. Созданный по нему заказ проходит только цепочку `Создан → Подтверждён → Принимается → Выполнен`. Предоплата и постоплата поступают в кассу выбранного склада один раз; уменьшение предоплаты при приёмке создаёт атомарный возврат, не затрагивая сейф.

Все действия разделены Django permissions и доступны через существующие наборы прав. Для денежных переходов дополнительно нужны права кассы, а сведения о поставщиках защищены отдельными правами просмотра.

При переходе на мультисклад старые физические остатки переносятся миграцией в подтверждённый склад `Варфоломеева 265`, после чего прежнее поле `CD/Tech.quantity` удаляется. Перед применением миграций к рабочей базе рекомендуется создать резервную копию SQLite.
