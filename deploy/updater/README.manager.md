# Менеджер ручных обновлений ReSOURCE

Этот компонент устанавливается отдельно от каталога CRM и не обновляет сам себя.
Требуются Linux, Python 3.14, rootless Docker с Compose и утилита `setfacl` (пакет acl).
Менеджер запускается под владельцем отдельного rootless Docker, без root/sudo.
Перед включением обязательны проверенный этап B, резервное восстановление и испытание
на выбранном VPS. Текущая CRM пока блокирует production; менеджер этот запрет не снимает.

## Подключение после подготовки VPS

1. Установить пакет в `/opt/resource-manager`, создать там `.venv`. Python-пакеты
   менеджеру не нужны: он использует стандартную библиотеку и Docker CLI.
2. Подготовить production Compose с сервисами `web`, `supervisor`, `postgres`.
   Web и supervisor используют один образ по digest из
   `ghcr.io/derber-q/gamebat_crm`, user `10001:10001`, read_only, cap_drop ALL,
   no-new-privileges. Не передавать Docker socket в эти сервисы. Перезапускать
   supervisor нужно со штатным корректным завершением всех worker.
3. Постоянные медиа, ключи и конфигурация находятся в отдельном shared-каталоге.
   Все его файлы должны быть доступны менеджеру для чтения резервной копии;
   проверьте права новых файлов, создаваемых CRM. Не хранить там сокеты и ссылки.
   PostgreSQL резервируется через `pg_dump` сервиса `postgres`. Не использовать
   SQLite production или два одновременно пишущих экземпляра CRM.
4. Скопировать `manager.example.json` в `/srv/resource-manager/manager.json`, задать
   реальные пути, HTTPS-origin, имя БД/пользователя и **host UID** пользователя web
   внутри rootless Docker. Это UID после отображения user namespace, а не просто 10001.
   Неверный UID не позволяет web посылать команды. Файл конфигурации не должен быть
   доступен для групповой/общей записи. После проверки VPS задать production_verified=true.
5. При частном GHCR выполнить `docker login ghcr.io` под пользователем менеджера с
   доступом только к чтению пакета. Для частного GitHub можно добавить
   `github_token_file` — абсолютный путь к приватному файлу read-only токена.
   Не передавать токен web-контейнеру, в аргументах команд или через форму CRM.
6. Начальную версию CRM развернуть вручную по digest с
   `GAMEBAT_ENV=production`, `GAMEBAT_RELEASE_SHA=<полный SHA>` и явными production
   настройками этапа B. У web и supervisor должны совпадать версии. После настройки
   мониторинга убедиться, что HTTPS `/crm/update-health/` возвращает status=ok.
7. Инициализировать личный журнал менеджера (существующий не перезаписывается):

   ```sh
   GAMEBAT_ENV=production /opt/resource-manager/.venv/bin/python -m deployment --config /srv/resource-manager/manager.json --init
   ```

8. Установить пользовательский `resource-updater.service`, включить rootless Docker
   и менеджер. Менеджер создаёт Unix socket и read-only JSON состояния с ACL только
   для нужного host UID. В web смонтировать **только** `/srv/resource-manager/public`
   read-only в `/run/resource-updates` и отдельный `/srv/resource-manager/gateway.sock`
   в `/run/resource-update.sock`. Задать:

   ```text
   GAMEBAT_UPDATE_STATUS_FILE=/run/resource-updates/status.json
   GAMEBAT_UPDATE_SOCKET=/run/resource-update.sock
   ```

   Не монтировать в web весь каталог менеджера, личную SQLite, backups или releases.
   Socket bind mount после аварийной замены socket-файла требует пересоздания web
   администратором сервера; до этого кнопка безопасно сообщает недоступность канала.
   Не добавлять timer, cron, Watchtower, git pull при старте или webhook установки.

## Подготовка версии и установка

В репозитории есть workflow «Подготовка ручного production-релиза». Он проверяет
Windows/SQLite, Linux/SQLite, PostgreSQL, браузер, миграции и менеджер, затем публикует
образ GHCR. Контекст образа создаётся `git archive`, без локальных файлов и ключей.
Успешный статус `resource/deployment` хранит digest для того же SHA. Новый запуск CI
сначала ставит pending; предыдущий success не перекрывает новую неудачную проверку.

Workflow не устанавливает сайт и не имеет доступа к VPS. Он намеренно не может дать
допуск текущему коду до реализации production/PostgreSQL: production_gate проверяет
реальные production-настройки. Наличие этого YAML не означает, что CI уже запускался.

В CRM superuser открывает «Интеграции → Обновления», нажимает «Проверить обновления»,
сверяет показанный SHA и подтверждает «Обновить до последней версии». Проверка не
устанавливает код. Установка относится к показанному SHA, а не к новому main, который
мог появиться после проверки. Повтор с тем же UUID не создаёт вторую операцию.
При отсутствии связи остаются последние известные сведения с временем их проверки.

Менеджер загружает образ по digest, проверяет labels source/revision/schema,
сверяет фактические миграции работающего PostgreSQL и выполняет кандидата в контейнере
без сети, данных, ключей и Docker socket. Обновление файлов миграций или зависимостей
блокируется до отдельно проверенной процедуры миграций. После остановки web/supervisor
создаются custom dump PostgreSQL, архив shared и контрольные суммы. Dump проверяется
`pg_restore --list`, архив полностью читается. Это не заменяет регулярное испытание
восстановления на отдельном PostgreSQL. Затем меняется только образ web/supervisor;
готовность фиксируется после проверки SHA, БД и стабильных worker через HTTPS.

## Ошибки и откат

Журнал хранится отдельно от кода и доступен после перезапуска сайта. Код ошибки
команды записывается без stdout/stderr с возможными секретами. Резервные копии не
публикуются через CRM. При провале запуска менеджер возвращает предыдущий совместимый
образ в рамках той же ручной операции; БД не восстанавливается и миграции не обращаются.
Кнопка отката также сохраняет новые продажи и данные. Она доступна только для
сохранённого образа с тем же отпечатком миграций/зависимостей.

После прерывания менеджера начатая операция получает interrupted; новые установки
блокируются. Администратор сервера проверяет контейнеры, журнал, резервные копии,
схему и незавершённые операции интеграций. При необходимости вручную запускает
проверенный сохранённый image.compose.json вместе с неизменённым production Compose.
После подтверждения работоспособности, остановив менеджер, выполняет:

```sh
GAMEBAT_ENV=production /opt/resource-manager/.venv/bin/python -m deployment --config /srv/resource-manager/manager.json --reconcile
```

Команда сверяет фактически запущенную версию и health, фиксирует сверку и снимает
блокировку. Она не устанавливает новую версию и не восстанавливает старую БД.
Затем можно запустить менеджер и обновить socket mount web. Никакое восстановление
данных с потерей новых продаж не входит в штатное обновление или откат.

Основания протокола: [GitHub commit statuses](https://docs.github.com/en/rest/commits/statuses),
[публикация образов GitHub Actions](https://docs.github.com/en/actions/tutorials/publish-packages/publish-docker-images),
[Docker rootless](https://docs.docker.com/engine/security/rootless/).
